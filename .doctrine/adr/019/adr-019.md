# ADR-019: Embedding, publication, and projection are independent asset policies

<!-- Reference forms: doc/glossary.md § reference forms. -->

## Context

Doctrine ships a large body of non-code material — templates, hymns, reference
docs, agent definitions, integration scripts, the shipped memory corpus — and
gets it into a client project through one accidental conflation. `src/install.rs`
embeds the whole `install/` tree via rust-embed and the installer projects nearly
every embedded file into `.doctrine/`. **Embedding and installation are therefore
the same policy by accident** (SPEC-009 D1): a file is projected into a client repo
because it happens to sit under the embed root, not because its presence at a
stable project path serves any operational purpose. The client-facing surface
enlarges whether or not a user can meaningfully service what lands there.

This surfaces as concrete cost. Every added template, doc, or adapter grows the
installed footprint and the trust surface. Framework-owned material that a user
might reasonably want to inspect, copy, or repair is only reachable if it was
*installed*, so "make it inspectable" and "install it" are wrongly coupled. And
material that genuinely must occupy a stable path (a managed `.gitignore`, a
config surface, a required harness adapter) is indistinguishable from material
that rode in on embed convenience.

RFC-021 (Claim C1, directionally accepted at high confidence) names the fix: the
policies that today travel together must be pulled apart. This is a corpus-wide
structural question — which properties an asset has, and why it occupies a project
path — not a one-off edit to the installer. Hence an ADR. It is the shared root
for two descending contracts: the SPEC-009/PRD-006 projection revision (REV-028)
and a new library/publication/search spec.

## Decision

**We will treat the following seven asset properties as independent, and make each
an explicit, separately-decided policy.** No property implies another; in
particular embedding ≠ publication ≠ projection. This is the one canonical
vocabulary — descendants (this ADR, REV-028, SPEC-009 D6) cite it unchanged:

```text
owned          canonical change authority over the asset
versioned      compatibility and provenance identity
distributed    delivered with a release or content package
embedded       compiled into the binary — a storage mechanism
runtime-loaded selected from an external/development source at runtime — the storage alternative
published      exposed for inspection/copy through a declared seam, without projection
projected      written to a stable path inside a client repo
```

The first group — owned, versioned, distributed, embedded, runtime-loaded — are
storage/delivery properties (embedding and runtime-loading being the two storage
mechanisms); the remaining two — published, projected — are *exposure* policies
orthogonal to storage. Embedding remains an excellent production default for
*storage*, but it confers neither publication nor projection. From this, three
positions follow:

1. **Projection follows semantic ownership, minimally.** A client installation
   contains only files whose presence at a stable project path is *operationally
   necessary* or materially improves project-level *discoverability, integration,
   control, or supported customization*. Every projected file has an explicit
   owner, a mutation policy, and a stated project-level reason to exist. Everything
   else remains framework-owned and is exposed intentionally, not installed by
   default.

2. **Publication is distinct from projection.** Framework-owned material may be
   public, auditable, and copyable through a declared seam *without* being written
   into the project. Being embedded does not make an asset public API; being
   Doctrine-owned does not make a published asset opaque. A file can be inspectable
   and reusable while living nowhere in the client repo.

3. **Projection boundaries are drawn by volatility, trust, mutation authority,
   consequence, and lifecycle — not footprint.** Where two contents differ on
   those axes they stay distinguishable, even when both belong in agent context.
   The load-bearing instance: **standing project governance and volatile project
   orientation must be physically distinct surfaces.** Orientation is
   agent-improvable by design; standing governance is high-consequence. Their
   different mutation authority means a single surface could not later carry both a
   "behaviours may improve this" affordance and an "explicit acceptance required"
   gate — so the boundary is drawn now, at the **physical** level. Enforcing that
   gate — a trust-acceptance/approval mechanism — is deliberately **out of scope for
   this decision** and deferred to RFC-021 Stage 5; C1 establishes only that the
   surfaces are separable, not how edits to them are trusted.

Physical source roots should follow semantic ownership rather than a single embed
root (directional; exact names are downstream design): artifact/config templates,
composable guidance, sealed definitions, curated reference, integration assets,
base-projection policy, and the shipped memory corpus each own their material.
`install/` ceases to own an asset merely because the binary embeds it.

**Reconciling minimal projection with the distinctions above:** a surface that is
distinct but *not yet populated* is not shipped empty — it **materializes on first
use**, joining the pattern already used for entity roots and customized hymns. Each
such surface has its own observable trigger and permitted actor (entity roots on
first entity of a kind; hymns on first customization; standing governance on
explicit user definition), not one blanket rule. The worked case: standing
governance **appears on disk only when the project explicitly defines standing
governance**, as a surface physically distinct from the volatile orientation
surface. This keeps the base projection minimal while drawing the
governance/orientation boundary up front, so a later Stage-5 trust-acceptance
mechanism inherits a lift-out rather than a re-analysis — without this decision
asserting that mechanism now.

## Consequences

### Positive

- The installed surface shrinks to what has a project-level reason to exist;
  footprint stops tracking embed convenience.
- "Inspectable / copyable" decouples from "installed" — user control is served by a
  publication surface, not by projecting files no one services.
- The governance/orientation split is drawn before the trust mechanism needs it, so
  Stage-5 trust-acceptance granularity is a physical lift-out, not a redesign.
- One shared principle governs both descending contracts (projection revision and
  the library spec), so neither restates it.

### Negative

- More explicit policy to declare: every asset now needs its owner, mutation
  policy, publication status, and projection reason stated, rather than inheriting
  them from the embed root.
- A publication/library surface and materialize-on-demand surfaces are new
  mechanism to build and maintain — the principle is not free to realise.
- Splitting the monolithic embed root into semantic roots is a migration of the
  source tree and the flake `srcWithDist` embed graft
  (`mem.pattern.embed.rustembed-recompile-and-symlinks`).

### Neutral

- Exact source-root names, the publication manifest schema, and the library/search
  surface are deliberately left to the descending specs.
- Migration/cleanup of existing installs is out of scope — there is no meaningful
  external user base (RFC-021 non-goal).

## Verification

- **VA** — a fresh base install contains only the minimal projected set
  (`.gitignore`, `doctrine.toml`, `boot-project.md`); no template, hymn, reference,
  agent, or integration file is projected by default.
- **VA** — standing governance does not ship as a base projection and is a surface
  physically distinct from orientation; `boot-project.md` carries no standing
  governance content. (Trust/approval *enforcement* on that surface is Stage-5, not
  verified here.)
- **VT** — projection policy is manifest-driven and asserted (the base fileset is
  what the projection policy declares, not what the embed root happens to contain).

The *policy* that publication is distinct from projection is established here; its
*delivery* — an actually-published, non-projected, inspectable asset — is **not** a
success condition of this ADR or of contract A. That existence check belongs to the
library/publication contract (B) and is verified there. Baking it in here would
make the C1 projection revision depend on delivering a sibling contract, violating
RFC-021's staging discipline.

Concrete mechanism and the requirement entities are SPEC-009's (REV-028) and the
new library spec's job; this ADR is verified through them, not restated here.
