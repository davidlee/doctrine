# ADR-020: Adopt execution capsules as the dispatch authority boundary

## Context

Doctrine's current dispatch isolates workers with Git worktrees, cooperative
identity markers, harness-specific spawn paths, and a trusted coordination
worktree. That system has accumulated sound local mechanisms, but their
composition is brittle: worker identity and capability vary by harness,
coordination shares a Git object store with untrusted work, and the trusted
orchestrator must replay a large worktree/import choreography correctly.

RFC-025 and SL-241 tested a smaller authority model. A trusted parent can create
a fresh operating-system-confined execution environment, give the worker broad
authority only inside it, harvest a Git bundle as hostile bytes, verify the
pinned result in a second fresh environment, and advance canonical Git state by
one expected-tip compare-and-swap. The Linux/bubblewrap evidence is sufficient
to select that architecture; it is not evidence for a macOS backend or for
production performance.

The costly fork in the road is the authority boundary, not later policy. If the
capsule is only a worktree wrapper, Doctrine retains the existing shared-Git and
harness-identity complexity. If the capsule is the transaction and the trusted
control plane alone owns canonical mutation, later retention, quota, monitoring,
and backend choices remain additive. The design must preserve correct work
through ordinary staleness or conflict without weakening the long-term security
boundary by reopening an old mutable capsule or trusting capsule-controlled Git
configuration.

## Decision

We will make a fresh **execution capsule** the dispatch trust and transaction
boundary. A persistent trusted control-plane orchestrator resolves the contract,
launches one fresh headless worker per phase transaction, harvests and inspects
its result, verifies the exact normalized candidate in a separate fresh capsule,
and alone admits the verified immutable identity into canonical Git state.

The capsule worker has broad local authority, including permission to edit local
Doctrine state and create local commits. It has no authority to mutate canonical
repositories or refs, no canonical credentials, and no writable shared Git object
store. Its local claims, process exit, branch names, and prose are evidence to
inspect, never admission authority.

The target transaction is:

1. Resolve an accepted base and project interpretation policy from that immutable
   base; a phase contract may only restrict the project policy.
2. Provision fresh mutable capsule state, then launch a headless worker through a
   platform backend that enforces the same authority properties.
3. Receive only a minimal completion notification. Snapshot the result bundle
   once into control-plane-owned storage and inspect it through a fresh quarantine
   repository; trusted code never runs Git in a capsule-authored repository.
4. Conform the pinned result to its contract, then verify the exact normalized
   candidate in a separate fresh verification capsule.
5. Record intent in the durable admission journal before canonical mutation and
   advance the accepted ref by one expected-tip compare-and-swap. Ref movement,
   conflict, or failed verification is reported and halted; nothing force-updates
   or silently resolves it.
6. Close and clean up only after the result, or a repair incorporating it, is
   integrated and formally closed, or after explicit operator abandonment.

Git bundle ingestion is the initial result transport. This is a bounded hostile-
file protocol, not a declaration that bundles are intrinsically safe. A later
transport may replace it only while preserving the rule that trusted code never
uses a capsule-authored repository as Git execution context.

Stale results reuse the existing candidate **semantics** behind a capsule-
provenance seam: object-only three-way classification, durable clean/conflicted
state, verification of the exact candidate, immutable-commit admission, and an
expected-tip compare-and-swap. They do not reuse the incumbent coordination-
branch journal as hidden scaffolding. A repair runs in a fresh capsule; harvested
source capsules stay frozen.

Until successful integration and formal closure, a frozen harvested capsule is
live work and v0 never automatically deletes or evicts it. Afterwards its richer
bundle, logs, and permitted transcript material are forensic exhibits that may
follow a separately-owned retention policy, while the compact admission journal
remains durable. V0 adds a conspicuous configurable free-space warning and accepts
manual capacity intervention; it does not add reservation, backpressure, automatic
eviction, or a new rescue archive.

The backend contract is property-based and cross-platform. Linux/bubblewrap is the
measured initial backend. A macOS mechanism must separately demonstrate equivalent
filesystem, process, credential, network, and canonical-repository authority
properties before it can claim parity.

This ADR establishes target architecture, not current implementation. ADR-011 and
the incumbent worktree dispatch remain authoritative until REV-046's cutover gates
are met. Solo `/execute` worktrees are outside this migration.

## Consequences

### Positive

- Canonical mutation has one explicit trusted owner, independent of harness
  identity or worker cooperation.
- Fresh phase and verification environments remove mutable-state carry-over while
  preserving the interactive orchestrator's context outside the capsules.
- Stale but correct work remains recoverable without granting the source capsule
  new authority or importing it wholesale into canonical Git.
- Retention, quota, monitoring, normalization-history, and backend policy remain
  additive choices rather than foundations of correctness.

### Negative

- Every phase pays provisioning, bundle harvest, and separate verification costs;
  v0 intentionally does not optimize these away.
- Frozen unresolved capsules consume predictable disk until integration, closure,
  or explicit abandonment. Capacity exhaustion may require manual intervention.
- Each supported platform needs a backend that proves equivalent properties;
  Linux evidence cannot be projected onto macOS.

### Neutral

- Machine or disk loss remains an out-of-band durability concern addressable by
  ordinary backup or replication; v0 does not become a distributed archive.
- This is proportionate execution isolation and operational forensics, not a
  claim that Doctrine is a cybersecurity or long-term evidence product.
- Full-history versus flattened canonical results is configurable policy. The
  frozen source remains the rescue payload before closure either way.

## Verification

- Contract tests prove the worker cannot mutate canonical refs, shared Git object
  storage, control-plane state, credentials, or forbidden host paths.
- Hostile-ingestion tests cover missing, malformed, oversized, symlinked, changing,
  and configuration-bearing bundle inputs; Git reads only the parent-owned snapshot
  through a fresh quarantine repository.
- End-to-end tests bind contracted base, interpretation policy, pinned source,
  normalized candidate, verification verdict, journal entry, and admitted commit.
- Crash/replay tests cover interruption before and after every external mutation;
  moved targets report and halt without force or automatic resolution.
- Concurrency tests cover same-base clean composition, true conflict, repeated
  staleness, fix-on-top candidate movement, and fresh-capsule repair.
- Lifecycle tests prove unresolved capsules are never automatically destroyed and
  that cleanup requires closure/incorporation or explicit abandonment.
- Backend conformance is demonstrated independently per platform. The initial gate
  recognizes only the measured Linux/bubblewrap backend.
