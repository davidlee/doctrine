# ADR-021: Unsafe code deny with a two-site budget

## Context

The workspace lint posture was `unsafe_code = "forbid"`. `forbid` is stronger
than `deny` in one specific way: it cannot be excepted at all, by anyone, at any
site — an `#[expect]` or `#[allow]` under a `forbid` is itself an error. That
made the posture self-enforcing and cost nothing while no code needed `unsafe`.

`SL-248` `PHASE-05` needed it at two sites in the capsule backend, and neither
has a safe route:

- **`EX-15`, the child's `RLIMIT_FSIZE`.** The cap must land on the *child*, not
  the parent, and `CommandExt::pre_exec` is the only route. The closure runs
  between `fork` and `exec`, where only async-signal-safe work is permitted; the
  closure performs one allocation-free `setrlimit` syscall, which is what that
  contract allows. Setting the limit on the parent and restoring it is the safe
  alternative, and it caps the trusted side for the window — a different and
  worse posture, and one `EX-15` does not describe.
- **`EX-16`, the `/proc/self/fd` sweep.** Marking inherited descriptors
  `CLOEXEC` requires `BorrowedFd::borrow_raw` on integers read out of the
  directory. There is no owned-handle route to a descriptor the process did not
  open.

The alternative was to leave invariant 12 and `sec-7` row 10 with no mechanism
behind them, which the design argues against directly.

The flip is repo-wide and is not reversible without finding every site. It
replaces an absolute guarantee with a conditional one, and what makes the
conditional version acceptable is a **test** — and a test can be deleted by
anyone with no governance trace. That asymmetry is why this is an ADR and not a
comment in `Cargo.toml`.

## Decision

We will set `unsafe_code = "deny"` at the workspace level rather than `forbid`,
and hold the exception count to **exactly two sites**, both in
`crates/doctrine-control/src/backend/bubblewrap.rs`.

`unsafe` stays denied by default everywhere. Each exception is an
`#[expect(unsafe_code, reason = …)]` — `expect`, never `allow`, so an exception
that stops being needed is itself a lint. Each exception guards exactly one
`unsafe` block; widening a block under an existing exception is a budget
increase, not a refactor.

**Two is the budget, not a starting point.** A third site is a finding and a
stop, not a judgement call.

## Consequences

### Positive

- The two bounds the capsule backend cannot express safely exist, so `EX-15`'s
  per-file cap and `EX-16`'s descriptor sweep have mechanisms rather than
  intentions.
- The exceptions are explicit, reviewable and **countable**. Under `forbid` the
  only options were "no `unsafe` anywhere" or "abandon the posture"; `deny` with
  a budget is the position that survives contact with a syscall.
- Each site carries a `reason` string naming the criterion it serves and the
  soundness argument for that specific block.

### Negative

- The guarantee is weaker in kind. `forbid` could not be overridden; `deny` can
  be, by anyone willing to write an attribute.
- The ceiling now depends on a test remaining in the tree. Deleting
  `the_unsafe_budget_is_exactly_two_sites` silently removes the ceiling — this
  ADR is the governance trace that deletion would otherwise not leave.

### Neutral

- No lockfile movement: the crates involved were already present and feature
  selections are not recorded there.

## Verification

`the_unsafe_budget_is_exactly_two_sites` in `bubblewrap.rs` asserts three
things against the file's own whitespace-normalised source:

1. exactly two `#[expect(unsafe_code` occurrences;
2. exactly two `unsafe {` blocks — so an exception widened to cover more code
   keeps the count at two while widening the budget, and is caught;
3. no `#[allow(unsafe_code` anywhere — `expect` only.

Both needles are composed at run time so the test's own source does not count
itself, and normalisation means an attribute `rustfmt` has broken across lines
counts the same as one on a single line. A count sensitive to formatting would
under-count a third site, which is the one direction this check must not fail
in.
