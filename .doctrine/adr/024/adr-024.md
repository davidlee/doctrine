# ADR-024: Shipped-corpus grounding: any address a client can resolve, never a repo-private id or path

## Context

Doctrine's product is correct *agent* behaviour in **client** repos. Its largest
client-facing surface is the corpus it ships: the published reference docs, the
shipped memory corpus, and the installed skills. All three are materialised into
arbitrary client repos and read there by agents who have no doctrine corpus of
their own.

**Entity ids are per-repo sequential.** A client mints its own `ADR-007`, its own
`SL-233`, counting from its own installation. So a shipped asset that cites
`ADR-007` does not *dangle* — `doctrine adr show ADR-007` returns a different,
unrelated record, with no error and no signal that the citation was never about
it. A broken link announces itself; this silently substitutes one claim for
another, in guidance an agent is being asked to act on. The same holds for a
repo-private source or spec path: it is unreachable, and it advertises a tree the
reader does not have.

**The rule existed twice, in halves, and reached neither the whole corpus nor its
worst case.** `DEC-127` generalised "no shipped asset may cite a repo-private
artefact" for the asset it was deciding, and is the immediate precedent here. Two
local memories state parts of the rule, each scoped to one sub-corpus: skill
platform-independence (the installed skills) and shipped-master body scrub
(shipped memory *bodies* on promotion). Neither reaches the published reference
docs, and no single rule covered all three.

**A written rule did not hold.** The corpus is enumerated site-by-site in
`ISS-309` (239 citation sites across the three sub-corpora), and the defect
recurred *during* that audit: a concurrent, good-faith edit to a shipped asset
introduced a fresh repo-private citation, with no signal available to its author
that the citation is wrong in a client repo. A defect invisible to the author
writing it is re-introduced by the next author, however well the existing
instances are swept.

This is a corpus-wide invariant binding every future shipped asset. It is not a
one-off edit and not slice-local design, so it belongs at governance altitude —
hence this record, descending from `ADR-005` and `ADR-019`.

## Decision

**We will require every claim in a shipped asset to be grounded on an address a
client can resolve.**

A shipped asset (`install/`, `memory/`, `plugins/`) may ground a claim on any of
these six forms:

1. **Prose that stands without a reference** — the fact is inlined.
2. **A published logical address** — `reference/<name>.md`, resolvable in every
   client through `doctrine library show` (`ADR-019`). A published doc has no
   file on disk in a client, so this is a logical address, not a path.
3. **A shipped memory key** — `[[mem.<key>]]`, where the key is present in the
   shipped corpus.
4. **A skill name** — the shipped skills are invoked by name.
5. **A CLI verb** — `doctrine <verb> …`; the CLI is the source of truth for
   shapes (`ADR-005`).
6. **An in-corpus relative path** — admissible **only** where the target is
   installed next to the citing file, such as a skill linking to its own sibling
   reference. A relative link from a published document reaches nothing.

**A repo-private entity id or a repo-private source/spec path is never
admissible, at any tier.** These six are not a new citation syntax; they are the
resolution seams a client already has.

**Disposition of an existing site.** Classify first, then act:

| class | action |
|---|---|
| a reference-form illustration, a client-structure reference, or fill-in-the-blank scaffolding | **leave** — the referent is the client's own structure, not this repo's contents |
| a one-clause rationale | **inline** the fact, drop the id |
| a durable, corpus-internal referent | **repoint** to a published `reference/<name>.md` |
| reasoning with no shipped home | **publish** a reference doc, then repoint |
| none of the above | **drop** |

The distinction throughout is *citing the client's structure* versus *citing this
repo's contents*. The evidence that a disposition succeeded is that the
**replacement resolves** — never that the old id no longer appears. A zero-hit
search is a claim about the search.

**Delivery.** The rule ships through framework surfaces, not through this record:
a published authoring doc, `reference/shipped-corpus-authoring.md`, states the
rule and the procedure for a client-facing author, and is pointed at from the
boot-tier reference register so it is reachable. This record is the rule's single
governance owner; the authoring doc is its delivery copy, not a second rule.

**Scope fence.** This governs **shipped** assets. It does not govern slice prose,
design docs, specs, reviews, this repository's own governance, or its source and
tests, whose citations are read in-repo and resolve correctly.

## Consequences

### Positive

- A client agent reading any shipped asset finds every citation either resolving
  to an address it can reach or standing alone; the silent-substitution failure
  mode is closed.
- One rule with one owner replaces two sub-corpus-scoped precedents, so a new
  shipped asset has a single reachability obligation to satisfy rather than a
  guess about which partial rule applies.
- A durable predicate now exists for the deferred enforcement gate to encode.

### Negative

- Authoring shipped prose carries a reachability obligation that authoring
  in-repo prose does not: a claim with no published home must be inlined, or its
  home published, before the asset ships.
- Every pre-existing violation is now a defect rather than an interpretation;
  the swept corpus is larger than a reviewer's recall, so the enumeration
  (`ISS-309`) has to be worked rather than sampled.

### Neutral

- **`POL-002` is not revised.** Its prohibitions are mechanism-worded and do not
  literally reach a shipped *citation*. This record supplies that content facet
  as a descendant; restating the rule inside the policy would duplicate it and
  widen a policy whose scope is intentionally mechanism-level. If enforcement
  finds this descendant insufficient, a policy revision is the escalation.
- **`DEC-127` is preserved, not superseded.** It decided that a specific asset
  ships on the published surface, and its generalisation is this record's
  `install/`-scoped precedent.
- The two local memories that restate parts of the rule live in the local memory
  corpus — a different concern from the shipped corpus. Consolidating them is a
  recorded follow-up, not part of this rule.
- The **enforcement gate** is deliberately not decided here: which existing seam
  it rides, and how it settles the duplicate-rule problem, is `QUE-227`'s — the
  follow-up that owns it.

## Verification

- The rule and its disposition procedure are delivered by
  `reference/shipped-corpus-authoring.md`, reachable through
  `doctrine library show` and pointed at from `install/routing-process.md`.
- Each swept site's disposition is recorded, and a repoint is proven by the
  published address resolving — the replacement resolving, never the id's
  absence.
- A client read in a scratch repo (no doctrine corpus) confirms the swept corpus:
  in that repo a repo-private id would resolve to *the client's* record, which is
  why the check runs there and not in this repository, where every citation
  resolves.
