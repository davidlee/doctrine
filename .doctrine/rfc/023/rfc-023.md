# RFC-023: Executable plan gates and adversarial TDD

> Status: **open** — problem statement and candidate directions only. Asserts no
> canon, proposes no shape. Raised from the SL-233 plan-hardening pass; the
> second half (baton-passed authorship) is unexplored and deliberately left as a
> question.

## Context

A plan's exit and verification criteria are the only thing standing between an
implementer and a phase that closes green while delivering nothing. Today almost
all of that load is carried by **prose an agent attests to**. The exceptions —
`slice conformance`, `check plan`, `verify-vt` — check narrow, mostly structural
properties.

The problem became concrete while hardening the SL-233 plan against an
implementer assumed to be lazy, literal-minded, and willing to make a gate green
without making the code right. Two findings drove this RFC.

**`verify-vt` proves text presence, not behaviour.** `src/vtgate.rs::check_vt`
never runs a test. It checks that a slice-modified file contains each `keyword`
as a raw substring — over unstripped source, so a comment satisfies it — and that
each `patterns` regex matches at least one line. Every VT row in a nine-phase
plan was therefore satisfiable by a comment. The repair was to hand-build four
scaffolds *around* the weakness: line-anchored declaration patterns, ~60
enumerated test-function names, a per-phase negative control, and a per-phase
escape sweep for `#[ignore]` / `todo!()` / `assert!(true)`. All of that is
compensation for a gate that stops one step short of running anything.

**Undeclared paths stall a phase at close, and the worker cannot fix it.** Ten
paths were found that phases must edit with no `design-target` selector — the
projected `.doctrine/routing-process.md`, `src/state.rs` (where a private
`STATE_SLICE_DIR` lives and STD-001 forbids a second literal), the help/boot
goldens that shift when a command family is added, and others. Each would have
landed work that `slice conformance` refuses at close, with the repair
unavailable to the actor who hit it: selectors are authored `.doctrine/` state
and dispatch workers cannot write it. They were found by walking each phase's
predicted edit set against head, by hand.

A third finding is about the plan rather than the gate: six scope objectives had
**no owning phase at all**, found by grepping scope sections against `plan.toml`
manually — twice, because the first sweep covered one section only.

The through-line: in each case the platform already holds the mechanism and
applies it at the wrong time, to the wrong target, or one step short of
execution.

## Discussion

### The thesis

**Verification should be executed, not attested.** A criterion an agent can
satisfy by asserting it has been satisfied is not a gate; it is a suggestion with
an id. The unifying question this RFC asks is how much of a plan's criteria set
can be made mechanical without violating POL-002 (no host-project conventions in
the engine) — and what to do about the remainder, which is irreducibly semantic.

`doctrine check` already demonstrates the POL-002-clean pattern: a
project-declared command, proxied by cadence, with the engine knowing only the
cadence. Several directions below are that pattern pointed at new targets.

### Direction A — trace design intent to plan criteria

`doctrine coverage` already computes "which requirement is verified by what". The
same machinery pointed at a slice's linked decisions would answer "which DEC /
QUE / ASM is claimed by no exit criterion". A `satisfies = ["DEC-058"]` edge on a
criterion plus an unclaimed report turns the manual scope-sweep into a line of
output. Failure mode today is silent: a plan omitting an objective looks exactly
like a plan covering it.

### Direction B — declare the edit set, check it at plan time

This is **RFC-004's accretion model pushed one layer finer**. RFC-004 has the
designer stamping `design-target` selectors and the auditor reading the
declared-vs-actual differential at the end. The gap this RFC observes is that
nothing checks the *plan's* intent against the declared set at authoring time —
the differential is computed at close, which is the one moment the responsible
actor can no longer act on it.

A `touches = [...]` list on `[[phase]]`, cross-checked by `check plan` against
the selector list, moves the stall from close-time to authoring-time. A second
leg in `worker_commit` — refuse a diff containing an undeclared path — moves the
residue from close-time to commit-time. Both are the same conformance
computation, run earlier.

Open: whether `touches` is a third RFC-004 layer (L1.5, "intended by phase"),
or whether phase-scoped intent belongs in the selector list itself with a
`PHASE-NN` provenance stamp, which RFC-004's primitive already carries.

### Direction C — a VT mode that runs the test

The largest single change. A declared per-test runner (the `check` proxy pattern:
`test-one = "<project command template>"`) plus a `test_name` field would let
`verify-vt` execute the named test and require success. Presence becomes passing,
and roughly two-thirds of the SL-233 scaffolding stops being necessary.

Cheaper and adjacent: a `tests = ["name_a", "name_b"]` field. Sixty
hand-written `^\s*fn <name>\(` regexes are the same regex sixty times, and the
current failure message is "pattern matched no line" rather than "test `name_b`
is missing".

Open: whether running a single test is the right granularity, given that a
per-test invocation is language-specific and some ecosystems have no addressable
single-test form. A weaker but universal variant is a declared command per VT row
(see Direction E) with the test-name form as sugar over it.

### Direction D — a vacuity verdict

The sharpest cheap check available. `vtgate` already emits `Unattributable` when
the mandated file was not modified by the slice. One level deeper is the real
question: **would this mandate have passed at the branch point?** If yes, it
proves nothing about the phase's work.

Two vacuous anchors were caught by hand in SL-233 (`run_design` and
`claim_fresh_id` both already exist at head) and only because someone was
looking. Evaluating the same mandate against the base tree is the same code
against a different tree, and the verdict name already has siblings.

### Direction E — executable VA rows

Roughly half the SL-233 hardening effort was expressing shell commands in prose,
because there is no field for a command: *"RUN: `rg -n '#\[ignore\]' …` returns
nothing"*. A `command` + `expect_exit` on a VA row, proxied like `check`, turns
twelve phases of hand-execution into one `slice verify-va` run. VA would stop
meaning "an agent asserts" and start meaning "an agent ran something that could
have failed".

This subsumes much of Direction C and is more general, at the cost of being less
declarative.

### Direction F — give the negative control a durable home

The one device that catches an assertion-free test is *"this test was observed
red before it was made green"*. In SL-233 that evidence lives in the phase sheet
— gitignored runtime state, erased by `rm -rf`, gone before audit. So the
strongest check in the plan currently rests on agent honesty and evaporates.

Red-then-green is a commit, so the evidence exists; it simply is not addressable.
A stamp — "test T observed red at commit C, output O" — keyed to the phase, plus
an audit check that every VT-named test carries one, closes the loop mechanically.

### Direction G — `check plan` lints

Cheap, all done by hand in SL-233. Compile every regex at authoring time (an
invalid one is a `Fail` discovered at conclude, hours later). Flag a pattern
matching nothing anywhere in the repo — can-never-match is worse than no pattern,
and every pattern shape in SL-233 had to be positive-controlled against existing
code before being written in. Flag a keyword whose only occurrences in the target
file are inside comments.

### Direction H — schema hygiene

Two small ones surfaced by splitting phases. **Criterion supersession**: ids are
immutable, so a reassigned criterion becomes a prose tombstone; a `superseded_by`
field would let `slice show` dim it rather than read it as live. **Explicit phase
order**: after appending split phases, execution order is array order while ids
are non-monotonic, and that fact survives only in a TOML comment. `src/plan.rs`
array-order is load-bearing and undiscoverable.

### The irreducible remainder — and the second question

Directions A–H mechanise structure. They cannot reach the thing that actually
decides whether a phase delivered: **is the assertion meaningful?** SL-233 needed
per-phase "anti-theatre" criteria aimed at each phase's specific way of being
faked — a bounds test whose fixture never reaches the bound; five distinct
refusals collapsing into one `is_err()`; a shim-equivalence test comparing exit
codes instead of bytes; a lock-gate test that omits three components and proves
nothing about which one the gate read; a core-process test with a hardcoded
command list wearing a parser's name. Each was hand-written against that phase's
particular temptation. No lint finds these.

The structural insight is that **all of them are only possible because one actor
writes both the test and the code it tests.** A test authored to fit an
implementation will fit it. That suggests the remainder is not a tooling problem
but an *orchestration* problem, which is the second half of this RFC and the part
that is genuinely unexplored:

**Adversarial TDD — baton-passed authorship.** If the test author and the
implementer are different agents, and the implementer cannot edit the test, the
"write a test that passes" degenerate strategy is unavailable. A sketch of the
loop, offered as a starting point rather than a proposal:

1. The coordinator hands agent **T** one exit criterion and the surrounding
   contract. T authors a failing test. T never sees an implementation.
2. The coordinator verifies the test is **red for the right reason** — the
   negative control of Direction F, now produced by construction rather than by
   attestation, and produced by an actor with no incentive to fake it.
3. The baton passes to agent **I**, which may edit production code but not the
   test file. I makes it green.
4. The coordinator verifies green, and — the interesting step — may hand the
   result *back* to T to attack: does the implementation satisfy the criterion,
   or only the test? A finding here is a new test, not a rewrite of the old one.
5. Refactor is a third posture, with both prior tests as the harness.

Questions this raises, none answered here:

- **Q1 — Is the write-fence enforceable?** The `worker_commit` gate can reject a
  diff touching the test file, so the mechanism plausibly exists on the claude
  arm. What is the equivalent on the subprocess arm, where the orchestrator
  imports a working-tree diff?
- **Q2 — What does T see?** Too little context and the test is wrong; enough
  context to write a good test may be enough to anticipate the implementation.
  The interesting question is whether T should see the *design* but never the
  *code*.
- **Q3 — Cost.** This is at least three agent turns per criterion, against one
  today. SL-233 carries ~60 named tests. Is this reserved for criteria above some
  risk threshold — and if so, which axis chooses (the `risk` facet? blast radius?
  the phases carrying design gates?).
- **Q4 — Who arbitrates a genuine disagreement** between T and I about whether
  the criterion is even satisfiable as written? Today an implementer who finds a
  criterion wrong routes to `/consult`. A two-agent loop needs the same escape
  without letting either agent use it to win.
- **Q5 — Does this collapse into the review ledger?** T attacking I's
  implementation in step 4 is adversarial review with a different payload. If the
  RV kind already models turn-based adversarial exchange with findings and
  dispositions, is baton-passed TDD a *new* mechanism or a second consumer of an
  existing one? This is the question most likely to shrink the work.
- **Q6 — Does the same split apply to the gate author?** SL-233's gates were
  hardened by an agent that did not write the plan. That was ad hoc. Whether
  plan-authoring and gate-authoring should be routinely separated is the same
  idea one level up.

## Outcome

Open. Nothing is decided and no shape is proposed.

The two halves are recorded together because they are the same problem at
different altitudes: Directions A–H make the *structure* of a criterion
executable, and adversarial TDD is the candidate answer for the *semantics*,
which no lint reaches. Splitting them would lose the reason either is needed.

Likely next steps, when this is picked up: A, D and G are cheap and independent
enough to be worth doing regardless of where the rest lands — each is an existing
mechanism applied at a different time or target. B needs reconciling against
RFC-004's primitive before it is worth designing separately. C and E overlap and
should be decided together. The adversarial-TDD half needs Q5 answered first,
because a positive answer makes most of the rest a consumer of existing review
machinery rather than new construction.
