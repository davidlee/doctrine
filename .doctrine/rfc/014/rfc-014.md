# RFC-014: Multi-harness fleet: declaration, routing, sandbox backend

## Context

Doctrine's dispatch is nominally harness-agnostic (ADR-011: binary owns
fork+mark+provision; spawn is a per-harness concession) but the multi-harness
story is unfinished in three concrete places:

1. **Unshipped spawn mechanism.** The codex/pi subprocess arm's actual spawn
   lives in `./scripts/pi-spawn-confined.sh` — project-local shell, *not* seeded
   by `doctrine install`. A client gets the `/dispatch-subprocess` prose skill
   but not the mechanism it invokes. The claude arm's spawn is the in-session
   `Agent` tool (skill prose); the subprocess arm's is orphaned shell.

2. **No fleet declaration or situational routing.** Nothing enumerates the
   harnesses a project actually has, nor maps *situation → (harness, model)*. The
   `/dispatch` router selects the arm off a single bool
   (`[dispatch] claude-force-subprocess-dispatch`) plus harness↔env agreement.
   That does not scale to a project with codex, pi, dirge, opencode, claude live
   at once — nor to a codex-*primary* client, where there is no in-session `Agent`
   backend at all and every worker is `subprocess`. The hymns corpus carries prose *per harness/model-trait* but is
   explicitly **not a registry** (hymns README: model is a trait vocabulary, no
   central registry) — so it is the wrong home for a live-process fleet.

3. **Sandbox backend is host-detected, not chosen — and can be absent.** bwrap
   (linux) vs seatbelt (macOS) is a capability, not user config, but bwrap can be
   missing on a stripped linux host. A hard-coded backend is fail-closed there.

None of these has an answer today, so "multi-harness" is not yet solved. This RFC
deliberates the shape of that answer before it becomes a slice.

## Discussion

### The load-bearing insight: backends are fixed at 2, bindings grow freely

The fleet does **not** grow a backend per harness. There are exactly **two spawn
backends**, and every harness binds to one:

| backend      | who owns the worker process         | confinement                 |
|--------------|-------------------------------------|-----------------------------|
| `agent`      | in-session (claude `Agent` tool)    | worktree jail, no subprocess |
| `subprocess` | orchestrator `exec`s a CLI child    | sandbox-wrapped (bwrap/seatbelt) + worktree jail |

Bindings observed in this project:

- **claude** → `agent`
- **codex** → `subprocess` (first-class when primary — see role note below)
- **pi** → `subprocess`
- **dirge** → `subprocess` (dirge ≈ pi — near drop-in)
- **opencode** → `subprocess` (confinement shape TBD; worth a spike)
- **flake-on-tap harnesses** → new *bindings*, not new *backends*

**codex plays two orthogonal roles; do not conflate them.** A harness can be
*both*:

1. a **primary harness** — the codex CLI is the top-level agent, binds `subprocess`,
   spawns its own workers. **First-class**: many clients run codex (not claude) as
   primary, so the fleet must bind it like any other subprocess harness.
2. an **MCP consult peer** — codex reached *inside* another harness (this project's
   setup: codex under claude via its MCP + plugin integration, for adversarial
   review). This is an orthogonal axis (an MCP tool), *not* a spawn target.

The earlier framing "codex is excluded from the fleet" was wrong: it is excluded
from *this project's active* fleet only because the operator drives it via MCP
(role 2) rather than as primary (role 1) — a subscription-cost choice, not a
capability limit. The role-2 usage here is simply less fleshed out. The design
must keep role 1 first-class and role 2 orthogonal; the *same* harness id can
appear as a fleet binding *and* as an MCP peer without contradiction.

Consequence: the design surface is small. Two backends means two spawn
mechanisms to ship and test; adding dirge/opencode is a config row plus prose,
not new machinery.

### Config home: `doctrine.toml`, not hymns

Routing and fleet live with **dispatch**, in `doctrine.toml` — the same file that
already carries `[dispatch]`, `[verification]`, `[reservation]`. Hymns stay
orthogonal: **hymns compose *prose*; the fleet composes *processes*.** Sketch:

```toml
[dispatch.fleet.claude]
backend = "agent"
model   = "claude-opus-4-8"     # opaque spawn arg, NOT a semantic key
sandbox = "none"                # agent backend has no subprocess to wrap

[dispatch.fleet.pi]
backend = "subprocess"
model   = "…"
sandbox = "auto"                # auto | bwrap | seatbelt | none | require

[dispatch.fleet.dirge]
backend = "subprocess"
sandbox = "auto"

[dispatch.routing]
default   = "claude"
# situation → harness (situations TBD: solo/parallel/phase-class/cost-tier?)
parallel  = "pi"
```

### The ADR-011 tension — must be resolved explicitly, not silently

ADR-011 **deliberately rejected a central model registry**: model identity is a
leaky proxy; the honest axes are traits, authored as an open vocabulary in the
hymns model band; keys are opaque, no privileged semantics. A `[dispatch.fleet]`
block whose entries name models *looks like that registry returning*.

Resolution to assert (candidate ADR-011 **delta**, not amend): the fleet names
**backends and spawn arguments**, not model semantics. `model = "…"` is the
literal token handed to a CLI at spawn — the same opaqueness ADR-011 already
grants. Trait-keyed prose composition stays entirely in hymns. Fleet ≠ registry
because it carries no meaning the engine reads; it is a process-launch table. A
reviewer will read a reversal here unless the delta says this outright.

### Sandbox as a probed third field, not a fourth surface

`sandbox` rides the `subprocess` backend as a per-binding field:

- `auto` (default) — probe host (a `doctrine doctor`-class capability check) →
  bwrap on linux, seatbelt on macOS, refuse-with-diagnostic if neither present.
- `bwrap` / `seatbelt` — pin explicitly.
- `none` — no sandbox (agent backend, or a trusted host).
- `require` — like `auto` but **refuse to spawn** if no backend is found
  (fail-closed for security-sensitive fleets, vs `auto`'s degrade).

The probe is the honest primitive; config only overrides or hardens it.

### Shipping the subprocess spawn (problem 1)

Two options, leaning toward the second:

- **(a) seed the script.** `doctrine install` writes a `pi-spawn`-class asset to
  disk; the skill invokes it. Simple, but re-introduces prose-drives-shell.
- **(b) template + router.** `doctrine.toml` declares a per-binding spawn command
  template; the `/dispatch` router fills and `exec`s it. Keeps the *exec* out of
  the binary (SL-056 Charge XIII — no subprocess seam may be a *required*
  framework element) while making the mechanism declared, diffable, and
  overridable. The sandbox wrapper composes onto the template.

(b) matches ADR-011's spirit (mechanism declared, not orphaned shell) without
making a subprocess a hard framework dependency.

## Outcome

**Open.** Direction converged; details for the descending slice:

- **OQ-1** — Situation vocabulary for `[dispatch.routing]`: what are the
  situations? (solo vs parallel; phase file-disjointness; cost/latency tier;
  explicit per-slice override?) Overlaps RFC-013's selection algebra — decide
  whether routing reuses that machinery or stays a flat table.
- **OQ-2** — Spawn shipping: template-in-config (b) vs seeded-script (a).
- **OQ-3** — opencode confinement shape — spike before committing a binding.
- **OQ-4** — Migration of `claude-force-subprocess-dispatch` (current single
  bool) into the fleet/routing model without breaking existing dispatch.
- **OQ-5** — ADR-011 delta wording: fleet-is-not-a-registry, authored where?
- **OQ-6** — The MCP consult-peer axis (codex-under-claude, role 2): does it get a
  config surface in this RFC (e.g. `[dispatch.peers]`) or stay wholly out of
  scope? It is orthogonal to spawn, but a project declaring "codex is my reviewer"
  is the same *fleet* intent from the operator's view.
- **OQ-7** — Codex-primary parity: verify no design step assumes an `agent`
  backend exists (a codex-primary client has none). The router must degrade to
  all-`subprocess` cleanly.
