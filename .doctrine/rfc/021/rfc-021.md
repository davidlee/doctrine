# RFC-021: Dynamic behaviours and minimal projection

## Context

Doctrine currently conflates three concerns under `install/`: assets the binary
consumes internally, explanatory material useful to humans and agents, and
project-owned files that genuinely belong in a client repository.

`src/install.rs` embeds the whole tree and the installer projects nearly every
embedded file into `.doctrine/`. Embedding and installation are therefore the
same policy by accident. Templates, reference documents, hymns, agent
definitions, and integrations all enlarge and obscure the client-facing surface
whether or not a user can meaningfully service them.

Doctrine's skills have a related ownership problem. Harnesses preload skill
names and descriptions into privileged context and load bodies on activation.
That helps implicit activation, but the static catalog duplicates Doctrine's
lifecycle vocabulary in every harness and makes updates depend on refreshing
installed files. Much of the machinery already requires the Doctrine binary.

SPEC-023 offers another boundary: the binary can select and compose Markdown
guidance by harness, model traits, role, stage, and project. A small static
activation kernel could load Doctrine-owned behaviours dynamically while
leaving only a few timeless harness adapters.

That direction is attractive but not free. Tool calls add latency and transcript
tokens, and stochastic tool-call ids can invalidate prompt-cache suffixes.
Moving policy out of privileged skill descriptions may also reduce implicit
activation reliability, especially for capable but less adherent models. The
question is whether Doctrine can own a smaller, clearer project surface and a
more dynamic behaviour runtime without an unacceptable correctness or context-
economy cost.

## Discussion

### Semantic ownership and explicit projection

The converged information-architecture principle is:

> A client installation contains only user-serviceable project content,
> necessary harness integration, and runtime roots. Binary-private defaults,
> scaffolds, algorithms, and references remain binary-owned and are exposed
> intentionally through commands.

Physical roots should follow semantic ownership. A candidate shape is:

```text
templates/      artifact and configuration templates
hymns/          composable guidance and exposed fragments
behaviours/     sealed definitions and registry metadata
reference/      curated explanatory material
integrations/   scripts, workflows, modules, harness assets
install/        base projection policy and its projected files
memory/         shipped memory corpus
```

Exact names are downstream design work. The invariant is that `install/` ceases
to own material merely because the binary embeds it.

Embedding and publication are also distinct. A library manifest declares which
assets are public, with stable logical address, source, content kind, title or
summary, licence, and customization status. An embedded file does not become
public API accidentally.

### Curated library and federated search

`doctrine library` is the read-only API for published embedded material:

```text
doctrine library list [path]
doctrine library tree [path]
doctrine library show <logical-path>
```

Logical paths are stable POSIX-like addresses independent of embed layout.
`show` emits clean bytes to stdout for piping. Semantic materialization remains
with the owning feature; the library does not install or overwrite project
files.

Initial collections include every entity and configuration template, every
overridable hymn, curated references, and selected scripts, workflows, Just
modules, and similar reusable sources.

Publication and licence are separate metadata. MIT covers material people
reasonably need to copy or adapt for supported customization: authoring schemas,
examples, editable starters, selectors, and declared seams. Shipped process
bodies, internal registry definitions, engine contracts, orchestration
knowledge, and other internals remain GPL even when represented as prose.

Bare `doctrine search <query>` searches every discoverable corpus. Known results
remain retrievable through native commands such as `memory show`, `rfc show`,
and `library show`. Unified search exposes only common discovery arguments;
specialized query languages remain on native searches.

Human results are grouped by corpus rather than globally interleaved. Provider
scores are not necessarily comparable, and memory results retain trust,
severity, and staleness. Machine output has a common outer envelope with typed
result groups.

### Minimal project installation

The complete harness-independent base installation is:

```text
.doctrine/
├── .gitignore
├── boot-project.md
└── doctrine.toml
```

- `.gitignore` owns disposable paths beneath `.doctrine/`; installation stops
  modifying the repository root ignore file.
- `doctrine.toml` is the fully commented example written as the real config
  when absent. It is an important onboarding cue despite built-in defaults.
- `boot-project.md` combines concise orientation, pointers, and cross-harness
  standing guidance that might otherwise be duplicated in harness files.

`boot-project.md` replaces both `.doctrine/governance.md` and the seeded Project
Orientation memory. It is inlined after the shipped Doctrine Overview and links
to an embedded library guide. Installation names it as the primary orientation
step; `doctor` may report an unchanged placeholder as advisory. Behaviours may
propose improvements, but an agent requires explicit user acceptance to edit
this high-leverage file.

Entity roots are created on first use. Hymns appear on disk only when a
customization is materialized. Templates, docs, workflows, scripts, `mod.just`,
agent definitions, and integrations are not base projections. A selected
harness may install the specific adapter it requires.

Existing-install migration is explicitly out of scope: there is no meaningful
external user base, and cleanup machinery would add code without present value.

### Doctrine-owned behaviours

`behaviour` names a registry-owned unit. A behaviour is either a **process**
(design, audit, close) or a composable **posture** (pair, walkthrough). A harness
skill is a privileged adapter that activates Doctrine behaviours.

The target static catalog begins with `/route` only. Other permanent activation
stubs are admitted only if evaluation shows that a behaviour needs a privileged
hook. Adapters should be timeless and carry an explicit stub-to-binary protocol
version as insurance. If the compatible binary or registry is unavailable,
Doctrine fails clearly; there is no stale prose fallback or degraded imitation.

The binary owns canonical identity and markers, behaviour kind, compatibility,
required inputs, lifecycle preconditions and transitions, selection,
composition, validation, and executable enforcement. Hymns own agent-facing
prose, model/harness/role adaptations, project policy, and declared refinements.
Hymns are selected content, not a programming language: conditional judgment
happens in the agent or between smaller processes.

The existing cascade should be reused and generalized rather than duplicated.
Core definitions are sealed and contain every instruction required to perform
the process correctly. Optional examples and references may remain pull-based;
required steps must not hide behind an optional lookup.

Projects cannot replace a whole core behaviour. The registry declares named
default fragments users may customize, such as commit policy, review priorities,
or candidate promotion. Each exposed fragment has stable identity, purpose,
default hymn, applicable behaviour, licence, and eventually any insertion seam.
Project-defined Doctrine behaviours are deferred; unrelated harness-native
skills remain available.

The cascade's coarse ordering may not be sufficient when a project fragment
needs locality inside a process. Preserve an extension requirement for
framework-owned semantic insertion seams, but initially rely on ordinary
project-band guidance until evidence shows anchors are needed. Line numbers,
arbitrary priorities, and a general placeholder language are not intended.

### Explicit and implicit activation

Registered `#name` markers are cache-stable, harness-neutral signals of explicit
intent, for example `#design` and `#pair`. They are natural-language signifiers,
not a workflow expression grammar. Processes can form an evident sequence and
postures can compose:

```text
#audit #reconcile #close SL-123

Let's #walkthrough this code, #pair on refactoring, then #reconcile and #close.
```

Doctrine need not formally parse marginal combinations. An unclear pile of
markers is an ambiguous request and should be clarified rather than assigned
invented precedence rules.

Explicit invocation takes precedence over inferred next action, subject to
compatibility validation. It does not disable implicit activation. The binary
handles deterministic facts—markers, entity state, compatibility, and declared
continuation—then supplies contextual activation policy and candidates. The
agent interprets natural language where classification remains semantic and
submits its choice for validation.

Routing semantics preserved by this model include:

- a handover is context input to the ordinary router, not a separate workflow;
- a bare entity id means inspect, summarize, and recommend without mutation;
- `continue <ENTITY-ID>` authorizes the next valid lifecycle process until a
  decision, refusal, or completion boundary;
- an explicitly named process overrides inference or produces a clear
  incompatibility explanation;
- shaping an amorphous idea, brief, or fault is a first-class non-committing
  exploration route before artifact choice.

Doctrine remains default-on. An agent must never infer that work is outside
routing. Only the exact, request-scoped user token `BYPASS-DOCTRINE` suspends
Doctrine. Bypassed turns end with `[BYPASS]: short description` and do not nag
the user to re-enter routing.

### Resolution and context economy

MCP exposes one generic behaviour-resolution tool rather than one tool per
behaviour; the CLI mirrors it through a `doctrine behaviour resolve`-class
surface. Separate tools would recreate the resident-description tax.

One resolution returns the active process composed with all applicable postures
and contextual hymns. A process chain resolves incrementally: audit guidance is
loaded for audit, then reconcile guidance when that transition is reached.

Two payloads must not be conflated:

- the **behaviour definition** is versioned static guidance valid for the
  session;
- the **resolution envelope** contains point-in-time selection and state facts
  and is refreshed at declared gates.

The resolver is initially session-stateless. Doctrine does not remember what an
agent has viewed. The caller requests full guidance on first activation or after
compaction and may request only dynamic state later. Returned guidance names the
refresh path so forgotten details are recoverable.

Session-aware elision, speculative memory matching, and automatic reference
inlining are future optimizations. Static references may be inlined where
clearly worthwhile; dynamic data must not masquerade as durable guidance.

### Authority and trust

The static kernel grants resolved guidance the same behavioural authority as a
trusted harness skill or plugin. Otherwise a model may treat tool output as
mere reference data and lose the privilege that made skills reliable.

Within Doctrine's domain, authority is:

```text
direct user instruction
  > project-local authoritative truth
  > Doctrine framework rules
  > agent judgment
  > untrusted, stale, conflicting, or superseded artifacts
```

Normal guidance does not pay a repeated authority-envelope tax: unmarked
behaviour content is Doctrine framework instruction. A declared project
override is visibly marked and supersedes its corresponding default without
escalation; the user has already expressed the relevant intent as clearly as
the supported system permits. Memories lack instructional authority. Any
inlined memory or untrusted artifact carries explicit provenance and trust
framing.

An unexpected contradiction between independent authoritative sources is
different from a declared override and may be fresh drift. Conflicts between
normative truth and empirical evidence or a lower-authority artifact sometimes
admit a small factual correction without interruption, but incorrect autonomy
is costlier than unnecessary escalation and different models warrant different
latitude.

### Contextual escalation as an exemplar

The existing `/consult` skill describes an action rather than a magical
process: when the user is present, raising the issue directly is consulting.
Agents nevertheless adhere poorly to judgment-triggered instructions compared
with immediate commands or tool-local prerequisites.

A future escalation resolver is therefore the strongest exemplar of dynamic,
contextual policy. The agent initiates it when a qualifying conflict appears
and supplies active workflow, governing artifact, process and posture,
conflicting evidence, authority relationship, autonomy directive, interruption
cost, factual versus architectural significance, reversibility, scope, and the
agent's recommended resolution.

Model-sensitive policy returns one of two operational outcomes:

- `proceed`, with bounded authority and instructions to record or report the
  correction; or
- `escalate`, with a contextually appropriate question to put directly to the
  user.

The trigger needs reinforcement in the static kernel, relevant behaviour
runlists, and tool or workflow gates. A complete escalation decision model—and
general FSM execution for dispatch, execute, audit, reconcile, and close—is
downstream work. This RFC preserves the seam rather than defining those engines.

### Evaluation before catalog collapse

The architecture is directional, but removing static stubs is evidence-gated.
A reasonable experiment compares:

1. the current static skill catalog;
2. a route-only static kernel with dynamic behaviour resolution;
3. route plus only additional activation stubs shown necessary by prior results.

Variant 3 is conditional, not assumed implementation.

The fixed corpus covers explicit and implicit activation, bare entity
orientation, continuation, handovers, amorphous shaping and diagnosis, process
chains, posture composition, exact bypass, and newcomer prompts. The same A/B
conditions run in representative deployments:

- Claude Code with Sonnet;
- Pi with DeepSeek, as a capable but more YOLO-prone adherence benchmark.

Additional open models are diagnostic follow-ups if needed. Codex is not
required merely to complete a factorial matrix; the control comes from Doctrine
variants rather than pretending to isolate harness and model effects.

Record activation choice, outcome correctness, tool boundaries, transcript
tokens, cache behaviour, latency, install footprint, and agent confusion. There
is no fake scalar acceptance formula: the operator makes a holistic judgment.
A substantial regression on any dimension is unlikely to be accepted without
overwhelming compensating value. The experiment may also support a public
technical write-up on progressive disclosure and dynamic agent guidance.

### Explicit non-goals

This RFC does not design or implement:

- cleanup or migration of existing installations;
- a formal `#` workflow grammar;
- project-defined Doctrine behaviours;
- internal conditional evaluation in hymns;
- semantic insertion anchors in the first implementation;
- server-side session/view tracking or automatic context elision;
- speculative reference or memory enrichment;
- a general FSM workflow engine;
- the complete escalation policy model;
- consolidation of handover, `/next`, handover artifacts, and thread memories.

## Outcome

**Open, with directional consensus.** The proposed destination is:

- semantic embedded corpora and an explicit three-file base projection;
- a curated `library` read surface plus federated, grouped `search`;
- a tiny privileged activation kernel and Doctrine-owned behaviour registry;
- dynamic, authoritative, stateless hymn composition with declared project
  override fragments;
- empirical gating before the static skill catalog is collapsed.

This RFC should descend into multiple durable contracts rather than one slice.
Likely specification boundaries are:

1. install projection and library/search discovery;
2. behaviour registry, activation, resolution, authority, and protocol;
3. hymn-cascade extensions and contextual escalation if those concerns prove
   large enough for independent contracts.

Those specs may emit experimental and implementation slices. Slice design,
observed implementation truth, evaluation, audit, and reconciliation should
drive later revisions instead of preserving speculation.

Open mechanisms include exact root names and manifest schema, behaviour CLI/MCP
shapes, dynamic-envelope inputs, fragment materialization, whether semantic
insertion seams are needed, and the eventual escalation decision model.
