### Problem statement

Doctrine’s current dispatch machinery has accumulated complexity across several interacting concerns:

* parallel workers require independent mutable workspaces;
* implementation must be tightly confined and auditable;
* Claude Code subagents expose uneven and sometimes opaque lifecycle, identity, hook, worktree, and environment semantics;
* Git state must remain crash-safe, exact, reviewable, and resistant to accidental or hostile mutation;
* the workflow should preserve token efficiency and bounded autonomy without transferring excessive authority to agents;
* deterministic tooling has progressively absorbed workflow duties, but the remaining orchestration boundary is still broad and harness-specific.

Worktrees solve workspace independence efficiently, but they also couple workers through a shared Git repository and object database. That coupling makes workspace identity, worker privilege, base selection, ref ownership, marker semantics, hook behaviour, and integration recovery part of the same trust model.

The investigation therefore begins from a broader thesis:

> A worker should not be a privileged participant in Doctrine’s canonical Git topology. It should operate inside a disposable execution environment, while trusted control-plane machinery provisions work, observes results, verifies conformance, and performs canonical mutations through tightly constrained channels.

A raw clone per work thread is one possible implementation. The simplifying move is not the clone alone; it is the authority boundary around the execution capsule.

## Discussion

This is a discussion artifact, not a decision record or governance; it has no binding authority.

### Design priorities

Optimisation order:

1. correctness;
2. reduction of human exertion;
3. token efficiency;
4. wall-clock efficiency.

The initial design should prefer obvious correctness over cache reuse or low provisioning latency. Fast-but-ambiguous state is an unacceptable foundation. Once the model is correct, provisioning and execution can be accelerated without changing its trust semantics.

### Invariants to preserve

The migration should preserve the product and safety properties, not necessarily the current machinery.

#### Parallel execution

Multiple phases may execute concurrently from an explicit accepted base without observing or corrupting another phase’s mutable workspace.

The phase is the unit of parallelism.

#### Bounded authority

A capsule may have broad authority over its own disposable local environment, but it must not gain general authority over:

* the canonical control-plane repository;
* authored Doctrine state;
* integration refs;
* remote Git credentials;
* unrelated host files;
* network services not explicitly granted to the work contract.

Authority should be absent by construction where possible, rather than inferred from fragile process identity.

#### Declared-scope conformance

The existing selector model remains valuable:

* declared and changed;
* declared but unchanged;
* changed but undeclared.

That algebra should be applied before canonical acceptance and retained as audit evidence. Phase-level touch declarations should narrow the slice-level selector set.

#### Auditable evidence

Doctrine must retain enough evidence to reconstruct:

* the contracted base;
* the capsule and phase identity;
* the worker-produced final state;
* worker history and metadata where useful;
* the declared-versus-actual differential;
* verification and audit outcomes;
* the exact normalized candidate;
* the exact admitted object;
* the object ultimately integrated.

#### Crash-safe integration

A crash may leave a transaction incomplete, but not ambiguous. Recovery should mean replay, inspection, or abandonment, never reconstruction from undocumented mutable state.

#### Rigorous verification

Verification should run behavioural criteria against the exact candidate being considered for acceptance. Textual attestation is not sufficient evidence of behaviour.

#### Token efficiency

Agent conversational context may persist across phase transactions. Filesystem authority and mutable project state need not persist with it.

The design should allow a long-running interactive Claude session to orchestrate several phases without repeatedly re-ingesting the whole slice or repository.

### Target authority model

#### Control plane

The control plane owns canonical truth and canonical mutation:

* provisioning;
* work contracts;
* accepted Git state;
* authored Doctrine state;
* result harvesting;
* conformance checks;
* candidate normalization;
* verification and audit records;
* admission;
* CAS-gated integration;
* capsule lifecycle and garbage collection.

#### Capsule orchestrator

Within its capsule, the orchestrator may initially have relatively broad local authority. It may:

* inspect and edit the local checkout;
* spawn subagents;
* run builds and tests;
* manage local commits and temporary branches;
* retain conversational and diagnostic context;
* write nominated coordination, escalation, result, and audit artifacts.

It cannot directly mutate the canonical control-plane repository. Cross-boundary operations occur only through a narrow Doctrine interface or through the control plane inspecting the capsule.

This corresponds to a mediated-orchestrator model now, with an intentional path toward an advisory orchestrator later as Doctrine absorbs more of the workflow state machine.

#### Capsule subagents

In a dispatch-configured Claude session:

* the main session thread is the capsule orchestrator;
* any tool invocation carrying subagent identity is subordinate authority;
* `agent_type` may select a narrower policy, but does not grant orchestration authority;
* unknown subordinate tools or mutation paths should be denied by default;
* Bash or equivalent execution remains inside the capsule confinement boundary;
* control-plane mutation remains unreachable.

The dispatch session is therefore an authority domain. The session configuration selects the domain; subagent metadata selects the subordinate policy inside it.

## Claude configuration direction

A practical transitional step is to launch a new interactive Claude session manually inside a prepared dispatch workspace.

The outer project session may use the Doctrine plugin without dispatch-specific confinement hooks. The dispatch session receives a dedicated configuration containing:

* confinement-appropriate hooks;
* dispatch-specific agents and tool policy;
* Doctrine MCP or binary interfaces appropriate to the capsule;
* role-specific prompts and plugins;
* workspace and base assertions.

The security-bearing configuration should not depend solely on a mutable plugin marketplace installation or on subagent-writable files. Prefer a deterministic launcher and externally protected hook implementation, for example:

```text
doctrine dispatch enter SL-123
  -> provision capsule
  -> validate base and configuration
  -> exec claude --settings <dispatch-settings>
```

Hooks and plugins remain harness integration mechanisms, not the sole hard security boundary. The control-plane separation, missing credentials, sandboxing, and trusted-side acceptance remain the stronger floor.

### Cross-boundary communication

The capsule should not push authoritative state into the control plane.

#### Notification channel

The outbound capsule-to-control-plane channel is a doorbell, not a data channel.

A notification may indicate only:

* result ready;
* checkpoint reached;
* escalation requested;
* user attention required;
* nominated capsule state changed.

The payload should be nil or minimal. The control plane already knows the capsule identity and location, and reads authoritative artifacts or Git state directly.

This can begin as a webhook-like callback, signal, FIFO, socket message, or narrow Doctrine command. Its semantics should remain: “inspect the nominated capsule” rather than “trust this supplied result.”

#### Coordination artifacts

For the initial design, coordination state lives inside the capsule and is harvested by the control plane.

Use a small, disciplined set of machine-readable artifacts, shaped as future protocol messages even before a broker exists:

```text
contract.toml
status.toml
escalation.toml
result.toml
audit/
```

Use atomic replacement. Treat these as explicit state snapshots or append-only evidence, not an informal scratch directory.

This allows a later move to a control-plane ledger or broker without changing the conceptual contract.

### Capsule and phase lifecycle

#### Identity and reuse

Capsules are slice-scoped resources. Phases are transaction boundaries.

* Serial execution may reuse the same capsule across successive phases.
* Parallel execution fans out across additional identical capsules.
* A capsule used for an earlier serial phase may later execute another independent phase in the same slice.
* There are no different species such as “primary capsule” and “phase capsule.”
* Every phase result is harvested at its boundary.
* All capsules are garbage-collected at slice close.

The simplifying assumption is that durable design, coordination, and audit state does not need to cross a phase boundary until the phase has completed. Mid-phase interruption of canonical state is not required.

#### Correct target model

The stronger long-term model distinguishes:

1. a clean, verified provisioning state at an accepted base;
2. disposable phase execution state derived from that provisioning state;
3. complete teardown of phase-local mutable state after harvest.

On Linux this may eventually use overlayfs, btrfs snapshots, reflinks, or another filesystem snapshot mechanism. Similar semantics may be implemented differently on macOS.

#### v0 lifecycle

The initial implementation should use the simplest correct model:

1. create a fresh capsule from the accepted canonical commit;
2. provision files from an explicit manifest;
3. perform a cold baseline build and verification;
4. execute one phase transaction;
5. harvest the result and evidence;
6. accept and normalize the result in the control plane;
7. rebuild a fresh capsule from the new accepted commit for subsequent dependent work;
8. use best-effort teardown only where a capsule is temporarily reused during the v0 transition.

Known gitignored state directories may be deleted during best-effort teardown, but this is not treated as a proof of hermeticity.

### Provisioning and filesystem hygiene

#### Provisioning source

Provisioning must not depend on copying arbitrary mutable state from the control-plane checkout. That is vulnerable to contamination and does not provide a reproducible base.

The provisioning input should be exactly:

```text
accepted Git tree
+ explicit provisioning manifest
+ immutable or independently managed toolchain/runtime inputs
```

The current `.worktreeinclude` mechanism provides a useful conceptual seed: selected non-Git files are named with gitignore-style paths and explicitly copied. It should evolve into a capsule provisioning manifest with clearer ownership and mutability semantics.

#### Hermetic phase boundary

Anything gitignored and not explicitly readonly is a possible mutable-state vector.

The desired reset semantics are:

> After a phase, nothing survives unless it belongs to the accepted Git tree, the provisioning manifest, or nominated harvest and coordination evidence.

Do not attempt to classify project caches as “safe across edits” versus “affected by this phase.” That distinction is likely brittle and language-specific. Preserve only caches that are demonstrably outside the mutable project state, or accept recomputation.

For v0, cold builds are acceptable.

### Accepted result and Git normalization

#### Worker freedom

Inside the capsule, the agent may commit as often as useful. It may use temporary branches, fixups, or checkpoint commits according to local working needs.

The control plane does not treat that commit topology as canonical project history.

#### Normative result

The authoritative phase result is the final accepted tree delta relative to the contracted base.

The control plane:

1. reads the capsule’s base and final Git state;
2. validates ancestry and contracted base;
3. computes the actual changed paths;
4. applies selector and phase touch-set conformance;
5. rejects governance or configuration escapes;
6. runs verification against the exact result;
7. normalizes the accepted result according to project and Doctrine policy;
8. creates the canonical phase commit or candidate object itself.

Doctrine’s current preference for one source-delta commit per phase remains a sensible default. Normalization may later become configurable according to project conventions.

#### Forensic evidence

Do not discard worker history merely because it is not canonical.

Retain, according to policy:

* capsule Git bundle or equivalent object archive;
* worker commit history;
* result manifest;
* tool and model metadata;
* audit findings;
* verification logs;
* declared and actual path sets;
* timestamps and capsule identity;
* relevant transcript or structured reasoning artifacts where permitted.

This preserves forensic and debugging value while keeping canonical integration simple.

### Git boundary

The current Git model contains valuable principles that should survive even if its topology is reduced:

* immutable object identity;
* explicit base pinning;
* exact candidate and admitted OIDs;
* no integration from a drifting live branch tip;
* journal-before-canonical-mutation;
* idempotent replay;
* expected-tip CAS;
* report-and-halt rather than auto-resolve;
* audit before admission.

The capsule should not write shared refs or canonical Git metadata.

The initial ingestion mechanism should be tested empirically, with parent-side fetch into a quarantine namespace as the leading hypothesis. Other candidates include Git bundles, patch series, or final-tree materialization.

Canonical integration should operate on a normalized, control-plane-owned candidate. The capsule’s local refs are evidence, not authority.

### v0 architectural sketch

```text
                         TRUSTED CONTROL PLANE
+------------------------------------------------------------------+
| canonical repository and authored Doctrine state                 |
| accepted base and work-contract registry                         |
| capsule provisioning and lifecycle                               |
| result harvesting, conformance, verification and normalization   |
| candidate/admission evidence                                     |
| CAS-gated integration                                            |
+-------------------------------+----------------------------------+
                                |
                                | provision explicit base + manifest
                                v
                         EXECUTION CAPSULE
+------------------------------------------------------------------+
| fresh local clone                                                |
| dispatch-specific Claude configuration                           |
| capsule orchestrator with broad local authority                  |
| confined subordinate agents                                     |
| no canonical repository authority                               |
| no push credentials                                              |
| local commits, builds, tests and coordination artifacts          |
+-------------------------------+----------------------------------+
                                |
                                | nil/minimal notification
                                v
                         CONTROL-PLANE HARVEST
+------------------------------------------------------------------+
| inspect nominated capsule                                        |
| archive forensic Git/history/metadata                            |
| compute final tree delta                                         |
| enforce selectors and forbidden paths                           |
| verify exact result                                              |
| normalize canonical phase commit                                |
| audit, admit, integrate under CAS                                |
+------------------------------------------------------------------+
```


#### Migration path

#### 1. Define the capsule contract

Introduce a harness-neutral abstraction:

```text
provision(contract)
launch(capsule)
notify(capsule, event)
inspect(capsule)
harvest(capsule)
verify(contract, result)
normalize(result)
gc(capsule)
```

Initially adapt the existing subprocess and worktree implementation where useful, but keep the contract independent of worktrees.

#### 2. Establish dispatch-configured interactive Claude sessions

Prove that a manually initiated session in a prepared workspace reliably receives:

* the intended settings and plugin set;
* the intended main-thread versus subagent policy;
* protected confinement hooks;
* the narrow Doctrine interface;
* no unintended control-plane authority.

This is the highest-value transitional simplification because it may remove much of the current Claude-specific identity and hook choreography without requiring an immediate Git redesign.

#### 3. Add raw-clone capsule provisioning

Provision selected phases from explicit accepted commits into independent clones. Remove remotes or credentials as required. Keep the existing downstream candidate and integration machinery temporarily.

#### 4. Move acceptance to parent-side harvesting

Stop treating worker self-commits or worker-produced patches as canonical. The control plane computes and validates the final result, archives local history, and creates the normalized candidate.

#### 5. Rebuild from canonical accepted state between dependent phases

Use fresh provisioning after each accepted phase. Accept cold builds until correctness and reproducibility are established.

#### 6. Collapse obsolete coordination topology

Once workers no longer participate in the canonical repository, reassess:

* persistent `dispatch/*` refs;
* coordination worktrees;
* worker markers as identity;
* base-by-placement;
* worktree import and landing verbs;
* mandatory per-phase evidence refs;
* candidate repair propagation choreography;
* harness-specific implementation altitudes.

Retain only mechanisms that still protect an invariant in the new model.

#### 7. Optimise provisioning without changing semantics

Investigate:

* overlayfs;
* btrfs or ZFS snapshots;
* reflink copies;
* Git alternates or shared readonly object stores;
* Nix-built immutable runtime layers;
* container or VM backends;
* remote execution.

These should accelerate the already-correct capsule model, not redefine its trust boundary.

## Outcome

### Investigation method

For every current dispatch mechanism, record:

```text
mechanism
property protected
failure prevented
whether the failure still exists with capsules
replacement mechanism
```

This avoids migrating complexity whose only purpose was defending against shared-worktree hazards.

The local investigation should exercise at least:

* subordinate writes to `.doctrine/` or `.claude/`;
* hook failure or removal;
* wrong base;
* rewritten local history;
* multiple or merge commits;
* undeclared paths;
* attempted push or credential access;
* capsule termination mid-phase;
* parent crash during harvest;
* trunk movement before admission;
* parallel disjoint phases;
* parallel conflicting phases;
* tester and implementer ownership violations;
* repaired candidate normalization;
* notification loss or duplication;
* stale coordination artifacts;
* baseline build failure.

Measure:

* trust-bearing lifecycle states;
* mutable refs;
* harness-specific branches;
* hooks with security significance;
* role-detection rules;
* crash-recovery procedures;
* Git operations between completion and candidate creation;
* token consumption per accepted phase;
* human interventions;
* wall-clock and disk cost as secondary metrics.

### Settled direction so far

1. Use execution capsules as the main abstraction; clone-per-thread is an implementation candidate.
2. Give the capsule orchestrator broad local authority, but no general control-plane authority.
3. Push canonical mutation behind a narrow Doctrine boundary and gradually absorb orchestration duties into Doctrine.
4. Use outbound capsule calls mainly as payload-free notifications; the control plane inspects authoritative capsule state.
5. Keep coordination and result artifacts capsule-local initially, but structure them for eventual ledger or broker ingestion.
6. Treat capsules as slice-scoped resources and phases as transaction boundaries.
7. Reuse capsules operationally where useful, but harvest every phase and garbage-collect all capsules at slice close.
8. Prefer fresh provisioning from canonical accepted Git state after each accepted dependent phase.
9. Begin with cold builds and correctness; optimise provisioning later.
10. Do not attempt fine-grained cache correctness classification.
11. Let workers commit freely inside the capsule.
12. Normalize the accepted final tree into canonical project history on the trusted side.
13. Preserve worker Git history, audit evidence, logs and metadata as forensic artifacts.
14. Preserve immutable OID, explicit admission, journal and CAS principles from the existing Git model.

### Next design questions

Continue breadth-first. The most consequential unresolved questions include:

1. **What is the minimal safe parent-side ingestion mechanism for a potentially hostile capsule Git repository?**

   * local fetch into quarantine;
   * Git bundle;
   * filesystem or tree materialization.

2. **What exactly belongs in the provisioning manifest?**

   * copied mutable files;
   * generated configuration;
   * readonly contextual material;
   * secrets or credentials, if any.

3. **How should work contracts express tool, network, credential, path and verification policy without becoming a generic workflow language?**

4. **What capsule-local state should persist across phase transactions besides the interactive agent session?**

5. **How should baseline verification be inherited by capsules derived from the same provisioning generation?**

6. **Which current refs remain useful as human-facing evidence views after the ledger and candidate OIDs become authoritative?**

7. **How should audit repair work?**

   * mutate a retained capsule;
   * create a new repair capsule from the rejected candidate;
   * treat every repair as a new candidate transaction.

8. **How should parallel results be ordered and rebased when several phases start from the same accepted base?**

9. **How should Linux and macOS provide equivalent security properties without requiring identical sandbox technology?**

10. **What is the smallest v0 that proves the authority model before replacing the existing Git topology?**
