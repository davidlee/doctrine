# RFC-019: Comparison-based value elicitation

## Context

`partial-order.md` (co-located in this RFC's directory) proposes a prioritisation
model built on **pairwise comparative judgement**: instead of asking
stakeholders to assign absolute scores to backlog items, the system presents
carefully chosen two-way comparisons ("if effort were equal, which matters more
for the next release?"), accumulates the answers as evidence, and combines the
inferred value model with engineering estimates, dependencies, and sequencing
preferences to recommend a delivery order. Its pitch rests on a well-supported
observation: humans produce more reliable *relative* judgements than *absolute*
ones, and a planning tool should ask for the cheap, reliable kind.

This RFC evaluates that proposal against the priority engine doctrine already
has — the actionability graph and multi-dimensional score (ADR-015), gating
(ADR-017), value-burndown (ADR-018), and the facet surfaces shipped under the
RFC-001/RFC-002 consumption-surfaces program — and sketches an implementation
path for the parts that are genuinely new.

### What the proposal asks for, decomposed

1. **Separation of forces.** Dependencies ≠ recommended sequencing ≠
   stakeholder value ≠ effort ≠ combined priority; each is kept distinct and
   priority is the derived combination.
2. **Partial information preserved.** Absent or rough data degrades the
   recommendation gracefully instead of blocking it; the model survives new
   items and new dependencies without a re-plan.
3. **Comparative elicitation.** Value is captured through pairwise choices,
   not absolute scores.
4. **Inference.** Accumulated comparisons produce a value model over items —
   a partial order that firms up as evidence accumulates.
5. **Active question selection.** The system chooses the next most informative
   comparison, minimising the number of decisions demanded of stakeholders.
6. **Tension surfacing.** Where the value order and the sensible delivery
   order disagree ("you value A more, but B is small and unblocking — do B
   first"), the disagreement is presented, not silently resolved.
7. **Audit trail.** When the order changes, the evidence that changed it is
   inspectable.
8. **Stakeholder-facing UX.** Sessions, framing lenses ("business value",
   "pain to lose from release", "strategic goal"), context shown per option.

## Discussion

### What the existing engine already delivers

Items 1 and 2 are not gaps — they are load-bearing design commitments of the
current engine, and the proposal's "how it differs from a normal backlog"
section describes doctrine's model almost exactly:

| Proposal force | Existing seam |
|---|---|
| Dependencies ("must happen before") | `needs` dep edges — gating (`blocked_by`), recursive leverage credit (ADR-015 §3), record-gating (ADR-017) |
| Recommended sequencing ("sensible earlier") | `after` seq edges — structural precedence, deliberately **not** a score weight (ADR-015 §3) |
| Stakeholder value | `value` facet (single finite f64 magnitude) → `value_dim` |
| Engineering effort + uncertainty | `estimate` facet — a **range** `[lower, upper]` with skew β; bare items anchor to `max_upper + margin` (ADR-015 §1) |
| Combined priority | derived `score = value_dim + risk_dim + leverage + optionality`, minus value-burndown (ADR-018 §4); never authored to disk |
| Graceful partial information | absent facets collapse to identities/floors, not errors (ADR-015 §1) |
| Sequencing recommendation surface | `next` (actionable frontier, seq-precedence-aware), `survey`, `blockers` |
| Explainability | `explain` — full `{base, value_dim, risk_dim, leverage, optionality, total}` breakdown |

Item 6 (tension surfacing) is *mostly* present: the value/effort tension the
proposal wants surfaced is exactly what `value_dim = value / est_cost` computes
— a small cheap item with moderate value can outrank a large high-value one,
and `explain` decomposes why. What is missing is the narrative form ("B first,
A remains the higher-value initiative") rather than the mechanism.

Item 7 (audit trail) is partial: facets, relations, and config are authored
and diffable, so *what* changed is in git history; but there is no provenance
for *why* `value = 7.0` — the number arrives by fiat. IDE-013
(estimate/value change history) is the existing backlog sibling for this gap.

### What is genuinely new

Items 3, 4, 5, and 8 have no counterpart in the corpus:

- Nothing captures a **comparative judgement** as evidence. Value is authored
  as an absolute scalar via `doctrine value set <ID> <MAGNITUDE>` — precisely
  the "abstract judgement made too early" the proposal argues against.
- Nothing **infers** value from evidence. The scalar is hand-set, take it or
  leave it.
- Nothing **selects questions**. The operator decides what to value and when.
- There is no stakeholder-facing surface at all; doctrine's audience is agents
  and the operating human, via CLI (plus the read-only map explorer).

So the honest evaluation is: **the proposal is not a rival sequencing engine —
it is a missing elicitation front-end for the `value` facet, plus provenance.**
The downstream machinery it envisions (combine value with effort ranges,
dependencies, sequencing hints; keep partial information alive; explain the
result) already exists and is governed. Rebuilding any of it would violate the
no-parallel-implementation rule. Conversely, dismissing the proposal as
"already built" would miss that the *capture* side is the weakest link in the
current value pipeline: garbage-in scalar values are the least defensible input
the score formula consumes. In RFC-001's terms this is a **capture surface**
gap — the mirror image of the consumption-surface gaps that program closed.

### Axioms

Adjudicating OQ-4 forced the underlying model to be stated outright. These
axioms govern everything below (and dissolved what first looked like a
cross-kind admissibility problem):

- **A1 — elicit base, derive consequence.** The engine already computes
  unlock-worth (recursive leverage), gating, and burndown from structure. A
  human judgement that bakes any of that in gets double-counted. Comparative
  judgements therefore target **intrinsic** facets only — value-in-itself,
  effort held equal, ignoring what an item unblocks or what depends on it —
  and the prompt must be framed to exclude consequence. Summing "the worth of
  the questions blocking X" into X's own value adds a derived quantity to its
  own inputs.
- **A2 — record value is derived, not authored (product policy).** Under the
  engine's model a record's delivery priority is entirely derived from what it
  unlocks (leverage from the work it gates, ADR-017); it *does* have an
  intrinsic settle-cost (estimate). Records are therefore outside the value
  domain and inside the estimate domain. *(Reworded at the 2026-07-11 external
  review: the earlier form — "knowledge has no intrinsic value" — was a
  philosophical overreach. Research plainly can carry option value and durable
  organisational knowledge; the defensible statement is that the engine
  assigns records no independently **authored** value — worth reaches them
  through governed structure. That is a product policy with an amendment path,
  not metaphysics.)*
- **A3 — value burns down; decomposition must not mint value.** ADR-018
  subtracts a fulfilling slice's value from the item it fulfils. If
  decomposing a task *added* value, the ordering would be useless. Judgements
  constrain the item's value as scoped; burndown applies after, as a
  post-pass (see OQ-7 for the partial-fulfilment wrinkle).
- **A4 — commensurability is a property of domains, not kinds.** What may be
  compared with what is decided by whether both sides carry the same
  intrinsic currency. SL vs IMP: same currency, fine. SL vs QUE: excluded by
  A2. SL vs RSK: excluded because a risk item's worth is expected-loss
  avoidance, which the score already carries in a *separate* dimension
  (`risk_dim`) — comparing across that boundary muddles two dimensions the
  engine deliberately keeps apart.

### Typed comparison domains and frames

The axioms give the ledger a type system.

**Domains.** Every row belongs to a facet domain, with its own admissibility
predicate, constraint semantics, and projection target:

| Domain | Admits | Constrains | Notes |
|---|---|---|---|
| `value` | value-bearing work kinds (SL + backlog minus RSK) | raw `value` facet (A1: pre-`kind_weight` — weights are operator policy on top of intrinsic worth, so a retune reorders policy without falsifying bounds) | Phases A–D |
| `estimate` | anything with a settle/delivery cost — work kinds **and** records | `est_cost` ordering (the scalar the engine already derives from a range via skew β); projection adjusts ranges minimally within bounds | sibling extension; comparative sizing is a better-trodden human skill than value scoring, and this is where team-facing "sequence everything that needs doing" sessions live. Honest caveat: record estimates are currently inert in scoring (records have no `value_dim`; leverage does not consume the record's own cost) — near-term payoff is the sequencing conversation itself |
| `risk` | risk-faceted items | likelihood / impact / exposure ordering | later, same machinery |

Cross-kind comparison *within* a domain is unremarkable; comparison *across*
domains is what A4 forbids.

**Frames.** A row's inferential force is defined by what the human was
actually asked, so the prompt frame cannot be free text: each domain carries a
**closed frame vocabulary**, and each frame maps to a specific formal
constraint (the same move ADR-016 made for relation roles — closed vocabulary
keeps semantics auditable). The proposal's own example questions have
*different* formal content and demonstrate why this matters:

- "which creates more business value, effort equal?" → `v_A > v_B` (value
  domain, the workhorse frame);
- "which would you rather have first?" → a delivery preference,
  `v_A/c_A > v_B/c_B` — a different inequality that entangles estimates and
  is honest only when framed as such;
- "which is more work?" → `c_A > c_B` (estimate domain).

The constraint layer consumes rows *by frame*; a frame the inference does not
yet understand is captured losslessly and left inert (the same
capture-everything / infer-only-what-is-sound posture throughout).

**Phase B design obligation** (external review 3): `prefer-first` shipped
inside the value-domain capture vocabulary (SL-210 D7) but constrains value
*density*, not raw value — it must never compile to `v_A > v_B`. Phase B
either gives it its own constraint compiler over current costs (the weighted
inequality `v_A·c_B > v_B·c_A`, which couples its bounds to estimate edits),
leaves it inert initially, or reclassifies it into a delivery-preference
domain.

### Design tensions

**T1 — ordinal evidence, cardinal consumer.** Comparisons yield ordinal
information; `value_dim` needs a cardinal magnitude to divide by `est_cost`.
*(Revised twice: at OQ-2 adjudication — maximal tolerance of missing
information, minimal tolerance of losing inferrable information — and at the
2026-07-11 external review, which showed the first revision conflated two
separable requirements: preserving the original evidence, and treating every
observation as inviolable truth. Human comparative judgement is fallible;
intransitive answers are ordinary noise, not exceptional corruption, and a
model that goes infeasible under them is unusable in practice.)*
The bridge is **three tiers** — evidence, constraint set, projection — the
derived two pure over `(ledger, facets, config)`:

- *Tier 1 — evidence (authored, lossless).* The ledger rows themselves:
  immutable observations, possibly mutually inconsistent. **Losslessness is a
  property of this tier and only this tier** — capture never discards, merges,
  or reinterprets. Calling the *inference* lossless was the earlier text's
  overclaim: compiling observations into inequalities is an interpretation.
- *Tier 2 — constraint set (derived interpretation, deterministic
  degradation).* Inference compiles active rows into formal constraints: an
  `equal-effort` judgement → strict inequality `v_A > v_B`; an `equal`
  response → equality/band; an authored `value` magnitude → **point anchor**,
  hard by construction (authored truth — the only unconditionally hard
  constraints in the system). Propagation over the compiled set derives
  per-item **bounds**: `A > B` with `B = 3.2` yields `v_A ∈ (3.2, ∞)`.
  Because judgements are fallible, the compiled system must stay usable under
  ordinary noise — degradation is deterministic, never statistical smoothing
  and never infeasibility:
  - **Preference cycles** (A > B > C > A): the cycle's members collapse to one
    *tied group* for propagation (SCC condensation — members share bounds),
    the cycle is surfaced as a finding naming its rows, and the constituent
    pairs are marked for reprobe. Inference proceeds over the condensation;
    the component stays usable and nobody is asked to retract
    valid-but-inconsistent evidence. **Phase B design obligation** (external
    review 3): condensation-edge semantics must be chosen and defended —
    collapse is serviceable degradation but not neutral. With `A > B > C > A`
    and `A > D`, naively sharing the tied group's bounds gives B and C a
    relation to D that no row asserts, amplifying noisy evidence beyond what
    exists. Candidate semantics: existential (any member carries the edge),
    universal (all members must), member-level bounds retained around the
    SCC, or conflicted components propagating only through anchors.
  - **Anchor conflicts** (judgement rows jointly incompatible with the
    authored anchors): anchors win; a **deterministic conflicting-evidence
    set sufficient to restore feasibility** is excluded from propagation as
    **residuals** and surfaced as a finding — preserving every anchor and
    maximising retained evidence per a documented policy. *(Weakened at
    external review 3 from "minimal conflicting rows": inclusion-minimal,
    minimum-cardinality, and first-found residual sets have very different
    complexity and stability, and minimum-correction sets can turn expensive;
    the selection policy is Phase B's to choose — the determinism and the
    documentation are not negotiable.)* T3(a)'s authored-wins logic applied
    at the constraint tier.
  - Every exclusion is visible: `explain` carries residual counts and the
    findings name the evidence, so an ignored answer can never be silent.
  - Seam noted for later: an explicit `asserted` marker promoting a specific
    row to anchor strength (a deliberate hard commitment, the review's
    "accepted constraints" tier) is expressible in this model without rework;
    not needed at ship.
- *Tier 3 — projection (derived scalar + diagnostics).* `value_dim` consumes
  a single number, so a representative point is projected **within** each
  item's feasible bounds (deterministic, sign-aware, implementation-owned —
  isotonic spacing generalises across signs; a constrained Bradley–Terry-style
  fit is usable only inside provably-positive components). The projection is
  labelled in `explain` alongside its bounds, provenance, and
  residual/contradiction diagnostics; it is never authored.

**Formal contract the Phase B design must pin** (2026-07-11 review — this is
design-level material, not implementation detail): whether strictness is
mathematical or an ε; representation of open and unbounded interval endpoints;
the gauge for an anchor-free component (its projection centres on
`DEFAULT_VALUE = 1.0`, the OQ-2 resolution); projection stability under small
evidence deltas (one new judgement must not wildly reorder projections); and
scale behaviour under anchor changes.

**Domain contract** (RV-260 F-1). The value carrier is any finite f64 —
negative magnitudes are legal today (`value set` accepts them) and stay legal.
Order-frame inequalities (`v_A > v_B`) are sign-agnostic and always valid.
**Ratio frames are sign-guarded**: a ratio judgement is admissible only where
inference can prove both sides' feasible regions strictly positive; elsewhere
the capture is refused with the reason (a ratio against a possibly-negative
or zero-crossing value is meaningless). Projection must be sign-aware: a
Bradley–Terry-style fit is usable only within provably-positive components;
isotonic spacing generalises across signs. The determinacy predicate needs no
sign restriction — with `est_cost` floored at `EPSILON` (ADR-015 INV-3),
`sign(v_A/c_A − v_B/c_B)` reduces to the sign of `v_A·c_B − v_B·c_A`, a linear
objective for any sign of `v`. Its extremes must be taken over the **joint
feasible set**, not the per-item interval box (see *Indeterminacy* — the
2026-07-11 review correction).

Rejected bridges:

- *Pure statistical fit (Bradley–Terry alone).* BT models paired comparisons
  probabilistically (P(A beats B) = sᴀ/(sᴀ+s\_B)) and fits point strengths
  from noisy evidence. Deterministic and cycle-tolerant, but it converts
  inequalities into point estimates (loses `v_A > 3.2` as a hard bound) and
  absorbs contradictions silently — both losses the OQ-2 requirement rules
  out. It survives only as a candidate *projection* inside the feasible
  region. The 2026-07-11 review's charge that rejecting BT wholesale
  "overcorrects" is answered by the three-tier split: evidence stays lossless
  (tier 1), interpretation degrades deterministically and visibly (tier 2),
  and the fit lives where fits belong (tier 3).
- *Pure structural partial order* (comparisons clamp the score-sorted surface
  directly). Collides with ADR-015's settled posture that structure wins only
  for seq edges; cannot compose with `est_cost`; turns intransitive human
  answers into hard sort failures instead of surfaced evidence conflicts.

**T2 — where comparisons live.** Three candidate homes:

- *Relation edge* (`A preferred_over B`): tempting, wrong. A comparison is not
  a durable semantic relation between the two items — it is contextual
  evidence (who judged, when, under which lens/framing), it is many-per-pair,
  and it must not enter the relation graph where the consequence pass and
  `inspect` would see it. ADR-016's own test (does the distinction change
  structure/graph-effect/inbound semantics?) says this is not relation
  vocabulary at all.
- *Per-entity facet rows*: a comparison has two subjects; storing it under
  either entity fabricates an owner and splits the pair's evidence.
- *Corpus-level append-only ledger* (authored tier, committed), organised as
  **session files** (OQ-3 resolution): `.doctrine/comparisons/<date>-<uid>.toml`
  — domain-neutral path, since estimate/risk domains share the ledger — each
  holding a `[session]` header (rater, audience, defaults) plus `[[judgement]]`
  rows that inherit its context. One row per judgement; `uid` per row (the
  date/uid pattern) is what supersession and tombstone references resolve
  against (T6). The **shipped v1 row** (SL-210) is
  `{uid, seq, a, b, preferred, domain, frame (closed vocab per domain), form:
  order|ratio, lens?, rater (mandatory, OQ-1; human|agent), by?, note?, date}`
  (`form`, not `kind`, to avoid colliding with entity-kind vocabulary; the
  human/agent rater distinction keeps `explain` honest — "bounds derived from
  2 human + 14 agent judgements" — and enables an elicitation mode where an
  agent pre-seeds cheap orderings and the selector prioritises *human
  confirmation* of the load-bearing ones, see T7).

  **Row vocabulary completion (v2, additive)** — the 2026-07-11 review showed
  v1 under-represents the constraint vocabulary this RFC itself discusses;
  the schema is versioned precisely so this is an additive revision, not a
  migration crisis:
  - a `response` generalising `preferred`: `prefer-a | prefer-b | equal |
    incomparable` — rough equality and "cannot compare / insufficient
    context" are legitimate answers v1 can only drop (an `equal` maps to a
    tier-2 equality/band; an `incomparable` maps to no constraint but records
    that the question was asked — selector fodder, not inference input).
    Compatibility rule (external review 3 — "additive structurally" needs a
    semantic mapping): v1 rows map deterministically, `preferred = a` →
    `response = prefer-a`, `preferred = b` → `prefer-b`; `preferred` and
    `response` do not coexist in v2 files. A single undifferentiated
    `incomparable` is likely too coarse for the selector — permanently
    incommensurable, insufficient context, wrong audience, and
    cannot-answer-now suppress or resurface differently; refining it is a
    Phase C-adjacent schema question, noted, not blocking;
  - a ratio **magnitude** where `form = ratio`: "A worth ≥ k× B" is
    meaningless without `k`;
  - explicit `supersedes = <row-uid>` (T6 revision);
  - a band tolerance for `equal`, if the Phase B design chooses ε-bands over
    exact ties.

  Claim correction (review): v1 capture was lossless *for the vocabulary it
  accepted* (strict order-form preferences); "full typed row from day one"
  overstated it. The version gate, not the v1 row, is the migration-free
  guarantee. Append-only matches the evidence semantics: revisions and
  withdrawals are appended rows, nothing is edited in place (see T6). This is
  the recommended home. Storage-rule fit: the ledger is authored evidence; the
  fitted values are **derived at read time** (pure function over ledger +
  config), exactly parallel to ADR-015's "no score is authored to disk".

  The session file is the unit of persistence because it models how judgements
  actually arrive — a sitting: one rater/audience, one date, a run of answers —
  and because the primary practical hazard is **two developer machines refining
  their backlog in isolation**: a single append-only file guarantees an EOF
  merge conflict on every reconvergence (elicitation is bursty — a session
  appends dozens of rows), where distinct session files merge as clean add/adds
  with no reservation machinery (filename uid via the existing date/uid
  pattern). Multi-agent worktree traffic is the same shape, secondary in
  practice (dispatch is implementation, not prioritisation). A
  `merge=union` single file was considered and rejected: union merge is
  line-based and can interleave multi-line TOML blocks into invalid syntax,
  and it duplicates rows under cherry-pick. Session metadata has to live
  somewhere regardless (OQ-1's audience scoping), and the web surface gets its
  natural round-trip artifact. Read seam: directory scan, the house pattern.
  Ad-hoc single comparisons land in an implicit session (settled at SL-210
  design D2: session-of-one per invocation; no per-day file, no lock).

**T3 — two sources of value.** Once projected values exist, an item may have
an authored `value` magnitude, comparison-derived bounds, both, or neither.
Resolution options:

- *(a) Authored wins; projection fills absence.* An authored magnitude is a
  point anchor in the constraint layer (it both wins for that item *and*
  propagates bounds to everything compared against it); items with evidence
  but no authored value take the projected point; items with neither keep the
  engine's live absent-value default — `DEFAULT_VALUE = 1.0` for value-bearing
  kinds (`src/priority/graph.rs`, SL-177), *not* the `value_dim = 0` ADR-015's
  prose still states (the ADR text is stale on this point; the Phase B
  amendment should correct it — RV-260 F-3). Projection fallback must
  reproduce the live default. Cheapest to reason about;
  preserves the operator's explicit override lever (the spirit of RFC-001
  surface (d)'s authored-pin). An authored value that *conflicts* with the
  bounds is a surfaced contradiction, not a silent win.
- *(b) Projection always wins when evidence exists.* Makes elicitation the
  authoritative channel; demotes `value set` to a seeding verb. Bolder, but
  removes the direct override and makes one stray comparison perturb
  deliberately-set values.
- *(c) Blend.* A confidence-weighted mix. Rejected: opaque, and `explain`
  would need to expose a fourth-order breakdown to stay honest.

Recommendation: (a), with `explain` labelling the source and bounds
(`value: 6.2 (projected, bounds (3.2, 9.1), 9 judgements)` vs
`value: 8.0 (authored)`). **Adopted**: (a) is now governed policy — REV-022
(approved, applied to ADR-015, 2026-07-11).

**T4 — audience mismatch.** The proposal's stakeholder sessions, framing
prompts, and per-option context cards are a product surface for humans who are
not doctrine operators. Doctrine's delivery order for that kind of surface is
settled by precedent: CLI verb first (agent/operator usable immediately),
web/map surface later if the interactive mode earns it (as `map serve` did for
graph viz). The elicitation *session* — show pair, capture answer, pick next
pair — is CLI-shaped enough to be useful long before any web UI exists, and an
agent can mediate a stakeholder conversation through it (the "structured
planning conversation, mediated by software" the proposal wants, with the
agent as facilitator). *(OQ-1 adjudication: a read-write web elicitation
surface serving distinct stakeholder audiences is an **intended** product
direction, not speculative — but it stays sequenced after the CLI evidence
pipeline proves the interaction.)*

**T5 — lenses vs frames.** The proposal's alternative framings split into two
different things once examined. Some change the *formal constraint* ("which
would you rather have first?" entangles cost) — those are **frames**, closed
vocabulary, handled above. Others change *which flavour of value* is being
judged ("business value" vs "strategic goal" vs user value, maintainability,
operational cost) — those are, in modelling terms, *dimensions of value*, and
the engine has exactly one value axis today. The **`lens`** column is the
optional dimension tag and the deliberate migration seam: record it now
(cheap, keeps evidence honest), fit a single scale initially. If per-lens
evidence demonstrably diverges — the same pair ordered differently under
different lenses — that is the trigger for IDE-035 (multi-dimensional value
with per-dimension coefficients, generalising the `risk_dim` treatment), and
per-lens constraint sets become per-dimension constraint sets almost for
free. The data to check the trigger will exist because we recorded it.

**Pooling discipline** *(added at the 2026-07-11 review — "capture both
lenses, fit one scale" is incoherent under a constraint model)*: `revenue:
A > B` and `user-safety: B > A` would register as a preference cycle when
they are the expected signature of distinct value dimensions, not a
contradiction. Until IDE-035 lands, the pooled tier-2 fit consumes
**unlensed rows only**. Lens-tagged rows are inert for `value_dim` — captured
losslessly, listed, reported per-lens in `explain`/`compare list`, and used to
check the divergence trigger — but never mixed into one constraint component,
neither with unlensed rows nor with rows under a different lens. Lens is
correspondingly part of row identity for supersession (T6).

**T6 — staleness is structural.** Items change after judgements about them
were made; the proposal itself warns comparisons are only as good as the item
descriptions compared. Content-diff detection (hash the body at capture, flag
mismatch) is rejected: "body changed" is a noisy proxy for "judgement invalid"
(most edits are elaboration and typo fixes), and doctrine's thesis is that
meaning-changes are governed *structurally*. A row's subject is the item **as
scoped identity**, not its prose snapshot; stable identity is assumed for
prioritisation unless reflected structurally. Validity semantics:

- **Supersession is explicit** *(revised at the 2026-07-11 review — the
  earlier implicit rule invented causality: two independently recorded
  judgements are not revisions merely because one uid sorts after the other,
  and lexicographic winner-picking silently discards concurrent evidence,
  contradicting tier-1 losslessness)*. A row supersedes another in exactly
  two ways: **explicitly**, by naming it (`supersedes = <row-uid>`, v2
  schema); or **implicitly within a single session file**, where the same
  rater re-answers the same question later in the sitting — same identity key
  `(pair, domain, frame, form, lens, rater)`, higher `seq` wins — a genuine
  revision, causally ordered by the file itself. Note `lens` (and `form`) are
  part of the identity key: two answers under different lenses must never
  supersede one another (T5). Same-key rows arriving in *different* sessions
  are **concurrent evidence, both active**: agreeing rows corroborate;
  conflicting rows are exactly what the tier-2 contradiction machinery
  surfaces (tied group + reprobe), and a human resolves the conflict with a
  new row that explicitly supersedes — surfaced disagreement, never a
  lexicographic winner. The `(date, session_uid, row_seq)` total key (RV-260
  F-4) survives as the deterministic *iteration and display* order — any two
  replicas holding the same merged file set still derive the same active-row
  set and the same diagnostics — and cherry-pick duplicates still collapse by
  uid; the key no longer selects winners.
- **Eviction** — explicit withdrawal, written as an appended *tombstone row*
  referencing the target row's **uid** (unambiguous regardless of file order;
  the ledger stays append-only; the audit trail shows a judgement existed
  and was withdrawn, by whom, when).
- **Lifecycle event-effect table** — structural entity events map to row
  effects: item goes terminal → its rows go inert for elicitation but stay
  active for inference — closing B does not falsify that A was judged above
  B; item superseded → rows evict with a reprobe hint (no
  silent transfer to the successor — meaning may have shifted; explicit
  transfer stays available); item decomposed → parent rows stay attached to
  the parent as-scoped, children inherit nothing (inheritance would mint
  value, violating A3).

**Anchor lifecycle** (RV-260 F-8): bounds are always a pure function of the
*current* anchors and active rows — there is no snapshotting (snapshotting
authored data into derived state would invert the storage rule). A terminal
item's *rows* persist as relative structure, but the absolute bounds they
propagate exist only while the anchor does: `value clear` on any item,
terminal or not, legitimately relaxes every bound derived through it, and the
determinacy check re-opens affected decisions as reprobe candidates — the
system responds, it does not pretend the anchor still holds.

The gap this leaves — silent in-place meaning rewrite under a stable id — is
exactly the ungoverned change doctrine's norms already prohibit;
content-hash detection would compensate for the violation rather than uphold
the norm. And because the ledger is committed, body-at-judgement-time is
recoverable from git history via the row's date, so a future *advisory*
drift diagnostic (`comparisons --drift` or a doctor check) needs no hash
column: it is evidence for a human deciding to evict, never an inference
input. If loosely-governed backlog bodies drift meaningfully in practice,
that diagnostic is the safety net.

**T7 — agent-seeded evidence needs a stated trust policy** *(added at the
2026-07-11 review)*. At ship, `rater = agent` rows constrain inference exactly
like human rows: the agent is the operator's instrument, provenance is
mandatory and disclosed (`explain`: "bounds from 2 human + 14 agent
judgements"), and the elicitation selector prioritises *human confirmation* of
load-bearing agent-seeded orderings. The named risk is real: an agent can
cheaply mint enough constraints to stabilise an ordering before any human is
consulted — meaning agent evidence could *close* questions humans never saw.
Accepted at ship for the operator-and-their-agent audience (the flood is
visible, attributable per row, and tombstone-able wholesale), with the policy
seam explicit: a config knob demoting agent rows — inert-until-confirmed, or
excluded from *determinacy* so agent evidence can propose orderings but never
retire a question — is the designed extension, mandatory before stakeholder
sessions (Phase D+) treat the ordering as elicited truth.

### Indeterminacy, reprobing, and question yield

The decision the engine actually takes from value is the ordering of
`value_dim = v / est_cost` among frontier items. Under the constraint layer
this yields a mechanical definition of when the corpus knows enough:

- A pair (A, B) is **determined** iff the sign of `v_A/c_A − v_B/c_B` is
  constant over the **joint feasible set** — every value assignment satisfying
  the complete active constraint system. *(Corrected at the 2026-07-11
  review: the earlier text reduced this to per-item interval endpoints, which
  is wrong — the latent values are jointly constrained, and marginal intervals
  discard the correlations. `v_A > v_B` with both marginals `[0, 10]` is
  determined over the joint set while the interval box calls it open. Box
  endpoint tests are conservative and incomplete, never "exact".)*
  Operationally the check is an optimisation: minimise and maximise the
  linear objective `v_A·c_B − v_B·c_A` over the constraint set; the pair is
  determined iff both extremes share a sign. For the shipped constraint
  vocabulary (strict order relations + point anchors — difference-constraint
  structure) those extremes are computable by graph propagation, no general
  LP solver required; equality bands and fixed-ratio rows preserve linearity;
  whether later vocabulary forces a genuine LP is a design question for the
  phase that admits it. Per-item bounds survive as the *display* projection
  of the joint set (`explain` renders them) — decisions are never computed
  from the box. Scope of "feasible assignment" (RV-260 F-5): value bounds
  vary; **costs are the scalar `est_cost` the engine actually consumes**
  (range collapsed via skew β, floored at `EPSILON` — ADR-015). Estimate
  *uncertainty* is not part of the feasible region; an estimate *edit* moves
  `est_cost` and re-runs determinacy (the reprobe dynamic below). A richer
  feasible-region model over `(lower, upper)` is Phase E's entry criterion,
  not an assumption of Phases A–C.
- Anything that moves bounds or costs — a new judgement, an authored value, an
  estimate edit — re-evaluates determinacy. The proposal's "estimates changed,
  so the order changed / reprobe" behaviour falls out with no clock and no
  staleness heuristic: B's estimate drops sharply → a previously determined
  pair goes indeterminate → it surfaces as a reprobe candidate automatically.
- **Question selection** (Phase C) picks the question with the maximum
  *guaranteed* shrinkage of the *decision-relevant* indeterminate set — not
  global sort entropy (mechanism in *Pair selection* below). The
  information-theoretic floor for a full total order is Θ(n log n)
  comparisons (comparison-sort bound); decision determinacy needs far fewer,
  which is the proposal's "minimum number of decisions" property made
  precise.
- **Yield ceiling.** Pure order questions cannot always determine
  `v_A/c_A` vs `v_B/c_B` when costs diverge — that requires ratio-form
  evidence ("is A worth at least ~2× B?"), which bounds `v_A/v_B` rather than
  just its sign. The ledger schema therefore carries a judgement-kind column
  (`order | ratio`) from day one, so the ceiling is liftable without a
  migration even though Phase A captures only `order` rows (OQ-6).

Engineering's seq/dep structure composes with (possibly conflicting)
stakeholder value order exactly as ADR-015 already prescribes — structure wins
for `after`/`needs`, value fills the silence. What is added is the *surfacing*:
where surviving structure overrides the value order, the conflict is rendered
(Phase D), never silently resolved.

### Pair selection: decision contexts, guaranteed yield, and the queue/curator split

**The objective is decision stability, not order completeness.** The corpus
never needs a total order; it needs the decisions it is about to take to be
stable under every feasible assignment within current bounds. Indeterminacy
away from those decisions is *deliberately preserved ignorance*: a pair buried
deep in the graph may never need ordering — estimates will move, deps will
land, scope will change before that decision bites — so asking now spends
scarce judgement budget on decisions that expire unresolved. This is A1's
logic applied to elicitation itself: derive everything derivable, ask only
where inference is silent *and the silence matters now*.

**Decision contexts.** What counts as decision-relevant is a pluggable
predicate over the feasible region, and two contexts are in scope:

- *Sequencing* (the internal / product-company default): the decision is
  "what next" — the actionable frontier's top ordering (to the depth the team
  plans against) must be order-stable.
- *Scoping* (agency-style fixed-scope projects and sprint planning — the same
  structure with different labels): the decision is a **cut**, computed by a
  precise algorithm (RV-260 F-7): iterate items in (value-density desc,
  canonical-id asc) order; for each item X, take `C = needs-closure(X) minus
  already-committed`; if `cost(C) ≤ remaining budget`, commit all of C and
  deduct; otherwise X is line-excluded — and **continue** (skip-and-continue,
  not stop: cheap items ranked below an unaffordable closure still admit).
  Deterministic given (bounds-projection, costs, budget). Decision stability
  is **membership stability**: each item on the same side of the line under
  every feasible assignment. Exact quantification over the continuous
  feasible region is not attempted; the proposed check — recompute the cut
  under the item's pessimal assignment (its value at lower bound, competitors
  at upper) and its optimal converse; same side in both ⇒ stable, else it
  joins the boundary band — is a **heuristic stress test**, two cut
  computations per item, cheap. *(Relabelled at the 2026-07-11 review: the
  earlier "sound, incomplete" claim is unproven — under a dependency-closed
  skip-and-continue greedy cut, membership is not obviously monotone in the
  value assignment: closures overlap, earlier commitments change later
  marginal closure costs, and the two extreme assignments may not even be
  jointly feasible. A soundness proof, or a joint-region reformulation, is
  Phase E entry material alongside the estimate feasible-region model.)* Items far above or
  far below the line are membership-stable even with wide value bounds, so
  the indeterminate set — where all elicitation flows — *is* the boundary
  band. Ordering within the
  committed set or the excluded tail is worthless, and the machinery knows it
  without being told. Two honest notes: the greedy value-density cut (which
  `value_dim = v/est_cost` ordering already embodies) is standard scoping
  practice but not optimal knapsack — deliberate policy, not accidental
  imprecision; and the budget itself is an input doctrine does not model — a
  per-invocation CLI/config parameter, not new entity modelling (design-time
  detail). This also answers the proposal's concession that MoSCoW is
  "situationally useful for release boundaries" properly: the boundary is
  derived, and buckets are replaced by a cut plus an explicit indeterminacy
  band. Stakeholder this-vs-that judgements reorder the work; engineering
  estimates move the line.

**The deterministic core: guaranteed yield.** Binary search works by picking
the probe that halves the space regardless of the answer; this is the
generalisation to a constraint graph with anchors. For each candidate
question, hypothetically apply each possible answer, run exact propagation
(cheap and pure — the constraint layer), and count newly-determined
decision-relevant pairs/memberships under each outcome. Rank candidates by
**guaranteed yield** — the *minimum* over the answers — so progress is
certain whatever the human says, weighted by decision impact (how prominent
the affected decision is: frontier rank, reorder amplitude, distance from the
water line). No probability model is needed. Honest theory note: optimal
adaptive sorting under partial information is intractable (counting linear
extensions is #P-hard); greedy max-min shrinkage is the principled tractable
move and degrades gracefully. **Stopping conditions** *(weakened at the
2026-07-11 review — zero one-step guaranteed yield does NOT prove the
decision set stable: a zero-immediate-yield bridge question — comparing A
against an anchored C — can unlock the question that settles A vs B, so
greedy exhaustion and stability are different facts)*: the queue **stalls**
when no candidate inside the bounded search policy has positive immediate
yield, or when remaining estimated yield falls below the attention threshold.
Stall means the one-step heuristic is exhausted, not that no informative
question sequence exists; the render says which. Stability, where claimed,
must be established independently (all decision-relevant pairs determined
over the joint set).

The cost claim made concrete (RV-260 F-6) — three bounds keep this cheap:
the **candidate pool** is not all-pairs but the indeterminate pairs inside
the decision-relevant region (top-of-frontier adjacency or the boundary
band) — O(K²) for a planning-depth K, not corpus-quadratic; **propagation
runs on the comparison constraint graph** (nodes = compared items + anchors,
edges = active rows), which is evidence-sized, not entity-graph-sized — the
priority engine's whole-graph passes are not re-run per hypothetical;
and bounds are computed **once per pass**, with each candidate needing at
most two hypothetical propagations, each linear in constraint edges
(longest-path over the condensed DAG). Total per queue refresh:
O(K² · |active rows|) — trivial at realistic sizes (hundreds of items,
hundreds of judgements). Internals (pool thresholds, impact weighting) stay
implementation-owned; what the RFC commits to is that a tractable plan
exists and the queue is **deterministic within its bounded candidate policy**
— not "exact" (2026-07-11 review): its utility ordering is greedy one-step
yield with the stall semantics above, and hypothetical propagation must run
over the joint constraint set, not marginal boxes.

**Cross-domain nomination.** Near a scoping water line, the highest-yield
question is often not a value comparison but an estimate refinement — the
line is uncertain from both sides (value uncertainty reorders items; estimate
uncertainty moves the cumulative-cost line itself). The yield computation is
in principle domain-blind — apply, propagate, count — so the selector can
nominate across domains in one queue: "compare A vs C" and "re-estimate B"
ranked together, each routed to the audience that can answer it (stakeholders
reorder, engineering re-estimates). In the scoping context the estimate
domain is therefore co-equal, not a sibling extension. **Scope honesty**
(RV-260 F-5): yield-ranking an estimate question requires a formal estimate
feasible-region model — what an answer constrains over `(lower, upper)`, and
what the hypothetical answer space even is for a range refinement (not
binary, unlike a comparison). That model is **Phase E's entry criterion**;
until it exists, estimate questions near the line are surfaced heuristically
by the agent curator, not yield-ranked by the engine — the queue's exactness
claim applies to the value domain only.

**The queue/curator split.** The engine owns the **candidate queue**: pure
over `(bounds, costs, ledger, statuses, context)`, ranked by guaranteed yield
× decision impact, each candidate carrying its reasons ("indeterminate
because costs diverge; resolving stabilises next's top 5; answer propagates
to 7 other pairs") — deterministic, testable, JSON-emittable, the same
legibility posture as `explain`. The agent owns **curation and
facilitation** on top:

- *commensurability-in-the-small* — A4's domain gate is coarse; within a
  domain, "fix docs typo" vs "rebuild auth" is admissible but a junk
  question: granularity and context distance degrade the evidence even when
  the pair is formally comparable. Genuinely semantic; the engine cannot rank
  it, an agent can;
- *audience fit* — which pairs this rater is competent and appropriate to
  judge (partially structural via kinds/tags, partially semantic);
- *frame choice and phrasing* — selecting the closed frame and rendering
  context (title, summary, deps, risk) into an answerable question;
- *session flow* — clustering related pairs for cognitive coherence, fatigue
  budget, lens switching, and recognising when a comparison has become a
  debate to park (a consult), not an answer to record.

The contract between the layers: the agent **selects from the queue** — skip,
reorder, cluster — but never invents the ranking. The guarantee is narrower
than first stated (2026-07-11 review): the queue is deterministic and
auditable, and no *determined* pair is offered **as a question** — but
determined pairs may still deserve human attention (drift checks,
confirmation of agent-seeded evidence, contradiction diagnosis), and no
elicitation system can promise zero wasted attention.
Capture stays open: a judgement arising organically in conversation is
recordable directly — `elicit` is curated, `compare` is not. The split
degrades cleanly: no agent → the queue head is a serviceable naive selector;
agent-CLI → the agent curates; the OQ-1 web surface later → the same queue
serving stakeholder sessions. The selection *objective* (decision stability
under the active context) is policy and lives here; the scoring internals
(yield weighting, impact decay with depth, thresholds) are
implementation-owned tuning, the ADR-015 posture on numeric defaults.

### Implementation path

Slice-sized phases, strictly additive, each independently shippable:

**Phase A — capture.** *(Shipped: SL-210, landed on main 2026-07-11;
RV-262/RV-263 clean.)* As built: domain-neutral top-level `doctrine compare`
verb group (capture / `list` / `withdraw` — naming settled at design, D1),
append-only session files under `.doctrine/comparisons/` (T2), session-of-one
implicit sessions (D2), closed value frames `equal-effort` + `prefer-first`
(D7), admissibility at capture (D6), versioned schema **v1** with
`(date, session_uid, seq)` ordering metadata and `form = order|ratio` carried
unexposed (D8). No scoring change — pure capture. The v2 additive columns
(response vocabulary, ratio magnitude, explicit `supersedes` — T2/T6
revisions) ride Phase B.

**Phase B — inference: resolution + constraint set + projection.** Schema v2
(the additive T2 columns) with capture-side acceptance of `equal` /
`incomparable` responses and explicit `supersedes`; row-validity resolution
per the revised T6 (explicit supersession, within-session implicit revision,
tombstones, lifecycle event-effect table) — pure over `(ledger, entity
statuses)`, which the scan already provides; tier-2 constraint compilation
with **deterministic degradation** (SCC tied-group collapse for cycles,
anchor-wins residual exclusion, lens partition per T5) and contradiction
findings surfaced like needs-cycle diagnoses; tier-3 deterministic projection
within bounds, flowing into `value_dim` under the REV-022 resolution policy
(already applied to ADR-015); `explain` gains the value-source line with
bounds and residual diagnostics. Wired as a pre-pass beside the existing base
pre-pass: scan reads the ledger once (impure seam), inference is pure.
**Honest sizing** (2026-07-11 review): B is *not* small — resolution
semantics, the strict-inequality formal contract, degradation, gauge fixing,
projection stability, and scoring integration each carry design weight; it is
one slice only if its design stays coherent as one, and splits if it sprawls.
Determinism tests mirror the existing no-NaN/total-order suite; propagation
tests cover chains, anchor conflicts (residual exclusion), preference cycles
(degraded, never infeasible), explicit and within-session supersession, lens
partition, tombstones, and lifecycle effects.

**Phase C — elicitation.** **Entry criterion** (2026-07-11 review): an
empirical evaluation of the Phase B inference layer against a real ledger
over this repo's own backlog — does it produce useful, stable bounds and
projections under genuine evidence, and do the degradation paths fire at
sane rates? Question-selection machinery is exploratory until that evidence
exists; committing to it now would design an adaptive selector against an
inference layer whose practical behaviour is unmeasured. Then: the candidate
queue plus a capture loop.
`doctrine value elicit [--lens L]` surfaces the ranked queue (*Pair
selection*): guaranteed-yield × decision-impact ordering, reasons attached,
JSON-emittable for an agent curator; un-compared items enter by binary
insertion against the projected median. Render the two items with enough
context to choose (title, body summary, deps, risk), accept the answer,
append to the ledger. The queue is a pure function over
`(bounds, costs, ledger, statuses, context)`. Estimate/value edits re-surface
reprobe candidates through the same determinacy check. Offers are
audience/session-scoped rather than kind-gated (a stakeholder session offers
product-shaped pairs; a team session offers anything admissible), and the
selector prioritises human confirmation of agent-seeded orderings where both
exist. The queue head is the naive selector and ships first; agent curation
(commensurability-in-the-small, frame choice, session flow) layers on top as
a skill, not engine code. The sequencing decision context ships here.

**Phase D — tension narrative + session surface.** Extend `next`/`explain`
with the value-rank vs delivery-rank disagreement callout ("SL-x outranks
SL-y on value; SL-y is cheaper and unblocking — surfaces first"), and render
where surviving seq structure overrides the value order rather than letting
structure win silently. Later, per OQ-1: session mode and the read-write web
elicitation surface for distinct stakeholder audiences — intended, but only
after C proves the interaction (same demotion discipline RFC-002 applied to
file-export).

**Phase E — scoping context.** The budget water-line: a cut report
(dependency-closed greedy cut at a per-invocation budget, membership-stability
band rendered explicitly) and the scoping decision context wired into the
queue, including cross-domain nomination (estimate-refinement questions
ranked alongside comparisons). **Entry criterion** (RV-260 F-5): a formal
estimate feasible-region model — what an answer constrains over
`(lower, upper)` and what the hypothetical answer space is for a range
refinement — designed and reviewed before this phase opens; without it,
cross-domain yield ranking stays out and estimate questions remain
curator-surfaced. Requires the estimate domain, so it rides after that
extension lands.

Sequencing: A → B → C strict (each consumes the previous); D piggybacks any
time after B. A was small and has shipped; **B is the load-bearing design
risk** (the review is right that it is not small); C carries the algorithmic
risk (question selection quality), is gated on B's empirical evaluation, and
can ship with the queue head as selector. The **estimate domain** (team-facing comparative sizing, records
included) is a sibling extension riding the same ledger and machinery —
sequenced after C proves the value path, as its own slice batch: est-domain
constraint semantics (`est_cost` ordering, range projection) and elicit
frames. Phase E follows it.

  determinacy demonstrably stalls? Whenever they land, ratio rows are
  sign-guarded per the T1 domain contract (admissible only where both sides'
  feasible regions are provably positive — RV-260 F-1).
