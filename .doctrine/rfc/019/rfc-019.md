# RFC-019: Comparison-based value elicitation

## Context

`partial-order.md` (repo root, currently untracked) proposes a prioritisation
model built on **pairwise comparative judgement**: instead of asking
stakeholders to assign absolute scores to backlog items, the system presents
carefully chosen two-way comparisons ("if effort were equal, which matters more
for the next release?"), accumulates the answers as evidence, and combines the
inferred value model with engineering estimates, dependencies, and sequencing
preferences to recommend a delivery order. Its pitch rests on a well-supported
observation: humans produce more reliable *relative* judgements than *absolute*
ones, and a planning tool should ask for the cheap, reliable kind.

This RFC evaluates that proposal against the priority engine doctrine already
has — the actionability graph and multi-dimensional score (ADR-015), gating
(ADR-017), value-burndown (ADR-018), and the facet surfaces shipped under the
RFC-001/RFC-002 consumption-surfaces program — and sketches an implementation
path for the parts that are genuinely new.

### What the proposal asks for, decomposed

1. **Separation of forces.** Dependencies ≠ recommended sequencing ≠
   stakeholder value ≠ effort ≠ combined priority; each is kept distinct and
   priority is the derived combination.
2. **Partial information preserved.** Absent or rough data degrades the
   recommendation gracefully instead of blocking it; the model survives new
   items and new dependencies without a re-plan.
3. **Comparative elicitation.** Value is captured through pairwise choices,
   not absolute scores.
4. **Inference.** Accumulated comparisons produce a value model over items —
   a partial order that firms up as evidence accumulates.
5. **Active question selection.** The system chooses the next most informative
   comparison, minimising the number of decisions demanded of stakeholders.
6. **Tension surfacing.** Where the value order and the sensible delivery
   order disagree ("you value A more, but B is small and unblocking — do B
   first"), the disagreement is presented, not silently resolved.
7. **Audit trail.** When the order changes, the evidence that changed it is
   inspectable.
8. **Stakeholder-facing UX.** Sessions, framing lenses ("business value",
   "pain to lose from release", "strategic goal"), context shown per option.

## Discussion

### What the existing engine already delivers

Items 1 and 2 are not gaps — they are load-bearing design commitments of the
current engine, and the proposal's "how it differs from a normal backlog"
section describes doctrine's model almost exactly:

| Proposal force | Existing seam |
|---|---|
| Dependencies ("must happen before") | `needs` dep edges — gating (`blocked_by`), recursive leverage credit (ADR-015 §3), record-gating (ADR-017) |
| Recommended sequencing ("sensible earlier") | `after` seq edges — structural precedence, deliberately **not** a score weight (ADR-015 §3) |
| Stakeholder value | `value` facet (single finite f64 magnitude) → `value_dim` |
| Engineering effort + uncertainty | `estimate` facet — a **range** `[lower, upper]` with skew β; bare items anchor to `max_upper + margin` (ADR-015 §1) |
| Combined priority | derived `score = value_dim + risk_dim + leverage + optionality`, minus value-burndown (ADR-018 §4); never authored to disk |
| Graceful partial information | absent facets collapse to identities/floors, not errors (ADR-015 §1) |
| Sequencing recommendation surface | `next` (actionable frontier, seq-precedence-aware), `survey`, `blockers` |
| Explainability | `explain` — full `{base, value_dim, risk_dim, leverage, optionality, total}` breakdown |

Item 6 (tension surfacing) is *mostly* present: the value/effort tension the
proposal wants surfaced is exactly what `value_dim = value / est_cost` computes
— a small cheap item with moderate value can outrank a large high-value one,
and `explain` decomposes why. What is missing is the narrative form ("B first,
A remains the higher-value initiative") rather than the mechanism.

Item 7 (audit trail) is partial: facets, relations, and config are authored
and diffable, so *what* changed is in git history; but there is no provenance
for *why* `value = 7.0` — the number arrives by fiat. IDE-013
(estimate/value change history) is the existing backlog sibling for this gap.

### What is genuinely new

Items 3, 4, 5, and 8 have no counterpart in the corpus:

- Nothing captures a **comparative judgement** as evidence. Value is authored
  as an absolute scalar via `doctrine value set <ID> <MAGNITUDE>` — precisely
  the "abstract judgement made too early" the proposal argues against.
- Nothing **infers** value from evidence. The scalar is hand-set, take it or
  leave it.
- Nothing **selects questions**. The operator decides what to value and when.
- There is no stakeholder-facing surface at all; doctrine's audience is agents
  and the operating human, via CLI (plus the read-only map explorer).

So the honest evaluation is: **the proposal is not a rival sequencing engine —
it is a missing elicitation front-end for the `value` facet, plus provenance.**
The downstream machinery it envisions (combine value with effort ranges,
dependencies, sequencing hints; keep partial information alive; explain the
result) already exists and is governed. Rebuilding any of it would violate the
no-parallel-implementation rule. Conversely, dismissing the proposal as
"already built" would miss that the *capture* side is the weakest link in the
current value pipeline: garbage-in scalar values are the least defensible input
the score formula consumes. In RFC-001's terms this is a **capture surface**
gap — the mirror image of the consumption-surface gaps that program closed.

### Design tensions

**T1 — ordinal evidence, cardinal consumer.** Comparisons yield ordinal
information (a partial order); `value_dim` needs a cardinal magnitude to divide
by `est_cost`. Two bridges exist:

- *(a) Latent-scale fit.* Treat comparisons as Bradley–Terry / Thurstone
  observations and fit latent strengths; map the fitted scale into value
  magnitudes. Pure, deterministic (BT via minorisation–maximisation converges;
  fixed iteration/tolerance gives reproducible output), handles intransitive
  evidence gracefully (it is evidence, not constraint — a preference cycle
  just flattens the fitted gap rather than crashing a toposort), and yields
  calibrated *gaps*, not just order.
- *(b) Structural partial order.* Keep comparisons as ordering constraints
  that clamp or reorder the score-sorted surface directly. Rejected as the
  primary bridge: it collides with ADR-015's settled posture that structure
  wins only for seq edges and weighted ordering fills the silence; it cannot
  express *how much* more valuable; and intransitive human answers become
  hard errors instead of soft evidence.

Recommendation: (a). Doctrine's value magnitude is an unbounded f64, so a
fitted scale maps without ceremony.

**T2 — where comparisons live.** Three candidate homes:

- *Relation edge* (`A preferred_over B`): tempting, wrong. A comparison is not
  a durable semantic relation between the two items — it is contextual
  evidence (who judged, when, under which lens/framing), it is many-per-pair,
  and it must not enter the relation graph where the consequence pass and
  `inspect` would see it. ADR-016's own test (does the distinction change
  structure/graph-effect/inbound semantics?) says this is not relation
  vocabulary at all.
- *Per-entity facet rows*: a comparison has two subjects; storing it under
  either entity fabricates an owner and splits the pair's evidence.
- *Corpus-level append-only ledger* (authored tier, committed): e.g.
  `.doctrine/value/comparisons.toml`, one row per judgement —
  `{a, b, preferred, lens, rater, note, date}`. Append-only matches the
  evidence semantics (later judgements supersede by recency weighting or
  simply accumulate; nothing is edited in place). This is the recommended
  home. Storage-rule fit: the ledger is authored evidence; the fitted values
  are **derived at read time** (pure function over ledger + config), exactly
  parallel to ADR-015's "no score is authored to disk".

**T3 — two sources of value.** Once fitted values exist, an item may have an
authored `value` magnitude, a fitted value, both, or neither. Resolution
options:

- *(a) Fitted fills absent.* Authored magnitude wins where present; fitted
  value supplies items that have comparison evidence but no authored value;
  items with neither keep the existing absent-value identity
  (`value_dim = 0`). Anchoring: authored-valued items that participate in
  comparisons pin the fitted scale to the existing magnitude range (the fit
  becomes a constrained regression). Cheapest to reason about; preserves the
  operator's explicit override lever (the spirit of RFC-001 surface (d)'s
  authored-pin).
- *(b) Fitted always wins when evidence exists.* Makes elicitation the
  authoritative channel; demotes `value set` to a seeding verb. Bolder,
  arguably purer, but removes the direct override and makes one stray
  comparison perturb deliberately-set values.
- *(c) Blend.* A confidence-weighted mix. Rejected: opaque, and `explain`
  would need to expose a fourth-order breakdown to stay honest.

Recommendation: (a), with `explain` labelling the source
(`value: 6.2 (fitted, 9 comparisons)` vs `value: 8.0 (authored)`).

**T4 — audience mismatch.** The proposal's stakeholder sessions, framing
prompts, and per-option context cards are a product surface for humans who are
not doctrine operators. Doctrine's delivery order for that kind of surface is
settled by precedent: CLI verb first (agent/operator usable immediately),
web/map surface later if the interactive mode earns it (as `map serve` did for
graph viz). The elicitation *session* — show pair, capture answer, pick next
pair — is CLI-shaped enough to be useful long before any web UI exists, and an
agent can mediate a stakeholder conversation through it (the "structured
planning conversation, mediated by software" the proposal wants, with the
agent as facilitator).

**T5 — lenses.** The proposal's alternative framings ("business value" vs
"pain to lose" vs "strategic goal") are, in modelling terms, *dimensions of
value*. The current engine has exactly one value axis. Folding multi-lens
elicitation into one fitted scale discards the distinction the lens was meant
to expose; modelling N value dimensions is a much larger change to ADR-015's
formula. Recommended posture: record the lens on the ledger row (cheap, keeps
the evidence honest) but fit a single scale initially, treating lens as
metadata. A future RFC can revisit multi-dimensional value if lens-tagged
evidence demonstrably diverges — the data to check will exist because we
recorded it.

**T6 — staleness.** Items change after judgements about them were made; the
proposal itself warns comparisons are only as good as the item descriptions
compared. Options: decay by age, invalidate on entity edit, or surface-only
("evidence predates last edit" flag in explain/elicit). Recommend
surface-only initially — decay/invalidation policy is tuning, not structure,
and can ride the config section later.

### Fit with backlog and governance

- **IDE-013** (estimate/value change history): the ledger *is* a value
  history for compared items; IDE-013 remains open for estimate drift but
  should be linked so neither effort duplicates the other.
- **IMP-021** (risk-facet backlog sort), **IMP-120** (transitive impact),
  **IMP-109** (catalog single-read): orthogonal; no interaction beyond the
  usual scan seams.
- **RFC-001 / RFC-002**: this is the capture-side sibling of the
  consumption-surfaces program; RFC-001's surface (d) note flags the
  authored-pin override as unverified — T3(a) deliberately keeps authored
  value as that override.
- **ADR-015** would need an amendment (or a small successor ADR) for the
  value-source resolution policy (T3) and the `[priority.value_fit]` config
  domain — the score formula's *input* changes provenance; the formula itself
  does not change. ADR-004 is untouched (no relation storage). ADR-001
  layering: fit lives beside scoring in the engine tier (`src/priority/` or a
  sibling `src/value/` module), pure over `(ledger, config, anchors)`.

### Implementation path

Slice-sized phases, strictly additive, each independently shippable:

**Phase A — capture.** Ledger schema + verbs:
`doctrine value compare <A> <B> --prefer <A|B> [--lens L] [--by RATER]
[--note ...]`, plus `doctrine value comparisons [<ID>]` to list evidence.
Append-only authored file under `.doctrine/`; schema versioned like other
doctrine TOML. No scoring change — pure capture. (Verb naming rides the
existing `value` noun; final shapes at design time, per CLI-is-source-of-truth.)

**Phase B — fit + resolution.** Pure Bradley–Terry fit (deterministic MM,
fixed tolerance; ties/lens as metadata), anchored regression against
authored-valued participants (T3a), wired as a pre-pass beside the existing
base pre-pass: scan reads the ledger once (impure seam), fit is pure, fitted
magnitudes flow into `value_dim` under the source-resolution rule. `explain`
gains the value-source line. ADR-015 amendment lands here. Determinism tests
mirror the existing no-NaN/total-order suite.

**Phase C — elicitation.** `doctrine value elicit [--lens L]`: propose the
next most informative pair — maximise expected information (closest fitted
strengths × fewest observations; un-compared items enter by binary insertion
against the fitted median), render the two items with enough context to
choose (title, body summary, deps, risk), accept the answer, append to
ledger. This is the "minimum decisions" property; selection is a pure
function over (fit, ledger).

**Phase D — tension narrative + session surface.** Extend `next`/`explain`
with the value-rank vs delivery-rank disagreement callout ("SL-x outranks
SL-y on value; SL-y is cheaper and unblocking — surfaces first"). Optional
later: session mode / web surface, only if C proves the interaction and an
external-stakeholder need materialises (same demotion discipline RFC-002
applied to file-export).

Sequencing: A → B → C strict (each consumes the previous); D piggybacks any
time after B. A and B are small; C carries the only interesting algorithmic
risk (question selection quality) and can ship with a naive selector first.

### Rejected framings

- **Replace the score with a pure partial order.** Throws away the working
  cardinal engine (leverage, burndown, risk, est_cost) for a strictly less
  informative structure; contradicts ADR-015 wholesale.
- **Comparisons as relations.** See T2 — wrong tier, pollutes the graph.
- **Stakeholder web UI first.** Inverts the project's proven surface order;
  builds the most speculative layer before the evidence pipeline exists.
- **Do nothing (proposal is redundant).** False: the capture-side gap is real
  and the current absolute-scalar elicitation is the weakest input the engine
  consumes.

## Outcome

Open. Position taken by this RFC:

1. The proposal's sequencing model is **already implemented** by the
   actionability graph + ADR-015 score; no second engine.
2. Its durable contribution is **comparative value elicitation**: an
   append-only comparison ledger (authored evidence), a deterministic
   Bradley–Terry fit (derived, read-time), source-resolution where authored
   value wins and fitted fills absence, and an active question-selection verb.
3. Path: Phases A–D above; ADR-015 amendment at Phase B; slices to follow
   acceptance of this RFC.

Open questions:

- **OQ-1** Multi-rater policy: aggregate all raters into one fit, or
  per-rater fits with disagreement surfaced? (Initial lean: one fit, rater as
  metadata; disagreement is a later report.)
- **OQ-2** Scale anchoring when *no* compared item has an authored value —
  fitted scale needs an arbitrary gauge (e.g. median → 1.0); acceptable?
- **OQ-3** Ledger location and name (`.doctrine/value/comparisons.toml` vs a
  facet-adjacent home); one file vs sharded — concurrency with multiple
  agents appending.
- **OQ-4** Does `value compare` accept records/governance kinds, or
  work-kinds only (backlog + SL) initially?
- **OQ-5** Staleness surfacing threshold (T6) — flag on any post-judgement
  edit, or body-content edits only?
