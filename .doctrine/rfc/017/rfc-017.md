# RFC-017: Human onboarding docs: tour, quickstart, mental model

## Context

Doctrine's written corpus is large but almost entirely aimed at **agents**
(shipped memories, skills, the boot snapshot, glossary, using-doctrine) or at
the **author** (ADRs, RFCs, specs). There is no human-facing on-ramp: a
newcomer meets a complex knot of opinions, concepts, and procedures with no
graded path in. The memory corpus is now browsable via the web interface,
which helps — but it is agent-voiced reference, not an introduction.

The reframe that bounds the work: doctrine's UX is **agent-mediated**. A new
user does not read documentation and then drive the CLI; they install, and
their agent carries the *how* (memories, skills, boot). Humans therefore need
exactly three things: **why this exists**, **the mental model** (enough to
supervise an agent and not fight the process), and **a credible path to first
success**. That is a small, finite doc set — not an open-ended documentation
programme.

In Diátaxis terms the corpus today has *reference* (glossary, using-doctrine —
agent-voiced) and *explanation* (ADRs/RFCs — deep, author-voiced), but **no
tutorial and no human-voiced orientation**. This RFC deliberates the shape of
that missing set.

## Discussion

### The doc set — five artifacts, in priority order

1. **Positioning paragraph** (30-second audience). One paragraph at the top of
   the README saying what doctrine is and why anyone should care, anchored by
   the one sentence only this project can write: *this codebase's own slices
   are designed, adversarially reviewed, executed, and audited by agents under
   this system — the ledgers are in the repo.* Candidate one-liner: "agentic
   development, with receipts."

2. **The Tour** (10-minute audience) — the centerpiece. An **annotated real
   slice**, end to end: scope → design → an external adversarial review that
   *visibly changed the design* → phases → audit → close. SL-199 is a strong
   candidate once closed: the review findings forcing design revisions are
   recorded in-line in the design doc — a real reviewer catching real flaws,
   in the artifact. Editing, not authoring: the material exists; the work is
   narration for a reader without the lore. The repo is its own case study;
   no abstract description of the process competes with a walk through a real
   artifact chain.

3. **Quickstart** (afternoon audience). `doctrine install` → first governed
   slice on the reader's own repo. Honest prerequisites (which harnesses, what
   works without the jail). Authored as an **acceptance test**, not just prose:
   the *zero-lore stranger test* — a fresh human + fresh agent in a clean repo
   complete the quickstart with no knowledge beyond the doc. Every point where
   the doc must say "you also need to know…" is a product gap, filed as
   backlog. (Human twin of RFC-016's memory-blind orchestrator test; the
   RFC-011 orientation work and the onboarding-a-stranger work are largely the
   same work.)

4. **"How doctrine thinks"** (mental-model page, ~5 short sections). The
   recurring invariants (mechanism over prose; report-and-halt; evidence
   immutable, intent journaled; trust nothing, belts server-side; knowledge
   trails confirmed code), the four pillars, the work/knowledge/decision
   boundary, storage tiers. Adapted from using-doctrine/glossary — a
   human-voiced layer that *links into* the existing corpus rather than
   duplicating it. The web memory interface wants a curated "start here"
   trail for the same reason: raw corpus exposure is reference, not
   orientation.

5. **FAQ / objections.** "Isn't this heavyweight?" — answered with RFC-011's
   measured numbers, not assertion; "which harnesses work?"; "can I use just
   the memory system?"; "why GPL?". Objections answered with receipts read as
   honest; the doc exists to pre-empt the predictable first questions.

### Method

- **Mine, don't author.** ADR/RFC discussion sections, the memory corpus, and
  using-doctrine already contain most of the raw content. The new writing is
  narration and sequencing for a lore-free reader.
- **Stranger-test cheaply.** Fresh clone, empty target repo, fresh agent
  session, author role-playing a newcomer; then one or two friendly outsiders.
  Each stall → backlog item. The test is repeatable after every install/skill
  change.
- **Govern under doctrine.** A docs slice (or a small spec for the doc set if
  it stabilises into durable product surface). Dogfooding the doc work
  generates Tour material as a by-product.
- **Placement.** In-repo `docs/` + a lean README that leads with the
  positioning paragraph and links the set. In-repo because the repo is where
  a newcomer actually lands; anything published elsewhere can source from it.

### Alternatives considered

- **Expose the memory corpus harder (web UI as the docs).** Rejected as the
  primary answer: agent-voiced reference material presumes the mental model
  it should be teaching. The web UI is a complement (deep-link target), not
  an on-ramp.
- **Comprehensive manual.** Rejected: the agent-mediated reframe makes most
  of a manual redundant (agents carry the how), and the maintenance burden
  would compete with the CLI's source-of-truth discipline (`--help` and the
  reference docs already own command truth).
- **Screencast/video tour.** Deferred: rots faster than an annotated artifact
  chain, and the artifact chain is the differentiator.

## Outcome

**Open.** Direction proposed; for the descending slice(s):

- **OQ-1** — Tour subject: which closed slice best shows the full chain with a
  visible review-changed-the-design beat (SL-199 candidate; needs to be closed
  and representative, not just dramatic).
- **OQ-2** — Tour format: single long annotated page vs stage-per-page;
  how much artifact text is inlined vs linked (`doctrine show` output vs
  raw prose excerpts).
- **OQ-3** — Quickstart's honest floor: what is the minimum viable environment
  (harness × platform × no-jail) the doc commits to supporting, and what does
  install need to do better to keep the doc short (gaps → backlog).
- **OQ-4** — Stranger-test protocol: scripted scenario, pass/fail criteria,
  cadence (per release? after skill changes?), and where results are recorded.
- **OQ-5** — Mental-model page ownership: standalone doc vs promotion into
  using-doctrine as a human-voiced preface; avoid a second competing
  explanation tier.
- **OQ-6** — Web memory interface: what a curated "start here" trail needs
  from the corpus (a tag? an ordered signpost chain?) without forking the
  memory model.
- **OQ-7** — README restructure: what moves out to `docs/` so the README can
  lead with positioning + Tour link without losing the contributor-facing
  content.
