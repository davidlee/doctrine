# RFC-031: Design run fitness

## Context

<!-- The forces at play: the problem, the question, and why it merits structured
     discussion. An RFC asserts NO canon — it is governance-neutral deliberation. -->

The managed design run (`doctrine design start|apply|resume|materialise`; engine
specified by `SPEC-029`, built by `SL-233`) is not yet fit for daily use. Since it
shipped it has cost more attention than it has saved. This RFC is the **program
home** for making it work well: what is wrong, in what order to fix it, and how
we will know it is fixed.

**Refreshed 2026-09-25.** The picture has moved since this RFC was minted: twelve
runs now reach `locked`, most of them ordinary slices. The state section, one new
force in the diagnosis, one new fitness measure and a recorded operator position
are the changes; the tracks keep their order.

It is deliberately *not* `RFC-026` (*Design review response effectiveness*),
which studies the review/response process and uses the design run as its
instrument, and *not* `RFC-030` (*Inquiry map as a general interview substrate*),
which deliberates one component's purpose. Both feed this program; neither is it.

**Supersedes a prior assessment.** On 2026-08-15 the cluster was judged to need no
RFC — "~22 of 27 items are conformance work and want slices". The slices came
(`SL-251`, `SL-256`) but the cluster kept growing (~27 → ~38 open) and the runs
kept stalling. What is missing is not deliberation per item but a single place
holding **order, rationale and a fitness bar**.

### State on 2026-09-25

Seventeen runs exist in this repo's corpus; twelve reached `locked`. Source is
`.doctrine/state/slice/*/design.toml` via `doctrine design show --format status`.

| slice | run | note |
|---|---|---|
| `SL-243` | drafting, rev 28 | parked since 2026-08; the `E8.3` subject (9 nodes, 0 edges) |
| `SL-253` | reviewing, rev 83 | 1 blocker + 1 major outstanding |
| `SL-258` | exploring, rev 8 | 14 nodes, 12 open, **13 blocked, frontier empty**; stalled since 2026-08-17 |
| `SL-247`, `SL-252` | abandoned | rev 24 / rev 26 |
| `SL-244`..`SL-246`, `SL-249`, `SL-250`, `SL-251`, `SL-256`, `SL-259`..`SL-263` | locked | 12 runs |

Three observations the 2026-09-11 snapshot could not make:

- **The locked set is no longer engine-only.** `SL-244` (*Gate conditions carry
their own contract*), `SL-245`, `SL-246`, `SL-249`, `SL-250`, `SL-260`
(*Design-review finding routing*), `SL-261` (*Design adopt verb*), `SL-262`
(*Envelope names the next move*) and `SL-263` are ordinary slices, not engine
repair. `SL-244` was unreadable on 2026-09-11 (`ISS-315`) and now reads at rev 92.
`SL-259` landed in the interval; whether the fleet is its consequence or a
coincidence is not established.
- **The traversal cursor is empty almost everywhere.** Sixteen of seventeen runs
report `cursor unset`; the only exception is `SL-258`, whose cursor sits on a
blocked node. Whatever the map is doing, nothing is steering it (`IMP-389`).
- **The review pass reads `STALE` on eleven of the twelve locked runs**, each with
one change since the declared baseline. Either post-lock out-of-band edits (the
reconcile path) invalidate it, or the invalidation rule is over-broad. The RFC
does not yet know which, and the difference matters for T5.

### Why it has gone badly

Read across the friction observations and `RFC-026` **E8** (the one measurement
of the shipped engine). Forces 1–5 were read on 2026-09-11; force 6 is new.

1. **The exit signal lies.** `apply` reports success for input it ignored
   (unknown keys, inert acts, wrong-stage acts) and — reportedly — failure for
   state that moved. An agent cannot drive a state machine whose transitions it
   cannot observe. Every other problem is amplified by this one. *Moved:*
   `SL-259` (*Truthful apply*) landed; `ISS-481` (`needs: null` silently no-ops)
   is its residue.
2. **The contract is discovered by reading source.** E8.7: 0.63 source reads per
   engine call, 15 of 33 for payload shape; one agent read `tests.rs` to learn how
   to clear a gate. `SL-251` made payload contracts fetchable; gate conditions,
   next obligation and node text are still not surfaced (`IMP-390`, `ISS-298`).
3. **Editing prose is disproportionately expensive.** Section bodies move whole
   (~90 KB payload to change a paragraph, `IMP-430`); re-adopting a hand-edited
   `design.md` needs full section fingerprints that no verb emits (`ISS-320`,
   `ISS-348`) — the single most-reported friction.
4. **Machinery shipped ahead of use.** The inquiry map's edge kinds shipped with
   full render support; E8.3 measured nine nodes and zero edges over seventeen
   revisions. Nothing puts the map in front of the user (`ISS-299`).
5. **Stored state outlives the binary** (`mem.fact.design-run.snapshot-outlives-the-binary`)
   and the engine was not written as though it did — so every strictness fix
   trades against reading live runs (`QUE-219`).
6. **Gate invalidation punishes discovery.** The two cumulative conditions bound
   to the inquiry map (`initial-concerns-recorded`, `user-accepts-sufficiency`)
   re-derive on any *shape* change, so adding a node or an edge after the map has
   been accepted voids both and re-faces the human gates — while `DEC-062` says
   map maintenance "does not require human approval". The cheapest strategy is to
   front-load the map and never touch its shape again, which is what runs do.
   Progress (resolving, reopening) is already exempt; shape is not.
   (`IMP-469`; the intent is unwritten — `IMP-471`.)

## Discussion

### Principle: use-driven, measured per step

Each track below lands as a slice, and each slice's close is followed by use on a
real (non-engine) design run before the next track's priority is re-judged. The
failure mode to avoid is the one that produced point 4: building from the backlog
rather than from observed use.

### Fitness bar — what "working well" means

Measured on a real slice's design run, start to `locked`, after a track lands:

| measure | baseline | target |
|---|---|---|
| source reads of `src/design_run/**` / prompt assets per engine call | 0.63 (E8.7) | ~0 |
| submissions that succeed but change nothing, or fail but change something | observed, uncounted | 0 by construction |
| payload bytes to change one paragraph of one section | ~90 KB | proportional to the delta |
| refused submissions per run spent on contract discovery | several per session | rare; each refusal names the fix |
| existing runs readable by the current binary | 5 of 6 | all |
| inquiry nodes/edges added after `user-accepts-sufficiency` | 0 — and each one voids the accepted judgement | ≥ 1, without voiding it |

The bar is the RFC's exit: when a run meets it, this RFC resolves and the
remaining cluster is ordinary backlog.

### Tracks, in priority order

Membership is judgement and lives here; **status is never recorded here** — query
it (`doctrine backlog list -t cluster:design-run`, `doctrine inspect RFC-031`).

**T1 — Truthful apply.** `SL-259`. Error ⇒ nothing landed; success ⇒ rows that
tell the truth; unknown or inert input ⇒ typed refusal; old snapshots readable.
Settles `QUE-219` as its first decision. Items: `ISS-315`, `ISS-333`, `ISS-328`,
`ISS-327`, `ISS-290`, `ISS-362`, `ISS-367`, `ISS-361`. *First because* every other
track's measurement depends on an honest exit signal. Post-`SL-259` residue:
`ISS-481`.

**T2 — Section edit loop.** `ISS-320` (dup `ISS-348`), `IMP-430`, `ISS-356`,
`ISS-320`'s question *is the section map adding information at all?* *Second
because* it is the most-reported friction and the dominant token cost per revision.

**T3 — Contract legibility, residue.** `IMP-390` (the three candidates `SL-251`
left: next obligation, gate conditions, what is accepted), `ISS-298`, `ISS-360`,
`ISS-282`, node-question text on a CLI surface, `CHR-067`.

**T4 — Map surfaced, then made live.** `ISS-299` → `CHR-065` (re-measure) →
settle `QUE-218`. Only then the semantic tier (`IMP-386`..`IMP-389`) or its
retirement. `ISS-300`, `ISS-303` are ungated correctness fixes here. The map's
*dynamic mode* is now a positive goal rather than a judged hypothesis: `IMP-470`
(the runbook obligation, cheapest lever), `IMP-469` (shape change must not void
cumulative attested conditions), and `IMP-471` (the intent is unwritten at
requirement tier; gated on `QUE-218`).

Two axes must not be conflated: `IMP-386` wants *more* propagation, backwards (a
changed answer flags its dependents); `IMP-469` wants *less*, forwards (a new node
must not void the human's sufficiency judgement). A cascade that ignores the
distinction makes the second worse. Coordinate with `RFC-030`, whose thesis may
reshape the map before T4 builds on it.

**T5 — Review integration.** `IMP-392` (findings onto the `RV` ledger; `DEC-125`),
`ISS-357`, `ISS-359`, `ISS-310`. The `SL-256` run's empty self-minted `RV` is the
motivating sighting.

**T6 — Durability and engine quality.** `IMP-412`, `IMP-366`, and test seams
`IMP-364` (dup `IMP-357`), `IMP-368`, `IMP-399`, `IMP-373`. Opportunistic —
ride other tracks' slices where they touch the same code.

### Position (2026-09-25): the map is meant to be live

Recorded at the operator's direction. `RFC-030` describes the inquiry map as a
*mutable graph* and `DEC-061` permits nodes to be added as discoveries become
concrete, yet the runbook never asks for growth (`IMP-470`) and the gate design
actively discourages it (`IMP-469`). The recorded position:

- the map is meant to grow and be re-edged over the course of a run; a *change of
  shape* should not require re-attesting the human's judgements about it —
  derived coverage should still react to it, attested judgement should not;
- the cheapest lever is prose (`IMP-470`), and it should be spent before any
  machinery;
- the intent is not written down at requirement tier at all (`IMP-471`), which is
  why every candidate fix is guessing.

This does not reorder the tracks. T1 and T2 still come first: a run cannot be
measured honestly until its exit signal tells the truth and its prose loop is
affordable.

### Open: repair or reduce?

Every track above repairs. The alternative is to cut: retire engine surface that
no run has used (parts of the runbook set mode, the attestation roster) so there
is less to make truthful and legible. The 2026-09-25 position weakens this for the
map specifically — its growth path is now *wanted*, not merely unproven, so T4's
judgement is about how to make it live rather than whether to keep it. The
question more broadly should be answered after T1 and T2, when a run can be
measured honestly.
