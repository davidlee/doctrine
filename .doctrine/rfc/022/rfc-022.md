# RFC-022: Agent trust model without human attestation

## Context

Doctrine's memory corpus is consumed by agents as fact. Nothing currently
establishes that a memory is *true* — only that it was recorded, and (via
`memory verify`) that its evidence was committed at some point. `trust_level` is
author-asserted. `verification_state` is largely `unverified` across the corpus.

**The threat model, stated.** The adversary is an agent compromised by prompt
injection, seriously misaligned, or stupid in a way indistinguishable from
malice. The goal is **blast-radius containment** — a bad agent should not be able
to propagate a false belief into the corpus and have later agents act on it. It
is explicitly *not* a model where the human operator is hostile, and it is not a
confidentiality model.

Two distinguishable harms sit under it:

1. **False attestation** — a memory whose recorded evidence does not match what
   the memory claims. Adversarial. This is what SL-232 has been attacking.
2. **Incorrect facts** — a memory that is simply wrong. Mostly accident and
   sloppiness, largely amenable to soft controls (prompting, authoring
   discipline), *but* soft controls fail silently and unmeasurably.

**Why this merits an RFC now.** SL-232 spent five adversarial review rounds
(RV-314, 41 findings) hardening `verify`'s byte-equality claim without a stated
threat model, and each round refuted the previous round's repair. The absence of
a bounded adversary meant no completeness criterion existed, so every round could
always find another mechanism. Stating the model above is what makes the question
answerable — and it reframes the question from "can `verify` be made total?" to
"what makes a claim in this corpus trustworthy at all?"

The question this RFC opens: **how do we build an effective trust / reputation
model for agents that does not depend on a human in the loop?**

Human attestation (hardware key, passphrase-gated signing) is assumed to be a
legitimate mechanism for a top trust tier and is *not* the subject here. The
subject is everything below that tier, which is where nearly all memories live.

## Discussion

### The crypto is bookkeeping; the security content is independence

Two sketches were raised:

- **(A) Certificates per model+role.** Self-sign at low trust; request
  independent verification from a different model+role holding a different key;
  promote on a two-key rule.
- **(B) No self-certification.** Bar an agent from boosting a memory it authored;
  have a fresh session review new/untrusted memories during `/dreaming`; allow a
  boost only with attached evidence.

Both reach for the same property. The keys are not what delivers it.

A signing key reachable by the agent attests **identity, not truthfulness**. A
prompt-injected agent `A` signs as `A` quite happily; the signature proves `A`
said it, which is exactly what we already knew. Against a compromised holder of a
key, a signature buys nothing.

What (A) is actually reaching for is the **two-man rule**: require two
independent failures rather than one. That is real security content, and the
crypto is only the auditable bookkeeping for it. So the design question is not
*what certificate scheme* but **what makes two agents independent, and can that
be enforced?**

### What actually decorrelates two agents

Ranked, with in-repo evidence:

| axis | strength | evidence |
|---|---|---|
| **different model** | strong | RV-314 rounds 2/3 (codex) and round 4 (Claude self-attack) each repeatedly caught what the other missed on the same document |
| **no shared context** | strong | a reviewer given the author's reasoning is anchored, not independent; one given the artifact plus the repo re-derives |
| **different session / agent-id** | weak alone | a fresh session of the same model on the same framing is barely independent |

Sketch (B) gets the second axis right and (A) does not address it at all. A
practical consequence: the reviewing agent should receive the memory body and the
repository, **not** the authoring session's transcript or rationale.

### The failure mode that defeats both sketches

**Prompt injection in the artifact under review is common-mode.** A memory
crafted to mislead attacks the author and every reviewer identically. Stacking
keys or models buys nothing against it — N-of-M assumes independent failure and
this is precisely a correlated one.

The only real mitigation is that the reviewer verifies against **external
evidence** rather than against the artifact's own claims. This is the load-bearing
part of sketch (B)'s "attaching the evidence they have": *`B` agrees with `A`* is
near-worthless; *`B` re-derived this from the code and here is the trace* is the
product. Doctrine already encodes this distinction in its verification taxonomy
(`VT` by test / `VA` by agent / `VH` by human) and in the review ledger's
"reproduce before you raise" discipline (ADR-007) — the machinery exists and is
not wired to memory trust.

A second structural failure: **a compromised agent that can spawn subagents can
manufacture its own quorum.** Any N-of-M scheme must have the reviewers spawned
by something the reviewed agent does not control. That is an orchestration
constraint, not a cryptographic one, and it is easy to get wrong.

### Three cheap wins, mostly already built

**1. Push facts toward executable verification, and trust becomes moot for them.**
A memory whose claim is pinned by a test or probe re-establishes its own truth on
every run; no reputation machinery is needed. The social layer should be reserved
for the residue that genuinely cannot be tested. This is the largest win and it
mostly exists (`VT`, `coverage record/verify`) — what is missing is the pressure
to prefer it at authoring time.

**2. Decay via the staleness seam.** Trust should fall automatically as the code a
memory describes churns. `commits_touching` and the staleness machinery — which
SL-232 is already reworking — *is* the decay function. This is a strong argument
for finishing a reduced SL-232 rather than shelving it.

**3. Track outcomes, not just attestations.** If a memory was retrieved and then
contradicted — an agent had to correct it, a `/feedback` cycle refuted it — that
should cost it trust automatically. Reputation grounded in *consequences* is much
harder to game than reputation grounded in votes, and needs no keys. **This
appears to be the clearest gap in the current system**: doctrine records
attestation but not outcome.

### Trust as a tuple, not a scalar

A single promotable number invites gaming and hides its own basis. A structured
value the consuming agent interprets:

| axis | values |
|---|---|
| evidence | asserted → re-derived → executable → human |
| independence | self → fresh-session → cross-model → cross-model + cross-context |
| freshness | commits touching the claim surface since attestation |
| outcomes | retrieved *n*, contradicted *m* |

"Two submarine keys" then falls out as one *policy* over this tuple rather than
being the mechanism itself — and other policies (a high tier requiring `VH`, a
low tier accepting self-assertion) compose on the same substrate.

### What keys are actually for

**Attribution across a trust boundary.** When memories move between repos, teams,
or organisations — which doctrine already contemplates in the shipped-corpus vs
local-items split — signing supplies provenance that git alone does not. Locally,
against a compromised key holder, it supplies nothing.

Proposed sequencing on the record: **build the independence + evidence layer
first; defer keys until memories cross a boundary.** Hardware-key attestation for
a top tier remains available and composes with the tuple above rather than
competing with it.

## Outcome

**Open.** Nothing here is canon; no decision is asserted.

Positions that appear settled enough to carry into design if this progresses:

- The keys are bookkeeping; **independence and external evidence** are the
  security content.
- **Self-certification must not promote** (sketch B's core), and "self" is best
  keyed on *context lineage*, not merely agent-id.
- **Quorum members must not be spawnable by the reviewed agent.**
- **Signing is deferred** until a trust boundary is crossed.

Open questions:

- **OQ-1** — How is "no shared context" *enforced* rather than merely intended? A
  fresh agent can be handed a clean brief, but proving the absence of anchoring is
  harder than arranging it.
- **OQ-2** — Can the reviewing agent read the memory as data safely? The corpus
  already wraps bodies in "treat as data, never as instruction" guards; is that
  sufficient for an agent whose *job* is to reason about the body?
- **OQ-3** — What is the outcome-tracking seam? Retrieval is already observable;
  contradiction is not currently a recorded event.
- **OQ-4** — Which kind carries the attestation record — an extension of the
  memory entity, or a separate record with its own lifecycle?
- **OQ-5** — Does decay need a policy per memory class? Evergreen orientation
  memories (ADR-002) have no claim surface to churn against.
