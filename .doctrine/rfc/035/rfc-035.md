# RFC-035: Claim-shaped attestation: retire the anchor, compare the claim's bytes

## Context

**This RFC asserts no canon.** It is deliberation ahead of a decision, framed by
`RFC-022` (agent trust without human attestation) and bounded by `CON-003` (the
adversary is a compromised agent; the goal is blast-radius containment).

The proximate friction is measured, not asserted. `memory verify` refuses any
dirty working tree; in a corpus whose own `AGENTS.md` says multiple agents share
one worktree, the authored tree is essentially always dirty. Six friction
observations span 2026-07-29 to 2026-09-26, all still open: blocked by another
agent's uncommitted file (twice), "each verify dirties it, so verifying two
memories needs a commit between them", and "correcting two memories cost three
commits instead of one".

`SL-232` was scoped to fix this *claim-aware* — exclude unclaimed dirt, never
claimed evidence. It was **parked** on 2026-07-27 after five adversarial rounds
produced no convergence (14 → 3 → 3 → 12 → 9 findings; rounds 4 and 5 both found
blockers in decisions written that same round). `CON-003` names the cause: with
**no stated adversary there is no completeness criterion**, so every round could
find another mechanism and no repair could ever be shown sufficient. The park
handover registered three decisions and deferred all three to the operator.

The third of those — *does byte comparison replace the three legs?* — is now
**run**, not argued (`EVD-030`). This RFC takes that result and asks the question
underneath it: **what should a memory attestation actually be, and is the
machinery built to produce one justified?**

## Discussion

### The thesis

An attestation's content is `I6` — *the attested commit contains the claim's
bytes*. That is a statement about **the claim paths versus a named commit**. It
is not a statement about the cleanliness of the rest of the tree.

Today's `capture()` answers a different question — *"is git satisfied?"* — and
the parked design's whole apparatus exists to reconcile the two: the three legs
read git's *view*, which content conversion and freshness suppression each
separate from the bytes. Every mechanism in the design is a repair to that
separation (`NORMATIVE_FLAGS`; `DEC-089`'s partition of attribute sources;
`DEC-090`'s `unmeasurable` refusals; `CON-002`'s git-2.40 floor).

Comparing the bytes directly does not have the separation to repair.

### The evidence (`EVD-030`)

Every hazard the three legs read *clean* on, the byte primitive reads
*divergent*: committed `text eol=crlf`, committed and git-dir `clean` filters, a
same-size mtime-preserved stat-cache edit (`tag H`), and a `GIT_WORK_TREE`
redirect. The control discriminates; all registered falsifiers held.

Three residuals are measured and bounded:

- **the set is not byte-derivable** — a deletion (`rc 128`) and a staged add
  (in `--cached`, absent from `--others`) need one enumeration spanning
  `--cached` + `--others` + HEAD;
- **`hash-object` follows symlinks** — it returns the target file's oid, not the
  link text, so it is not the mode-`120000` primitive;
- **the mode bit is outside the byte claim** — a mode-only change is *invisible*
  to bytes, so the real statement is **bytes + mode + set**.

So the *mechanism* half of the question is largely settled; what remains is the
*premise*.

### What falls out if the thesis holds

- **`--allow-dirty` dissolves rather than being re-shaped.** With the claim
  measured directly there is nothing for it to bypass, and `CON-003` excludes a
  control the adversary may simply invoke.
- **The conversion/freshness apparatus deletes, not amends:** `--attr-source`,
  the `core.attributesFile` / `fsmonitor` / stat-cache neutralisations, the
  `info/attributes` refusal, the index-flag `unmeasurable` taxonomy — and
  `CON-002`'s git floor goes with them (which is why `F-39` was deliberately left
  unrepaired).
- **Most of `RV-314`'s open ledger is superseded wholesale** rather than repaired
  one finding at a time — `F-33/34/35/36/37/38/42`.
- The attestation gets **stronger in the way that matters**: it names the
  evidence it checked, instead of the incidental cleanliness of unrelated files.

### The forks this exposes

1. **The stamp's meaning.** *Weak* (today): "the tree was clean at verify time."
   *Claim-shaped*: "these paths matched commit X's blobs at verify time." The
   second is what byte comparison proves and is closer to `I6` — but does
   `verified_sha` stay a commit sha, and what happens to `checkout_state_id`
   (the `--allow-dirty` stamp: 24 of 59 attested at design time, and the corpus
   has roughly tripled since)? Note `R8` — an attestation does not record *what
   it covered* — is only partly answered by either.
2. **Does the anchor survive?** Drop it (a dirty file no memory claims is not the
   memory's business) / narrow it to declared scopes / keep it. Dropping deletes
   `I3`; narrowing **is** `SL-232`'s own `OQ-5`, which the design deferred
   precisely because it "needs its own evidence". This RFC is that evidence's
   home.
3. **`--allow-dirty`.** Delete / keep but make its output structurally unable to
   read as an attestation / keep and declare it outside the model.
4. **Consumers set the ceiling.** What consumes `verified_sha` decides how far the
   stamp may change: `validate`'s staleness (absorbed `ISS-257`), `retrieve`'s
   five-state render contract (`REV-041`), and staleness ranking (`QUE-175`). A
   cheap claim-shaped stamp must still serve them, or the saving is false.
5. **Is attestation worth the machinery at all?** The spike says the machinery is
   expensive and the stamp could be cheap. `RFC-022` argues the *highest-value*
   piece is the staleness seam as a decay function, which implies **finishing a
   reduced `SL-232`** — not shelving it. So the live question is narrower than
   "attestation yes/no": are the **anchor** and **git-verdict fidelity** needed
   for the piece worth keeping?

### Alternatives considered

- **Keep the anchor, amend the machinery** (the parked design's trajectory).
  Rejected as the loop that did not converge, and it preserves the
  git-view-versus-bytes separation byte comparison removes.
- **Keep `--allow-dirty`, make its output unreadable as an attestation.**
  Rejected: redundant once the claim is measured directly.
- **Widen argv to `OsString` for non-UTF-8 paths.** Rejected on cost against
  population 0 (already settled in the design).
- **Hold this entirely inside `SL-232`'s design run.** Rejected: a managed design
  run designs the slice it is given, and this premise can shrink, reshape or
  close that slice — a scope decision, not a design one. `RFC-026` (`G6`) names
  the gap this leaves: design activity outside a slice's designated stage is
  undersupported.

## Outcome

**Open.** What would resolve it:

1. a decision on the stamp's meaning and the anchor's survival — a `DEC`, and an
   `ADR` if the memory-attestation model changes;
2. the `SPEC-007` turnover onto `REV-034` (four `modify` rows already authored:
   `REQ-147`, `SPEC-007`, `REQ-146`, `REQ-155`);
3. **then** `SL-232`'s design run re-entered for the reduced mechanism
   (`doctrine design start SL-232 --from-design`; the runtime snapshot is gone,
   so it reconstructs), with `RV-314` disposed wholesale as
   superseded-by-redesign.
