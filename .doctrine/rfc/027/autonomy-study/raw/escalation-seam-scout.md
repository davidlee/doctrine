# Scout Brief: Incumbent worker→orchestrator signalling seams in doctrine

## Summary

Doctrine's dispatch system deliberately has **no structured worker→orchestrator signal for "anything other than phase done"**. Every write-grade channel a confined worker can reach funnels into exactly one outcome (`Committed`) or one of a closed set of belt **refusals** (`Refused`) — there is no blocked/halt/needs-judgement/question arm. The trusted orchestrator's dispose surface (`dispatch next`, `dispatch next_ready`, the funnel state machine) is a single-prescription machine whose `NextKind` vocabulary is purely `spawn / await-worker / import / verify / triage-verify-failure / reverify-stale / conclude / reap / all-reaped`, plus the phase-sheet `status = "blocked"` that the orchestrator (not the worker) writes via `slice phase`. A worker CAN author a structured record for later harvest — `observation_record` (`friction` only) — because the MCP **server** (unconfined) performs the write at the primary root, though the record lands under the `.doctrine/` floor the worker's own commit belt rejects. The managed design run DOES carry an open-question/blocking-inquiry state (`InquiryLifecycle::Open`/`Deferred` and the engine-derived `blocking-inquiries-dispositioned` gate that pauses `inquiring→drafting`), but answering it requires `design apply`, which is `Write`-classed and **refused under worker-mode** — so only the orchestrator/user answers. There is **no** implemented append-only "admission journal": the funnel record (`FunnelRecord`/`PhaseRow` committed under `funnel.toml` via one CAS writer) and the dispatch `ledger::Journal` are committed ordered records, but neither is an admission journal of worker signals, and the word "admission" in the dispatch corpus names candidate-ledger pinning, not a journal.

## Findings

### Q1 — A worker CANNOT hand back BLOCKED / needs-judgement / question today

The worker-facing commit tool has a two-variant result type only:

- `pub(crate) enum WorkerCommitOutput { Committed { oid, base, undeclared }, Refused { reason, detail } }` (src/mcp_server/worker_commit.rs:58-70). The comment at lines 48-55 states refusals are "a normal `Ok` result carrying its token — NOT a JSON-RPC error — so the worker/orchestrator reads the reason structurally." Every refusal is one of the closed belt tokens: `empty-delta`, `forbidden-zone`, `not-at-base`, `commit-gate-red`, `late-recommit` (worker_commit.rs:31-46), plus resolver tokens like `unknown-agent`, `stale-record`, `unprovable-fork` (worker_commit.rs:395-402, 810-815). There is no `Blocked`/`NeedsJudgement`/`Question` variant.
- **Positive control** for the absence: `grep -n "worker_commit" src/mcp_server/worker_commit.rs` hit. Then `grep -in "blocked\|needs-judgment\|needs_judgment\|question" src/mcp_server/worker_commit.rs` returned only the *comments* — line 155 "blocked awaiting this MCP call" (a description of the worker agent, not an outcome) and line 1069 "never dropped, never blocked" (an `undeclared` path). No outcome carries it.

The funnel state machine has no such state:
- `Position` is closed at `Spawned, WorkerCommitted, Imported, Verified, Concluded, Reaped` (funnel_machine.rs:79-84). `TransitionKind` closed at `Spawn, RecordWorkerCommit, Import, Verify, Conclude, Reap` (funnel_machine.rs:126-131).
- **Positive control:** `grep -in "judg" src/funnel_machine.rs` → exit 1 (no hit). There is no halted/needs-judgement position.
- The per-phase row model carries only `spawn / worker_commit / import / verify / conclude / reap` stamps — `PhaseRow` fields (funnel_machine.rs:236-258).

The orchestrator dispose oracle has no such arm:
- `NextKind` is closed at `Spawn, AwaitWorker, Import, Verify, TriageVerifyFailure, ReverifyStale, Conclude, Reap, AllReaped` (dispatch.rs:6502-6517). `next_kind` projects `Expected` one-for-one with exactly one position-derived discriminator (dispatch.rs:6539-6557). `is_runnable` = `Import | Verify | Conclude | Reap` (dispatch.rs:6582-6588); `AwaitWorker` and `Triage` ("a judgment beat") are explicitly NOT runnable (dispatch.rs:6580-6581).
- The single "judgment halt" that exists is `Triage` from **red stored verify evidence**, coord-tree-global, deliberately outranking mechanical progress (dispatch.rs:6592-6600) — that is a *fail* verdict, not a worker signalling a request for judgement. It is reached by the orchestrator's own `dispatch verify` running red.

The only "blocked" in the whole dispatch/funnel vocabulary is **`ReceiptStatus::Blocked`**, which is **derived from a runtime phase sheet** (`crate::state::read_phase_status`) via `PhaseStatus::Blocked`:

- `ReceiptStatus::Blocked` in `run_plan_next`/`run_status` comes from `classify_sheet`/`derive_receipt_status` reading the gitignored `.doctrine/state/slice/<NNN>/phases/phase-NN.toml` sheet value `status = "blocked"` (state.rs `PhaseStatus::Blocked`, dispatch.rs:4680-4705 receipt matrix row 6; state.rs `read_phase_status` at 178-180).
- Who writes that sheet: **`set_phase_status`** (state.rs:302-403) — the writer behind `doctrine slice phase --status blocked`. The funnel's own `dispatch_conclude_phase` uses it only to flip `Completed` (mcp_server/dispatch.rs:605-656, line 645-647 `set_phase_status(... PhaseStatus::Completed ...)`).
- **The worker cannot write this sheet either** — the sheet lives under `.doctrine/state/` (gitignored) and `worker_commit`'s `is_forbidden_zone` hard-refuses any path starting with `DOCTRINE_PREFIX` (`.doctrine/`) (worker_commit.rs:88-96, `classify_scope` line 121-129 → `forbidden-zone`). So the only entities that can set `blocked` are the orchestrator CLI (`slice phase`) or a manual operator edit.

**Conclusion Q1:** A worker today has exactly two truth outcomes — *commit* or *belt-refused* — and both mean "phase progressed as far as the gate allows". There is no third channel for "I need judgement" through `worker_commit`, `dispatch_import/conclude/reap`, or the `next` oracle. Labouring the obvious: the worker **can** simply *not* call `worker_commit` and return control-channel prose in its hand-back (that is the *ad-hoc* seam the harness provides), but no structured route exists.

### Q2 — A worker CAN author ONE structured record the trusted side harvests: `observation_record` (friction), via the unconfined server

- The MCP tool exists: `TOOL_OBSERVATION_RECORD: &str = "observation_record"` (mcp_server/tools.rs:37), dispatched at tools.rs:1196, implemented at `run_observation_record` (tools.rs:1295).
- It is **explicitly worker-reachable**; the tool description says "Deliberately NARROWER than the trusted CLI, because it is reachable from a confined worker: it creates `friction` ONLY" (tools.rs:419). It refuses every other capture key — `kind, source, counters, gauges, …` via `CAPTURE_REFUSED_KEYS` (tools.rs:58, 1334-1341).
- **Where the write happens:** `run_observation_record` writes through `crate::observation::Service::new(root.to_path_buf(), SourceRegistry::empty())` → `service.record_friction(&envelope)` (tools.rs:1323-1328) → `Store::create` writes under `RECORDS_DIR = ".doctrine/observations/records"` (observation/store.rs:37, `create` at store.rs:143-220, records landing at `root.join(RECORDS_DIR)`).
- **Worker-fork nuance — the "fork cannot write it directly":** the *write is performed by the MCP server process*, which runs **unconfined** at the **primary root** the server resolved (tools.rs:1315 "the server resolves the registered primary repository root (there is no path/root argument)"). The worker never writes into its own worktree. The physical path `.doctrine/observations/` is under the `.doctrine/` floor that `worker_commit::is_forbidden_zone` would reject in a *worker commit delta* (worker_commit.rs:88-96), so a worker can **never** commit an observation itself — it must go through `observation_record`, and the worker-mode CLI guard explicitly shunts workers there: `"worker fork … refusing `{verb}` — workers cannot capture observations locally. Confined Claude workers: use the `observation_record` MCP tool."` (commands/guard.rs:521-527).
- **Harvest discipline:** records are *authored* and diffable (boot context instrumentation section) and deliberately left untracked until someone commits them — i.e. the trusted side later commits them. The record is `friction`-typed only; the service admits `record_measurement` only for registered machine sources, and the empty production `SourceRegistry` refuses everything (observation/mod.rs:34-40, `record_measurement` at 104-119 with the "not a registered machine source" refusal; tools.rs:1324 passes `SourceRegistry::empty()`).

**Conclusion Q2:** Yes — a worker can author exactly one structured, harvestable record today: a `friction` observation via the `observation_record` MCP tool, written by the unconfined server to `.doctrine/observations/records/`. The worker fork cannot write that file itself (jail floor + forbidden-zone belt), and the worker-mode CLI refuses local capture.

### Q3 — The managed design run DOES carry an inquiry/pending state that pauses `inquiring→drafting`; only the trusted side may answer it

- The run model has an inquiry map whose nodes have `InquiryLifecycle { Open, Resolved, Deferred, Pruned }` (design_run/inquiry.rs:60-70).
- **`blocked` is derived, never stored (DEC-060):** `InquiryMap::is_blocked` answers from `needs` edges + target lifecycle — a node is blocked when a `needs`-dependency is `Open` or `Deferred` (inquiry.rs:9-12, 433-441). A `blocked()` iterator enumerates them (inquiry.rs:466-471).
- **The gate that pauses the run:** the `InquiringDrafting` advance (stage-edge exploring→inquiring→drafting) requires the condition `BlockingInquiriesDispositioned = "blocking-inquiries-dispositioned"`, derived `EngineSource::Dispositions`, `Reach::Cumulative` (design_run/gate.rs:610-616, and the Σ `expected_next`-style remedies at tests.rs:1155-1175). Until every blocking inquiry is disposed, the run cannot legally advance past the `Inquiring` stage.
- **How a blocking inquiry is "answered" (disposed):** `InquiryNode::resolve` requires a semantic `Disposition` — one of `Created { record }`, `Adopted { record }`, `RetainedUnresolved { note }`, `NonDurable { note }` (inquiry.rs:89-111, resolve at 337-352, with `DispositionMissing` refusal at 362-372). The `Disposition` is applied through a **checkpoint declaration** mapping `Dispose::Create/Adopt/Unresolved/NonDurable` → `Disposition` (design_run/run.rs:1439-1468) in `apply`.
- **Who may answer:** the answering path is `doctrine design apply` — which the worker-mode guard classifies as `Write` and **refuses in a worker fork** (commands/guard.rs:475-478 `DesignCommand::Apply(_) => Write("design apply")`; guard.rs:485+ `worker_guard` refuses all `Write`/`Orchestrator` verbs). So the answer is given by the **orchestrator side (user/coordinator)**, never a confined worker. Additionally two neighbouring gates are **user-fixed-actor**: `GoverningContextRecorded` and `InitialConcernsRecorded` require `RequiredActor::Fixed(ActorClass::User)`; `UserAcceptsSufficiency` likewise (gate.rs:562-598, 618-628; note `BlockingInquiriesDispositioned` itself is engine-derived with **no required actor** — any `apply` submission disposing the blocking nodes clears it). `design materialise`/`start` are likewise `Write` and worker-refused (guard.rs:476-477).

**Conclusion Q3:** Yes. The design run has an open/inquiry+blocking state (`InquiryLifecycle`, derived `is_blocked`, gate `blocking-inquiries-dispositioned`) that pauses the run at `inquiring` pending disposition. The dispose answer arrives through `design apply`, which is orchestrator/user-only; workers are blocked by the worker-mode guard.

### Q4 — There is NO append-only "admission journal" implemented today

- **Positive control:** `grep -rn "Admission\|admission" src/ledger.rs` hits (`CurrentAdmission`, `Admission` in the candidates ledger, ledger.rs:176, 182, 234-238) → the instrument works.
- **Zero:** `grep -rni "admission journal" src/` → exit 1, no hit. The word "admission" in the dispatch corpus names **candidate-role pinning** (`CurrentAdmission { close_target, review_surface }`, ledger.rs:233-248), not a worker-signal journal.
- What **is** implemented and is *close-but-not-it*:
  - The **funnel record** — `FunnelRecord { schema, rows: Vec<PhaseRow> }` committed as `.doctrine/dispatch/<NNN>/funnel.toml` on `dispatch/<NNN>`, written through **the sole writer** `land_funnel_transitions` using one `commit_on_behalf` CAS per landing (dispatch.rs:5666-5677, 5964-6010 "THE sole writer … `read the record at tip → fold ts IN ORDER … land it with ONE commit_on_behalf CAS`"). It is **append-only under CAS** — the comment at dispatch.rs:5734-5735: "the ref is append-only under CAS (`commit_on_behalf` constructs each commit with `expected_old` as its parent), so a recorded row cannot be silently rewritten". Per-phase rows **upsert** by phase id (dispatch.rs:5686-5692 `fn upsert`), so the "log" is one row per phase, not a growing event stream.
  - The dispatch **`ledger::Journal`** — `Journal { rows: Vec<JournalRow>, allowed_clobbers }`, `journal.toml` committed on `dispatch/<NNN>` (ledger.rs:29-46, dispatch.rs records it via `commit_journal` in `run_record_integration`). Rows are CAS projection rows (`source_oid/target_ref/expected_old_oid/planned_new_oid/applied_new_oid/status`), and `run_record_integration` *replaces* an existing trunk row rather than strictly appending (dispatch.rs:1157-1158 `if let Some(slot) = … find … { *slot = row } else { journal.rows.push(row) }`). So it is an ordered manifest, not an append-only event log of worker signals.
- Neither carries the *semantic* ("admission journal = control-plane-owned ordered log of worker dispositions/signals") the question asks about. No such module or type exists in code.

## Design implications

- **A worker→orchestrator "needs judgement" channel would be net-new machinery.** The incumbent seams give the worker only `Committed | Refused{token}` (worker_commit), `observation_record` (friction-only, server-side write), and unstructured hand-back prose. Any new judgment/question signal must decide whether it is (a) a new `WorkerCommitOutput` variant, (b) a new observation kind, or (c) a new funnel `Transition`/`Position` — and each lands in a different authority (the worker_commit belt, the observation service, or the funnel machine), so the coupling cost differs sharply. The funnel machine is the *only* place a pause-that-gates-`next` can be expressed, but its `Position` ordering (`Spawned … Reaped`) and the `next` totality theorem both assume advance-only; inserting a pause state would break the "exactly one prescription, always" invariant the oracle relies on (dispatch.rs:6590-6600).
- **The `.doctrine/` floor is the real boundary for any worker-authored record.** Since `worker_commit` hard-refuses `.doctrine/` and committed `funnel.toml`/`journal.toml` live under `.doctrine/dispatch/`, any worker-authored durable artifact must either go through a server-side MCP tool (like `observation_record`) or into a path outside the floor. `observation_record` is the living template for the server-resolved, narrow-tool pattern.
- **The design run is the existing "ask the question, pause" model** — but it is orchestrator-side only (`design apply` refused under worker-mode). If the goal is a *worker*-initiated question, the design-run inquiry machinery is the wrong home; the worker has no `design` write access.
- **The funnel record is not an event log.** Rows upsert by phase; re-record replaces. Building an actual append-only ordered journal of worker signals would diverge from both the funnel record (upsert-by-phase) and the dispatch `Journal` (CAS row with replace-on-trunk). The `PhaseRow` `updated_at` stamps exist (funnel_machine.rs:237) and could underpin ordering, but there is no monotonic sequence number today.
