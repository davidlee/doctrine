# RFC-028: Verifiable Human Authorization

**Status:** Proposed
**Authors:**
**Created:** 2026-08-04
**Updated:** 2026-08-05 — separated attestation from authorization; added the privileged-filesystem mechanism and made it the first implementation
**Target:** Doctrine authorization, governance, and execution policy
**Implementation candidates:** privileged read-only mount (local / bwrap); [`rust-minisign`](https://github.com/jedisct1/rust-minisign) (portable)

## Summary

Doctrine must sometimes distinguish between:

1. an agent deciding that an action is appropriate;
2. Doctrine policy permitting the action;
3. a human user explicitly authorizing the action.

Today, explicit human sanction is established primarily through trusted execution recipes and interpretation of interactive session context. This is adequate for ordinary collaborative use, but weak for exceptional operations such as:

* waiving an adversarial review;
* overriding a governance rule;
* accepting an unresolved risk;
* approving out-of-scope file changes;
* authorizing publication or remote mutation;
* delegating bounded authority to an agent.

This RFC introduces **typed authorizations**: narrowly scoped, state-bound statements that a jailed agent can request and present but cannot manufacture.

An authorization has four parts, and only the last of them is a security mechanism:

```text
Authorization
├── claim        — action, target, parameters, issuer
├── basis        — the state the approval assumes
├── validity     — issued, expiry, uses, nonce
└── attestation  — why Doctrine should believe a human granted it
    ├── privileged-filesystem   (local, single-host, jailed)
    └── detached-signature      (portable, transportable, remotely verifiable)
```

The first three carry Doctrine's semantics and do not vary with the mechanism. Attestation is pluggable, and **the cryptography is not what supplies authority** — it is one way of transporting an authority boundary that exists elsewhere. Under Doctrine's actual deployment, agents run inside a bubblewrap jail and that boundary is already supplied by the kernel: a file visible but immutable inside the jail can only have been written from outside it. Where that holds, a signature is redundant machinery.

So this RFC proposes two mechanisms and an order. **Privileged-filesystem attestation first** — it is materially cheaper, and its prerequisite (separating Doctrine's data by permission structure) is worth having on its own account. **Detached signatures later**, using `rust-minisign`, when an approval must survive outside the environment whose mount established its provenance.

Doctrine remains responsible for the more important layer either way: defining what was authorized, by whom, under which conditions, for how long, and whether that authorization remains valid at the point of use.

## Motivation

An agent operating on a user’s behalf may be able to perform actions whose legitimacy depends on explicit human judgment.

For example, an agent may conclude that adversarial review is unnecessary because:

* the change appears trivial;
* obtaining review would delay execution;
* the agent believes another check is equivalent;
* the agent misunderstands the applicable governance rule;
* the agent is attempting to avoid scrutiny.

The resulting state may look identical regardless of whether the user explicitly approved the waiver.

Interactive transcripts can provide evidence, but they are not a strong authority boundary:

* authority must be reconstructed from natural language;
* the relevant statement may be ambiguous;
* the agent may paraphrase or misrepresent the user’s instruction;
* session context may be unavailable during later audit;
* a jailed agent may be able to write artifacts claiming approval;
* Doctrine cannot reliably enforce natural-language sanction as a transition precondition.

Doctrine requires a first-class distinction between:

* **agent judgment**;
* **policy validity**;
* **human authority**.

## Hypothesis

A jailed agent can safely request, transport, and present a human authorization without being able to manufacture one, provided that:

* the authority that attests an authorization is unavailable inside the jail — a private key the agent cannot read, or a directory the agent cannot write;
* the authorization is a typed envelope whose semantics are fixed at approval time, not reconstructed later from agent-controlled material;
* the authorization is bound to the intended operation and relevant state;
* verification anchors on a trust root established outside the agent’s control;
* replay, expiry, and state drift are checked when the authorization is consumed.

This would allow Doctrine policy to require explicit human sanction without requiring Doctrine to trust the agent’s account of that sanction.

Note that the first clause admits two readings, and the RFC's central claim is that the weaker-looking one is sufficient locally: *unreadable key* and *unwritable directory* are both capability boundaries the jail already enforces, and the second is free.

## Goals

This proposal aims to:

1. make explicit human authorization machine-verifiable;
2. bind authorization to a specific semantic action;
3. prevent an agent from broadening or reinterpreting an authorization;
4. invalidate authorization when relevant state changes;
5. prevent accidental or malicious replay;
6. retain signed authorization and consumption as audit evidence;
7. support offline and local-first operation;
8. avoid introducing a general identity, certificate, or key-distribution system prematurely;
9. keep attestation pluggable, and adopt the cheapest mechanism that satisfies the deployment's threat model;
10. reuse established cryptographic primitives rather than implementing custom signing, *where* signing is warranted.

## Non-goals

This RFC does not attempt to:

* prove that a human fully understood an authorization;
* prove that a particular physical person controlled the signing device;
* provide non-repudiation in the legal sense;
* replace jail, filesystem, process, or network confinement;
* replace Doctrine’s ordinary policy and gate evaluation;
* establish a general-purpose PKI;
* secure a compromised host operating outside the jail;
* infer authorization from arbitrary signed prose;
* make every user interaction require a cryptographic ceremony;
* distinguish a human from any other principal holding the attesting capability — a key holder or an out-of-jail writer.

Authorization is intended for policy-significant actions where explicit human sanction matters.

## Terminology

### Principal

An identity recognised by Doctrine as able to authorize actions — under the signature mechanism, represented by one or more trusted public keys; under the privileged-filesystem mechanism, represented by write access to the privileged store.

A principal may correspond to a user, operator, maintainer, project owner, or another authority recognised by Doctrine.

### Attestation

The evidence that an authorization was granted by a principal rather than fabricated by the agent, and the mechanism that produces and checks it.

Two mechanisms are proposed: **privileged filesystem** (authenticity from where the approval resides) and **detached signature** (authenticity from a signature over its contents). The attestation mechanism is orthogonal to the claim, basis, and validity it attests.

### Authority

Permission to authorize a class of semantic actions.

Examples:

```text
gate.waive
risk.accept
scope.expand
remote.publish
authority.delegate
```

### Authorization request

An unsigned, canonical description of an action for which human authorization is requested.

### Granted authorization

An authorization envelope accompanied by valid attestation from a principal with the required authority — a valid signature, or residence in the privileged store.

### Consumption

The application of an authorization to the protected operation it permits.

Some authorizations may be reusable by design, but exceptional-operation authorizations should normally be one-shot.

### Basis

The state against which the authorization was granted.

The basis may include document hashes, graph state, repository state, gate inputs, plan revisions, or other material facts whose alteration should invalidate the authorization.

## Security model

The expected deployment has three relevant trust zones.

### User environment

The user environment holds whatever capability attests an authorization.

Under the signature mechanism that is a private signing key, encrypted at rest unless an external key agent or hardware-backed signer is used:

```text
~/.config/doctrine/keys/authority.key
```

Under the privileged-filesystem mechanism it is write access to the authority store, which the jail mounts read-only:

```text
~/.local/share/doctrine/authority/
```

Both are capabilities the jail withholds from the agent. Neither is evidence of a human — see *What the local mechanism proves*.

### Jailed agent environment

The agent can:

* create authorization requests;
* read the trust root (public keys, or the privileged store);
* receive or observe granted authorizations;
* ask Doctrine to verify them;
* attempt protected operations.

The agent cannot:

* read the private signing key;
* write the privileged authority store;
* invoke an unrestricted signing or approval service;
* modify the authoritative trust root;
* cause Doctrine to accept an invalid or stale authorization.

### Doctrine verifier

Doctrine verifies authorization as part of the protected transition.

A separate successful invocation of `doctrine authorization verify` is informative but not sufficient. The operation that consumes the authorization must repeat validation against current state.

## Core design

Attestation must cover a typed authorization envelope, not merely a document hash, an arbitrary string, or a bare marker such as `approved`. This holds under both mechanisms: a signature must be computed over the typed envelope, and a privileged-store file must *be* the typed envelope.

An authorization envelope describes:

* what is being authorized;
* which target it applies to;
* which state the authorization assumes;
* who issued it;
* when it is valid;
* whether it may be reused;
* any constraints or explanation attached to it.

Example:

```toml
schema = "doctrine.authorization.v1"

id = "AUTH-01J4..."
issuer = "principal:david"

action = "gate.waive"
target = "slice:SL-217"

[parameters]
gate = "adversarial-review"

[basis]
workspace = "workspace:01J..."
git_head = "8c9fd9c..."
plan_hash = "blake3:42a7..."
gate_input_hash = "blake3:931b..."

[validity]
issued_at = "2026-08-04T02:00:00+10:00"
expires_at = "2026-08-04T03:00:00+10:00"
nonce = "01J4..."
uses = 1

[explanation]
reason = "Accepted for this exploratory implementation."
```

The envelope is the same under both mechanisms. Under the signature mechanism Doctrine serializes it into a deterministic canonical representation and signs the resulting bytes — the signature must not be computed over a user-facing rendering, mutable TOML formatting, or an incomplete subset of the envelope. Under the privileged-filesystem mechanism the envelope is written verbatim into the authority store, and its authenticity comes from that placement.

**The envelope must be self-contained under either mechanism**, and the reason is sharper in the local case. The request lives inside the jail and is therefore agent-mutable. An approval that referenced its request by id alone would be trivially subverted: obtain approval for `AUTH-01J4`, then rewrite `AUTH-01J4.request.toml`. So the granted envelope restates the full claim, basis, and validity; the request is a proposal that the approval flow reads exactly once.

### Attestation-dependent fields

An envelope field is only meaningful if its mechanism can enforce it. `uses` is the case that bites: under a read-only store no in-jail process can decrement it (see *Consumption under a read-only store*). The envelope should therefore record which mechanism attested it, and Doctrine should refuse an envelope whose validity constraints its mechanism cannot enforce, rather than silently ignoring them:

```toml
[attestation]
mechanism = "privileged-filesystem"   # or "detached-signature"
```

## Attestation mechanisms

### Privileged filesystem (the local mechanism)

**The observation.** Doctrine's agents already run inside a bubblewrap jail defined in `flake.nix`, with read-only mounts an established part of the design. In that deployment:

> A file that is visible but immutable inside the jail can only have been created or changed by something outside the jail.

That is an authenticity claim of the same shape as a signature check, obtained from the mount table instead of from Ed25519.

**The layout.** Authorization state moves out of the project tree into a host-owned store, writable only outside the jail and bind-mounted read-only inside it:

```text
~/.local/share/doctrine/authority/
├── policy.toml      # which actions may be authorized, and by whom
└── approvals/       # one envelope per granted approval
                     #   host: read-write
                     #   jail: read-only bind mount
```

**This is the prerequisite, and it is the real cost.** Doctrine's data must be separated by **permission structure**, not only by the existing authored / runtime / derived tiers. Those three are a *durability* axis and all three are agent-writable; this is an orthogonal *authority* axis — who may write it, not how long it lasts. Nothing under `.doctrine/` can hold an approval, because the agent can write all of `.doctrine/`. Introducing that fourth axis is a structural change to Doctrine's storage model and should be scoped as such.

**The flow.** Inside the jail, the agent requests:

```sh
doctrine authorization request \
  gate.waive \
  --target SL-217 \
  --gate adversarial-review
```

Outside the jail, the user reviews and approves:

```sh
doctrine authorization approve <request>
```

`approve` parses the typed request, renders its semantic effect, requires explicit confirmation, and atomically writes a self-contained envelope into the privileged store.

Inside the jail, Doctrine verifies:

1. the store is present, and **not writable from here**;
2. an approval matching the pending operation exists in the store;
3. its action, target, and parameters match;
4. its basis still matches current state;
5. it is within its validity period;
6. its use conditions are satisfied.

No signature is required, because the approval's **storage provenance** establishes its authority.

### Two self-checks the local mechanism cannot omit

Moving the trust root into the filesystem creates two failure modes with no cryptographic analogue. Both must fail closed.

**1. The store must be provably read-only from inside.** If the mount is misconfigured read-write, the scheme degrades silently to agent-forgeable with no outward symptom — every approval still verifies, and nothing looks wrong. Doctrine must probe writability at verification time and treat `store-writable` as an authorization failure, not a warning.

**2. The store path must not be agent-influenced.** The agent controls its own argv and environment. If the store location resolves from `DOCTRINE_AUTHORITY_DIR`, from project config, or from anything else under `.doctrine/`, the agent points it at a directory it can write and forges the entire corpus. Path resolution must come from a source the agent cannot alter: a compiled default, overridable only by host-owned configuration that itself lives inside the privileged mount.

The second is the sharper trap, because Doctrine's existing configuration conventions make an env-var or `doctrine.toml` override the obvious implementation.

### Consumption under a read-only store

Because the mount is read-only inside the jail, the consuming process cannot delete, move, or annotate the approval. One-shot semantics must come from elsewhere.

The clean answer is to make an approval valid for a **transition**, not for an operation:

```text
state A  ──[protected transition, approved for basis A]──▶  state B
```

Once the transition succeeds the basis no longer matches, so a replay fails `basis-mismatch` without anyone having recorded a consumption. Replay resistance becomes a property of the state binding rather than of a ledger — which is where this RFC already located most of it.

This is sufficient for every action proposed for the first implementation — `gate.waive`, `risk.accept`, `scope.expand`, plan expansion, transition approval — because each changes the state it is bound to.

It is *not* sufficient for an operation that leaves its bound state unchanged (an idempotent publish, a read-only export). Those require one of:

* a host-owned consumption ledger, written by the same out-of-jail process that approves;
* an out-of-jail authorization broker (see *Host-mediated approval socket*);
* an intrinsically unique or idempotent operation identifier recorded by the operation itself.

Restricting the first implementation to state-mutating actions avoids the question entirely, and is the right initial scope.

### What the local mechanism proves

Precisely this:

> A process with write access outside this jail placed this approval in the privileged directory.

It does not prove a human did so. That inference holds only while:

* the privileged directory is writable by the user and no other principal;
* no signing, approval, or privileged-write helper is exposed inside the jail;
* no host credential or socket capable of writing the directory is forwarded in;
* the jail cannot remount, escape, or otherwise cross the boundary.

Each is a genuine precondition, and each is checkable at install time rather than on every use — which is part of why the mechanism is cheap.

### How the two mechanisms compare

A detached signature is not stronger *in kind*: it also proves control of a capability, not human presence. The honest deltas:

| | privileged filesystem | detached signature |
|---|---|---|
| authority root | mount configuration | private key |
| survives leaving the host | no | yes |
| independently re-verifiable later | only in situ | yes |
| adds a presence factor | no | yes, if the key is passphrase-gated |
| one-shot enforcement | basis transition only | basis transition, or a consumption ledger |
| implementation surface | envelope + placement + two self-checks | envelope + canonical encoding + key management + trust registry + rotation |

The presence row is the one substantive security advantage: a scheduled job running outside the jail can write a file, but cannot use a passphrase-gated key. Where that distinction matters the signature mechanism is warranted; where it does not, it is ceremony.

Every other row favouring signatures is about **portability**, not about authority.

## Authorization lifecycle

### 1. Request

The jailed agent requests authorization for a protected action:

```sh
doctrine authorization request \
  gate.waive \
  --target SL-217 \
  --gate adversarial-review
```

Doctrine resolves the relevant current state and creates an unsigned request.

The agent should not manually supply basis hashes where Doctrine can derive them.

The request may be written to a file:

```text
.doctrine/authorizations/AUTH-01J4.request.toml
```

### 2. Review and grant

Outside the jail, the user invokes the mechanism's grant command — `approve` for the privileged store, `sign` for a detached signature:

```sh
doctrine authorization approve \
  .doctrine/authorizations/AUTH-01J4.request.toml
```

The grant command:

1. parses the request;
2. validates its schema;
3. rejects unknown security-relevant fields;
4. independently renders its semantic effect;
5. presents the authorization to the user;
6. requires an explicit confirmation;
7. attests the envelope — writing it atomically into the privileged store, or signing its canonical form;
8. emits a granted authorization.

Steps 1–6 are identical under both mechanisms and carry most of the security value; only step 7 differs. This is the practical argument for the layering: the expensive, judgement-bearing part of the flow is mechanism-independent.

Note that the request path shown above is *inside* the jail. The out-of-jail grant command must therefore be able to read the project tree, which the jail bind-mounts from the host — or accept the claim restated on its own command line. Either way, what it writes is self-contained.

Example presentation:

```text
AUTHORIZE

Action:
  Waive gate "adversarial-review"

Target:
  Slice SL-217

Bound state:
  Workspace: 01J...
  Git HEAD: 8c9fd9c...
  Plan: 42a7...
  Gate inputs: 931b...

Validity:
  One use
  Expires: 2026-08-04 03:00 Australia/Melbourne

Reason:
  Accepted for this exploratory implementation.
```

The user must never be asked to approve an opaque hash without a trusted semantic rendering.

### 3. Transport

The granted authorization is made available inside the jail.

Under the privileged-filesystem mechanism there is no transport step: the approval becomes visible in the read-only mount the moment it is written, and moving it anywhere else would destroy the provenance that makes it authoritative. Under the signature mechanism the artifact is transported explicitly, and it is safe to treat it as a bearer capability only because its scope is narrow and its basis is state-bound.

Possession of the authorization permits only the exact action described by the envelope.

### 4. Verification

Doctrine verifies:

1. the envelope schema is supported;
2. the attestation is valid for its declared mechanism — a cryptographically valid signature, or residence in a store proven read-only from here;
3. the attesting capability is trusted — a trusted key, or the configured privileged store resolved from a non-agent-influenced path;
4. the granting principal has authority for the requested action;
5. the action parameters match the pending operation;
6. the target matches;
7. the authorization is within its validity period;
8. the current state matches the attested basis;
9. the authorization has remaining uses, where its mechanism can enforce that;
10. the authorization has not been revoked or consumed.

### 5. Consumption

The protected transition and authorization consumption must be coupled.

Conceptually:

```text
validate current state
validate authorization
apply protected transition
record authorization consumption
commit atomically
```

A prior verification result must not be accepted as evidence that the authorization remains valid.

Where atomic storage is unavailable, Doctrine must use equivalent concurrency preconditions and fail closed if current state cannot be proven unchanged.

Under the privileged-filesystem mechanism the `record authorization consumption` step has nowhere to write, and one-shot semantics fall to the basis transition instead — see *Consumption under a read-only store*.

## Attestation: detached signature (portable mode)

This section specifies the second mechanism. It is not required for the first implementation.

Doctrine will use `rust-minisign` as the signature implementation.

This provides:

* Ed25519-based signatures;
* BLAKE2b prehashing;
* detached signature containers;
* encrypted persistent secret keys;
* public-key verification;
* a compact, established interchange format.

Doctrine must not implement its own signature algorithm.

### Signed bytes

The signature covers the complete canonical authorization envelope.

Doctrine should pass the canonical bytes directly to Minisign. It should not sign only an independently calculated Doctrine hash unless required by a future storage boundary.

Minisign already performs content prehashing before signing.

### Trusted and untrusted comments

Minisign supports both trusted and untrusted comments.

Doctrine may use the signed trusted comment for a concise human-readable description:

```text
Doctrine authorization: waive adversarial-review for SL-217
```

However:

* the untrusted comment must never affect authorization semantics;
* the trusted comment remains informational;
* all enforceable semantics must exist inside the signed envelope;
* Doctrine must not reconstruct an authorization by parsing comments.

This avoids two competing representations of the same authority claim.

## Canonicalization

Authorization signatures depend on deterministic serialization. **This requirement is attestation-specific, and it is most of what the local mechanism avoids.**

Without a signature there are no signed bytes, so deterministic encoding is no longer authenticity-critical. It degrades from *signature-critical* to *comparison-critical*: the envelope still needs a typed parse and deterministic basis hashing so that claim and basis can be compared against the pending operation. Field ordering, Unicode normalization, line endings, and the adversarial canonicalization test surface that goes with them are simply absent under privileged-filesystem attestation.

The remainder of this section applies to the signature mechanism.

The canonical representation must define:

* field ordering;
* string encoding;
* timestamp format;
* identifier normalization;
* integer and decimal representation;
* treatment of absent and empty values;
* map ordering;
* extension handling;
* line endings;
* Unicode normalization.

The human-editable TOML form need not itself be canonical.

A likely model is:

```text
TOML request
    ↓ parse
typed AuthorizationEnvelope
    ↓ canonical encode
canonical bytes
    ↓ sign
Minisign signature
```

Verification repeats the typed parse and canonical encoding.

The canonical format should be versioned independently through the envelope schema.

## Trust registry

The jail requires access to the trust root but must not be able to establish new root authority.

**Under the local mechanism the registry largely collapses.** The privileged store *is* the trust root: there are no keys to distribute, fingerprint, rotate, or revoke, and no principal-to-key binding to maintain. What survives is the authority-class table — which actions may be authorized at all — and that becomes a `policy.toml` in the same privileged mount. Key management, key identity, and rotation are portable-mode concerns.

This is a second large slice of the cost difference, and it removes a whole category of long-lived operational surface rather than merely deferring it.

The remainder of this section applies to the signature mechanism. A host-level registry may resemble:

```toml
schema = "doctrine.trust.v1"

[[principal]]
id = "david"
display_name = "David"

[[principal.key]]
fingerprint = "blake3:..."
public_key = "RW..."
status = "active"

[principal.authority]
allow = [
  "gate.waive",
  "risk.accept",
  "scope.expand",
  "remote.publish",
]
```

The registry should be:

* stored outside project-controlled state;
* mounted read-only into jailed environments;
* loaded from user or installation configuration;
* protected from mutation by the agent.

A repository may declare which authorities it requires, but must not be able to make an arbitrary key authoritative merely by including that key in version control.

### Key identity

Minisign includes a compact key identifier in signatures. This may be used to select a candidate public key.

Doctrine should identify trusted keys using a fingerprint of the complete public key rather than treating the compact Minisign key identifier as globally authoritative.

Verification must ultimately match the complete trusted public key.

## Policy integration

Signed authorizations are evidence consumed by Doctrine policy.

A protected rule might conceptually require:

```text
gate may be waived when:

authorization.action == "gate.waive"
authorization.target == current slice
authorization.parameters.gate == current gate
authorization.basis == current relevant state
authorization.issuer has authority "gate.waive"
authorization is valid and unconsumed
```

This should remain distinct from ordinary gate satisfaction.

A waived gate is not equivalent to a passed gate. Doctrine should preserve the disposition:

```text
gate outcome:
  status: waived
  authorization: AUTH-01J4...
  issuer: principal:david
  reason: Accepted for this exploratory implementation.
```

## Authority layers

This proposal formalizes three independent layers.

### Execution permission

Can the process invoke or technically perform the operation?

Enforced by jail, filesystem, operating-system, network, and command capabilities.

### Policy permission

Does Doctrine consider the operation valid under current project and governance rules?

Enforced by Doctrine predicates, gates, transitions, invariants, and validation.

### Human sanction

Did a trusted human authority explicitly approve the exceptional operation?

Established by an attested authorization. Note the recursion: this third layer is *itself* established by the first — the attesting capability is withheld from the agent by jail, filesystem, and process confinement. The privileged-filesystem mechanism simply makes that dependency explicit rather than routing it through a key.

An operation may require all three.

A valid human authorization does not automatically make an otherwise impossible or structurally invalid operation legal. It satisfies only the policy condition that requires explicit human sanction.

## Scope and least authority

Authorizations should be narrow by default.

Preferred:

```text
Waive gate adversarial-review
for slice SL-217
over plan hash 42a7...
once
before 03:00
```

Avoid:

```text
David permits review waivers.
```

Broad reusable authority is delegation, not ordinary authorization, and requires a separate model.

The default authorization should specify:

* one action;
* one target;
* explicit parameters;
* current basis;
* one use;
* short expiry.

## Replay resistance

An authorization may be replayed if it remains valid after its intended use.

Doctrine should combine:

* unique authorization identifiers;
* unpredictable nonces;
* explicit use counts;
* consumption records;
* expiry;
* state binding.

Consumption must be checked against authoritative Doctrine state, not merely the presence of a local marker file the agent can delete.

For Git-backed local operation, the exact persistence and concurrency mechanism remains an implementation decision, but reuse must fail closed.

Under the privileged-filesystem mechanism, only *expiry* and *state binding* from that list are enforceable in-jail; identifiers and nonces remain useful for audit and correlation but carry no enforcement. Scoping the first implementation to state-mutating actions makes state binding sufficient on its own.

## State binding and drift

The signed basis determines which changes invalidate authorization.

This must be action-specific.

For a gate waiver, relevant basis might include:

* gate identifier;
* target entity;
* gate definition;
* gate inputs;
* implementation plan revision;
* repository HEAD.

Binding every authorization to every workspace byte would be unnecessarily fragile. Binding too little would allow the agent to alter the substance after approval.

Each authorization action should define a basis resolver that derives the minimal state necessary to preserve the meaning of the user’s approval.

The resolver itself is part of Doctrine policy and must not rely on agent-supplied judgment where deterministic state is available.

## User comprehension and subterfuge

Attestation proves control of a capability — a key, or write access to a directory. It does not prove informed consent.

The grant interface is therefore security-sensitive, and equally so under both mechanisms: this is where a misleading request turns into a real authorization, and nothing downstream can recover from it.

The host-side grant command must:

* parse typed requests rather than sign arbitrary files by default;
* prominently display the actual action and target;
* display all constraints and expiry;
* summarize state binding in intelligible terms;
* distinguish user-authored explanation from agent-authored explanation;
* warn about unusually broad or reusable grants;
* reject unsupported schema versions;
* avoid allowing the request to control terminal presentation;
* prevent invisible or misleading Unicode where practical.

A generic low-level signing command may exist for diagnostics, but policy-significant authorizations should use action-aware grant flows.

## Storage and provenance

Doctrine should retain:

* the authorization envelope;
* the attestation — the signature, or the store path and mount state observed at verification;
* the signing-key fingerprint, where one exists;
* the resolved principal;
* verification results;
* the protected operation;
* the consumption record;
* any failure or invalidation reason.

A granted authorization is immutable evidence — cryptographically under the signature mechanism, and by the read-only mount under the local one. The local mechanism's immutability is *contextual*: it holds inside the jail and does not travel. An approval copied out of the privileged store into project state is a record of an authorization, not an authorization.

The surrounding operational record may add facts such as:

```toml
[consumption]
consumed_at = "2026-08-04T02:17:00+10:00"
operation = "transition:gate-waiver"
resulting_record = "REC-01J4..."
state_hash = "blake3:..."
```

These consumption facts are not part of the original signature. They are Doctrine’s record of how the signed authority was used.

## Proposed CLI surface

Initial commands (local mechanism):

```sh
doctrine authorization request <action> [arguments]   # in-jail
doctrine authorization inspect <request-or-authorization>
doctrine authorization approve <request>              # out-of-jail; writes the privileged store
doctrine authorization verify <authorization>
```

Portable mechanism, added later:

```sh
doctrine authorization sign <request>
doctrine authorization consume <authorization>
```

`doctrine authorization approve` must refuse to run from inside the jail — not as a security control (it could not write the store anyway) but so the failure names the boundary instead of surfacing as a permission error.

Protected domain commands should normally consume authorization directly:

```sh
doctrine gate waive adversarial-review \
  --slice SL-217 \
  --authorization AUTH-01J4.signed.toml
```

`authorization consume` may be useful for testing and internal integration but should not become the ordinary user workflow.

Key management (portable mechanism only):

```sh
doctrine key generate
doctrine key inspect
doctrine key export-public
doctrine key rotate
```

Trust management (portable mechanism only):

```sh
doctrine trust list
doctrine trust add-public-key
doctrine trust disable-key
doctrine trust inspect-principal
```

Trust mutation commands must not be available to an agent merely because the Doctrine binary is executable inside the jail. The filesystem and configuration boundary remains authoritative. Under the local mechanism this is not a discipline to maintain but a structural fact: there is nothing to mutate that the agent can reach.

The local mechanism also wants one diagnostic, because its silent-degradation mode has no other symptom:

```sh
doctrine authorization doctor   # is the store present, mounted, and read-only from here?
```

## Failure semantics

Authorization failure must be explicit and typed.

Example failure classes:

Mechanism-independent classes:

```text
insufficient-authority
schema-unsupported
action-mismatch
target-mismatch
basis-mismatch
expired
not-yet-valid
malformed-envelope
unenforceable-validity     # envelope constrains what its mechanism cannot enforce
```

Privileged-filesystem classes:

```text
store-absent               # the privileged mount is missing
store-writable             # the mount is not read-only from here — trust root void
store-path-untrusted       # the store path was resolved from agent-influenced input
approval-absent            # no matching approval in the store
```

Detached-signature classes:

```text
signature-invalid
unknown-key
untrusted-key
already-consumed
revoked
canonicalization-failed
```

`store-writable` and `store-path-untrusted` are structural failures rather than authorization failures: they mean no authorization can be trusted in this environment at all, and should be reported as such rather than as a rejection of the particular request.

Protected operations fail closed on any authorization error.

Error output should distinguish:

* malformed or forged authorization;
* valid authorization for the wrong operation;
* valid authorization invalidated by later state drift;
* valid authorization lacking sufficient authority.

This distinction is important for both users and audit.

## Initial authorization actions

The first implementation should be deliberately narrow.

Recommended initial actions:

### `gate.waive`

Explicitly waive a named gate for a specific target and current basis.

This is the clearest motivating case and exercises state binding, policy integration, and one-shot consumption.

### `risk.accept`

Accept a specific unresolved risk or finding without asserting that it has been resolved.

### `scope.expand`

Authorize a known expansion beyond the currently sanctioned files or entities.

This may address governance violations caused by required but previously undiscovered file touches.

Additional actions should be added only when their semantics and basis can be specified precisely.

## Implementation sequence

The signature work moves to the end. The first four phases deliver a working authorization boundary with no cryptography in them.

### Phase 1: Permission-structured storage

* introduce the privileged authority store as an authority-axis storage tier, distinct from authored / runtime / derived;
* define its location and the non-agent-influenced path resolution rule;
* mount it read-only into the jail (`flake.nix`);
* implement the read-only and path-provenance self-checks, and `authorization doctor`;
* test that a writable or agent-relocated store fails closed.

This phase is the prerequisite, and it is where the design risk lives.

### Phase 2: Typed authorization envelope

* define `doctrine.authorization.v1`, including the `[attestation]` mechanism field;
* implement typed parsing and deterministic basis hashing;
* implement `request`, `inspect`, `approve`, and `verify` over the privileged store;
* test that a mutated request cannot alter an already-granted approval.

### Phase 3: Authority classes

* define the host-owned `policy.toml` inside the privileged mount;
* implement authority resolution for action classes;
* test that project-controlled configuration cannot grant authority.

No keys, principals, fingerprints, or rotation in this phase.

### Phase 4: Gate-waiver integration

* define the `gate.waive` basis resolver;
* require authorization for waiver transitions;
* validate at the point of transition;
* record waiver provenance;
* add replay, expiry, mismatch, and drift tests.

### Phase 5: Replay and audit

* establish one-shot semantics by basis transition, and restrict the action set to state-mutating actions;
* define concurrency behavior;
* expose authorization provenance in inspection and audit output;
* ensure an approval cannot be silently reused across branches or workspaces.

### Phase 6: Additional action families

* `risk.accept`;
* `scope.expand`;
* bounded delegation, if justified.

### Phase 7: Detached signatures (portable mode)

Undertaken only when a driving requirement exists — an approval that must leave the host, be verified remotely, or stand as independently re-verifiable audit evidence.

* integrate `rust-minisign`; generate encrypted key pairs; establish public-key fingerprinting;
* define the canonical encoding and the signature container, with adversarial canonicalization tests;
* add the trust registry: principals, keys, authority resolution, rotation;
* add an authoritative consumption ledger, unblocking non-state-mutating actions;
* publication and remote mutation actions.

Note that the envelope, the grant review flow, the basis resolvers, the policy integration, and the failure taxonomy all carry over unchanged. That is the test of whether the layering in this RFC is real.

## Testing requirements

Mechanism-independent, required from Phase 2:

* mutated request after grant;
* insufficient principal authority;
* expired authorization;
* future-dated authorization;
* changed target;
* changed action parameters;
* changed repository state;
* changed plan or gate inputs;
* replay after the bound transition has completed;
* concurrent consumption attempts;
* unsupported schema versions;
* an envelope constraining validity its mechanism cannot enforce;
* authorization copied between workspaces;
* authorization copied between targets;
* legitimate non-material state changes;
* material state changes omitted by an incorrect basis resolver.

Privileged-filesystem, required from Phase 1:

* store mounted read-write — must fail closed, and must be the *first* check;
* store absent or unmounted;
* store path supplied through the environment, project config, or any other agent-reachable input;
* an approval forged in an agent-writable directory shaped like the store;
* an approval present in the store but for a different workspace;
* authority `policy.toml` shadowed from project state.

Detached-signature, deferred to Phase 7:

* modified envelope after signing;
* modified trusted comment;
* misleading untrusted comment;
* wrong public key;
* matching compact key identifier with different full key;
* unknown principal;
* malformed canonical representations;
* reordered human-readable TOML fields;
* trust registry mutation from inside the jail;
* repeated consumption against the ledger.

Basis resolver tests are policy tests, not cryptographic tests, and are required under both mechanisms.

## Alternatives considered

### Interactive transcript inspection

Retains useful contextual evidence but cannot provide a deterministic authority predicate.

### Signed Git commits or tags

Can prove that a key signed repository state, but poorly expresses narrow semantic authorization and does not naturally support one-shot consumption, expiry, or action parameters.

### GPG

Provides mature signing and identity machinery but introduces substantial complexity and operational surface unnecessary for the initial Doctrine use case.

### SSH signatures

A plausible alternative, especially where users already manage SSH keys. It may be reconsidered if agent-backed or hardware-backed SSH signing materially improves usability.

### Raw Ed25519 implementation

Rejected. Doctrine should not define or implement its own signature format where an established compact system is available.

### Host-mediated approval socket

Could keep attesting material out of the jail entirely and ask a trusted host service to approve each operation. This may eventually provide stronger immediacy and usability, and it is the natural answer for one-shot consumption of non-state-mutating actions — but it adds a privileged online service and an IPC boundary. Offline authorizations are simpler and independently auditable.

The privileged-filesystem mechanism is best read as this alternative with the socket removed: the same out-of-jail authority, mediated by the kernel's mount table instead of by a running daemon.

### Signature-first sequencing

The original form of this RFC. Rejected as the *first* implementation, not on its merits: it front-loads canonical encoding, key management, and a trust registry to obtain an authority boundary that the jail already provides on this deployment. Signatures remain the right answer for portability and are retained as Phase 7.

### An untyped approval marker in the privileged store

The degenerate version of the local mechanism: a file whose presence means `approved`. Rejected. Storage provenance establishes *who*, not *what* — without a typed claim and a bound basis, an approval granted for one action authorizes anything the agent later attempts. The envelope is not the part of this design that cryptography was paying for.

## Open questions

1. What canonical encoding should Doctrine standardize on?
2. Which authorization and consumption records belong in Git-backed project state versus user-local state?
3. How should one-shot consumption behave across branches and isolated clones?
4. Should authorization expiry be mandatory for all exceptional operations?
5. Which basis elements should `gate.waive` bind in the first implementation?
6. Should explanation text distinguish agent proposal from user-authored justification?
7. How should key rotation preserve historical verification?
8. Should multiple signatures or threshold authorization be supported later?
9. Should public keys be scoped globally, per workspace, or through layered trust configuration?
10. Can hardware-backed signing be added without changing the authorization envelope?
11. Should a signed authorization be represented as one self-contained artifact or an envelope plus detached `.minisig` file?
12. How should revoked keys affect historical authorizations that were valid when consumed?

Opened by the privileged-filesystem mechanism:

13. Where does the authority store live, and how is its path resolved such that no agent-reachable input can influence it? A compiled default is the obvious answer and the least configurable one.
14. How does Doctrine prove a mount is read-only from inside — attempted write, `/proc/self/mountinfo`, or both? An attempted write is authoritative but leaves residue on a misconfigured store.
15. Is the permission axis a fourth storage tier alongside authored / runtime / derived, or an orthogonal attribute of the existing three? The latter is more honest and more invasive.
16. How does the store behave across worktrees and dispatch forks, where `basis.workspace` and the git topology both differ from the coordination tree?
17. Can the out-of-jail `approve` command read an in-jail request path reliably across every supported jail configuration, or must the claim be restatable on the command line?
18. Should a granted approval be mirrored into project state as audit evidence, given that the copy is a record and not an authorization?
19. Is `store-writable` a hard refusal for every protected operation, or may Doctrine degrade to a warned, transcript-evidenced mode? A hard refusal is correct and will be unpopular the first time a mount is misconfigured.
20. Does anything in Doctrine's threat model need the presence factor that a passphrase-gated key supplies and a directory write does not — and if so, does that action belong in the first implementation at all?

## Long-term direction

Attested authorization creates a foundation for more than exceptional approvals. Most of the extensions below require the portable mechanism, which is a further argument for keeping the attestation layer separable rather than for building it first.

Possible extensions include:

* multi-party approval;
* threshold authorization;
* temporary delegation;
* role-scoped project authority;
* hardware-backed signing;
* remote approval devices;
* signed release and publication authority;
* cryptographically attributable policy changes;
* authorization chains;
* external organizational trust providers.

These extensions should not be included in the initial design unless required by an immediate use case.

The initial objective is narrower:

> Doctrine must be able to distinguish an agent’s decision from an explicit, verifiable exercise of human authority.

## Decision

Adopt typed authorizations as a first-class Doctrine governance primitive, with **attestation as a separate, pluggable layer** beneath the claim, basis, and validity that carry Doctrine's semantics.

Implement **privileged-filesystem attestation first**: a host-owned authority store, writable outside the jail and mounted read-only inside it, where an approval's authenticity derives from where it resides rather than from a signature over its contents. Its prerequisite — separating Doctrine's data by permission structure, an authority axis orthogonal to the authored / runtime / derived durability axis — is the substantive work, and is worth doing on its own account.

Guard the mechanism with two non-negotiable self-checks that fail closed: the store must be provably read-only from inside the jail, and its path must not be resolvable from agent-influenced input.

Establish one-shot semantics through basis transition rather than a consumption ledger, and restrict the initial action set to state-mutating actions so that this suffices.

Begin with `gate.waive` as the first integrated action.

Defer `rust-minisign` and detached signatures to Phase 7, undertaken when an approval must survive outside the environment whose mount establishes its provenance — copied into Git, transported between machines, verified remotely, or retained as independently re-verifiable audit evidence.

Treat attestation validity as necessary but insufficient under either mechanism: every authorization must also satisfy Doctrine’s rules for authority, action, target, state, freshness, and consumption.
