# ISS-525: Installed pi extension TS breaks client type-aware lint

<!-- Backlog item body — context, detail, links. The structured, queried fields
     live in the sister `backlog-NNN.toml`; this prose is free-form and is never
     structurally parsed (the storage rule). -->

## Observed (malebolge, 2026-10-19)

`doctrine install` writes the pi extension (`.pi/extensions/doctrine/*.ts`,
header "Generated by doctrine boot install — do not edit") into the client's
source tree. The client's toolchain knows nothing about it:

```
eslint.config.js ── projectService: true   (type-aware rules)
        └─ every linted .ts must belong to a tsconfig project
tsconfig.json ── include: ["src", "test", "vitest.config.ts"]
.pi/extensions/doctrine/*.ts ── in no tsconfig → eslint errors on all 3 files
```

Pulling them into tsconfig fails too: they import
`@earendil-works/pi-coding-agent` and `typebox` (not client deps), and their
style (single quotes, `child_process` without `node:`) breaks strict client
lint. Malebolge worked around it by ignoring `.pi` (malebolge `3f5b506`).

Any client with type-aware linting or a broad `tsc` include breaks the same
way.

## Options

1. Install under a path toolchains already skip — if pi can load extensions
   from one (check pi's extension discovery; e.g. a dot-dir already
   conventionally ignored, or a user-level location).
2. Have `doctrine install` print (not apply) the matching lint/format ignores.
   Applying them would be the platform writing host-tool config — POL-002
   (platform independence from host conventions) forbids that; see IMP-355
   for the same tension with prettier and its folder-local mitigation.
3. Folder-local mitigation in the IMP-355 style: ship ignore-honouring config
   inside `.pi/extensions/doctrine/` itself. Weak for eslint flat config and
   tsc, which don't honour nested ignore files — probably not viable.

Related: IMP-355 (kind-local `.prettierignore`), ISS-479 (codex boot install
also writes pi extensions — widens the blast radius to non-pi users).
