# ISS-352: Worktree provisioning never regenerates the derived runtime tier

## The gap

`doctrine worktree fork` provisions a new tree by copying the gitignored files
its `.worktreeinclude` allows, withholding the tiers `WITHHELD` names, and
stamping the worker marker (`worktree/fork.rs:180`–`193`). Nothing regenerates
the **derived** tier. So a fresh worktree gets no skills, no shipped memory
corpus, and no boot snapshot — and no step in the lifecycle ever puts them there.

`allowlist.rs:99` states the opposite as settled fact:

```rust
/// Gitignored-but-*derived* trees: regenerated by `doctrine install` in the fork,
/// never copied and not a hazard — documented, deliberately out of [`WITHHELD`]
pub(crate) const DERIVED_RUNTIME: &[&str] = &[".doctrine/skills/*", ".doctrine/agents/*"];
```

"Regenerated by `doctrine install` in the fork" describes an intent nobody
executes. The classification is right — these are derived, not state, and must
not be copied — but the regeneration half was never wired, so the paths simply
fall through as unallowlisted and stay absent.

## Evidence

Every live worktree, counted:

| worktree | skills | agents | memory/shipped |
|---|---|---|---|
| primary | 35 | 7 | 31 |
| `.worktrees/SL-231-p01` (worker fork) | 0 | 1 | 0 |
| `.worktrees/SL-186-p04` (worker fork) | 0 | 1 | 0 |
| `.dispatch/SL-209` (coordination tree) | 0 | 1 | 0 |
| `.worktrees/SL-254-audit` (adopted) | 0 | 1 | 0 |
| `.worktrees/SL-248` | 35 | 4 | 31 |

`SL-248` is the exception that proves it: its whole `.doctrine/state` and derived
tiers were **hand-copied** wholesale, which is also how it acquired a foreign
`boot.md` and a `boundaries.toml` (see `ISS-350`). Doing it by hand is the only
way it happens today.

## What is and is not already covered

The boot snapshot alone is partly covered, by accident of harness rather than by
design: the claude `SessionStart` hook runs `doctrine prompt resolve`, which
regenerates `.doctrine/state/boot.md` in whatever tree the session opens in.
That is why `.worktrees/SL-254-audit` has a fresh local snapshot while the pi
worker forks have none.

Two things follow. It is **late** — provisioning finishes with the tree unusable
and the first session repairs it — and it is **harness-conditional**: a worker
that is not a claude session never triggers it. Skills and the shipped memory
corpus have no equivalent fallback at all.

## Why it matters more now

An agent in a fork has no `/route`, no `/execute`, no `/audit`, and no shipped
memory to retrieve. It is the same repo with its instrumentation missing, which
is a quiet failure: nothing errors, the agent simply cannot reach the skills the
governance assumes it is following.

It also generalises past this repo. `ISS-350` §10 records the direction of
travel — capsules replace dispatch, and a capsule is a fresh clone whose derived
tier is likewise absent. The sibling project dropped doctrine's boot snapshot
from its sideband allowlist on the rule that **state a consumer regenerates per
checkout does not travel** (oubliette `NOTES item 32`), whose positive half is
that regeneration belongs to provisioning. That repo needs the same hook —
declared generically as *the command a target runs in a fresh checkout* — and
`doctrine install` is the value it would supply. Fixing it here is what makes
that answer available there.

## Fix direction

Run `doctrine install` (or the subset that regenerates derived runtime) as a step
of fork provisioning, after the copier at `worktree/fork.rs:188`. Questions worth
settling before implementing, not now:

- **Cost.** `install` does a memory sync and a skills write per fork. Measure it
  before making it unconditional — a fork is meant to be cheap.
- **Idempotence and failure posture.** A provisioning step that fails must not
  leave a half-provisioned fork; decide whether it degrades (warn, continue) like
  the boundary-capture tail, or fails the fork.
- **Scope.** Whether the boot snapshot is regenerated here too, or left to the
  session hook that already does it. Doing it at provision makes the tree
  self-sufficient and harness-independent, which is the stated principle.
- **Which verb owns it.** `worktree fork` is the sole creation+provision+mark
  verb, so it is the natural home; `run_provision` is the *copier* and should
  probably stay one.

## Verification

- `worktree/fork.rs:180`–`193` — the four provisioning steps, none of them
  regenerative.
- `worktree/allowlist.rs:99` — `DERIVED_RUNTIME` and the claim to correct.
- `.claude/settings.json` `SessionStart` — `prompt resolve` + `memory sync`, the
  accidental partial cover.
- The counts above reproduce with a per-worktree `ls` of `.doctrine/skills`,
  `.doctrine/agents`, `.doctrine/memory/shipped`.
