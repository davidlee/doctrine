# DEC-156: Backend admission proves denial by one-property-removed controls

REQ-459's suite is an executed conformance suite parameterised by backend, not a Linux test file. A future backend is admitted by implementing the backend contract and passing the same assertions; it never edits them (REQ-459 criterion 3). On a host where the backend is unavailable the suite reports **not admitted** — never a green skip — and admission is a recorded verdict naming backend, host, and date, so criterion 3's "independently" has an artefact to point at.

**A shape-only suite was rejected.** Asserting the argv and mount posture purely is hermetic and cheap, and proves only that the profile was written as intended. REQ-459's criteria are claims about enforcement, criterion 2 admits Linux on "SL-241 evidence and production acceptance tests", and this slice's Non-Goals already state that the SL-241 rig's hostile rows carry across as behaviour, as production acceptance tests. Shape assertions are necessary and never sufficient — this is risk R3 stated concretely.

**The probes execute against a backend primitive, not against bubblewrap directly.** The backend exposes a minimal capability — execute this argv inside the capsule, return exit status and termination facts — which the suite drives and the later launch slice builds on. This is not the launch verb: no work contract, no harvest, no result publication. REQ-459's process-tree-teardown and resource-observation criteria are claims about that primitive and have nowhere else to attach, and a suite driving bubblewrap itself would certify a path production never takes.

**Denial is proven by a one-property-removed control, not by an unconfined baseline.** The inference required is that the probe was refused *because of* the enforcement under test, and what licenses it is a capsule with everything intact except that one axis. An unconfined baseline supports only the weaker claim that the attempt can succeed somewhere, and carries every hazard the paired execution introduces. One-property-removed is SL-241's mutant-driver discipline and keeps the allowlist, the namespace posture, and the decoy targets present under both arms. SL-241's rule stands: a guard never seen to fire is not known to work (`probe-guards.sh`, EX-10), so each of the eight properties carries its paired execution.

**Correction, 2026-08-06 — the count is eight, not seven.** This record originally said seven, and `SL-248`'s design drafted a property table against that number by merging *process-tree teardown* with *trusted observation of resource limits and termination* into one row, on the reasoning that both ask what the trusted parent can establish about a process it did not trust. `RV-346` `F-2` (external pass, raiser codex) refuted it, and the refutation is this record's own principle turned on its arithmetic: the two are independent enforcement claims, so a backend can reap every descendant and still misclassify a timeout as a signal, or classify termination perfectly and leave a grandchild alive. A control that removes both axes at once cannot establish which guard produced the paired result — exactly what one-property-removed exists to prevent — so the merged row would have admitted a backend failing one of `SPEC-030` § Platform backend contract's eight clauses. Teardown and observation therefore carry separate properties, separate probes, and separate one-axis controls, and the suite's eight rows stand in one-to-one correspondence with the spec's eight clauses. Only the number changes; every argument above it is untouched, and the correction was authorised by the human author rather than taken mid-run.

**Second correction, 2026-08-06 — the count is nine, and the one-to-one sentence above does not survive it.** `RV-346` `F-19` (external pass, raiser codex, round 3) executed the mutant this suite did not have: a backend that binds exactly the declared input set and binds it *writable*. Every row of the design's table passed it, because no row ever wrote to something it had asked to be read-only — the rows execute from bound paths, read undeclared ones, and write only where writing is expected. Such a backend hands every capsule mutable shared host state, including the per-base export DEC-157 makes the immutable input and every concurrent transaction on that base shares.

The arithmetic error is the mirror of the first one. There, two clauses were wrongly merged into one row. Here, one clause — `SPEC-030`'s *an explicit base and input set* — was wrongly assumed to be one claim. It is two, and they fail apart in both directions: a backend can bind only the declared paths and bind them writable, or bind read-only and bind more than was declared. Neither implies the other, so under this record's own principle they take separate rows, separate probes, and separate one-axis controls. Immutability's unique mechanism is the read-onlyness of a binding that exists under both arms, which is what makes it controllable at all.

So the suite has **nine rows over eight clauses**, and the claim that its rows stand in one-to-one correspondence with the spec's clauses is withdrawn: every clause is covered, and one clause is covered twice, because one control can only remove one mechanism. Only the number and that correspondence sentence move; every argument above them is untouched. Authorised by the human author rather than taken mid-run, on the same terms as the first correction.

**Hazardous properties reach decoys, never the real thing.** Bounded filesystem reach and denial of canonical state and credentials need a target. A decoy canonical repository and a decoy credential file are bound at the allowlist boundary; the probe asserts denial against the decoy and the control, allowlist widened by exactly one entry, asserts reach against the same decoy. The real canonical repository and real credentials are outside the mount set under both arms, so no arrangement of the suite touches them.

**Residual hazards, per property.** Network reachability is asserted against a loopback listener held trusted-side rather than against the internet — `--unshare-all` denies that as it denies egress, so the distinction holds offline and in CI with no external contact. Process-tree teardown is contained by `timeout -k` outside the sandbox plus a process-group kill in the harness teardown, the arrangement `sandbox.sh:288` already uses; the control's orphan is what the outer reaper exists for. Resource exhaustion writes into a size-capped tmpfs, so the unbounded write is bounded by the mount rather than by the host disk.

**The capsule root is not on tmpfs.** Self-cleaning is tempting and would falsify two things: REQ-461's free-space probe reads real available space, and resource observation on a tmpfs measures the mount's size rather than the disk's. The capsule root sits on real disk under a per-run temporary root that the fixture removes on the way out.

**Cleanup is a test-harness responsibility.** Removing that temporary root must not mint a product-side capsule-delete capability for test convenience. DEC-133 and DEC-137 hold that a harvested capsule is live work; a delete primitive introduced here for tidiness is what a later slice would reach for.

**Third correction, 2026-08-06 — the count is eleven, and the rows are derived from channels rather than from clauses.** `RV-346` `F-19` moved this count once by splitting a clause; `F-20`'s round-4 successor `F-26` moved it again, and this time the lesson is not arithmetic. Codex built the mutant the brief asked for: a backend identical to a conforming one on every observation the suite made, but preserving one inherited file descriptor across `execute`. It passed all nine rows, because every one of them reasons about *paths* and an already-open descriptor is not a path — so the capsule receives an open credential file or a preconnected socket through a channel nothing in the suite looks at. The mechanism was isolated from the reviewer's own sandbox before it was raised: a direct child given an inheritable descriptor read the decoy and exited 0, while the bubblewrap-shaped profile exposed no bytes. `BubblewrapBackend` closes descriptors; the suite was what failed.

**The class fix is a channel ledger, and writing it found a second hole.** The suite had been deriving one row per `SPEC-030` clause. A clause is written in the vocabulary of what a capsule must not *have*; a row has to be written in the vocabulary of the mechanism by which it *gets* it. Those are not in correspondence, and clause 2 — *an explicit base and input set* — names an outcome reachable by four distinct mechanisms while naming none of them. `sec-2` now carries the closed enumeration of ways authority crosses `execute`, each channel naming the row that proves it. Filling that table in showed the **environment** channel had no executed row either: `CapsuleEnvVar` being a closed enum binds callers and says nothing about what a backend inherits, and the only proof `--clearenv` is present was an argv shape assertion — which this record itself holds to be necessary and never sufficient. So the count moves nine → eleven: row 10 closes descriptors, row 11 closes the environment.

**Provenance, stated exactly.** The human author authorised the tenth row and, in the same instruction, directed that the remediation fix the class rather than the instance. The eleventh is what that direction produced — it was not raised by the review and was not taken as an independent judgement mid-run; it is the first cell the mandated ledger showed empty. Recorded this way rather than as a bare count so a later reader can tell which part was authorised directly and which followed from the authorised method.

**What this says about the correction sequence.** Three corrections, seven → eight → nine → eleven, every one found by an adversary constructing the backend the suite would wrongly pass and none by anyone re-reading the rows. Four of the added rows are clause 2. The ledger does not make the suite complete — an enumeration asserting its own completeness is precisely the invariant `F-26` refuted, one level up — and `sec-9` residual 5 records what it leaves open, including the channels it lists but does not row. What it changes is the failure mode: from *nobody thought of this channel* to *this channel has a blank cell*.

**A row's containment is part of its payload.** `RV-346` `F-27` strengthened row 7 — *orphan a descendant* was a representative negation of process-tree teardown, not the strongest one, and a backend reaping only the original process group passed it while a `setsid` descendant survived. The payload now escapes the session. That invalidated this record's own containment note above: a process-group kill cannot reap the survivor the strengthened control creates, so teardown containment is a session kill. Whenever a payload is strengthened, the harness's ability to clean up after the control arm has to be re-derived with it, or the suite leaks a process per run and says nothing.
