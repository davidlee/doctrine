# DEC-157: Capsules clone inside from a per-base immutable export

A capsule's immutable input is a **per-base bare export** — a repository holding exactly the contracted commit's history, built trusted-side once per base and shared read-only by every capsule on that base. It is bound read-only into the capsule, and the capsule runs `git clone --no-hardlinks` from it *inside* the sandbox, so no working tree is ever materialised trusted-side. That clone-inside mechanism is SL-241's, proven at its EX-8; `--no-hardlinks` is not tuning but the mitigation `provision.sh:56-61` records, since a local clone hardlinks object files by default and a hostile capsule corrupting a shared object would corrupt its source.

**The export is mechanism-neutral; the read-only binding is not.** These are two separable halves and the split is deliberate. The trusted side produces an immutable per-base export — a plain artefact with no confinement mechanism in it, reusable by any backend. *How that export becomes readable inside the capsule at a known path, and nothing else of the host with it,* is a capability of the backend contract (DEC-156), not part of this decision. Bubblewrap realises it as a read-only bind; a Docker backend would use a volume, a virtual machine a share, and a Landlock-supplemented arm a path rule over an existing directory. A future backend inherits the export and the clone-inside posture unchanged and supplies only its own realisation of the capability.

**Why an export rather than the canonical repository itself.** Binding the canonical repository is what the spike's fixture does and costs nothing trusted-side, but it places the canonical object store inside the mount set: REQ-448 criterion 1's denial of shared object storage then rests on a read-only mount rather than on absence, and the capsule can read every ref and branch rather than only its contracted history. The hardlink mitigation additionally fails silently — a later clone invocation that drops the flag reintroduces the hazard with nothing to notice. With an export the canonical repository is outside the mount set under every arm, which is the structural form of the same denial, and REQ-450's "explicit immutable inputs" becomes a physical hashable object rather than a description. Sharing one export across capsules is not shared *mutable* state, so REQ-450 criterion 1 is untouched. A bundle file is the same idea carrying a format question and no advantage.

**Cost.** One bare repository per distinct base. In dispatch every phase of a slice shares a base, so one export serves many capsules. Implementation rides `git init --bare` plus the existing fetch at `src/git.rs:2718`; there is no clone or bundle helper in `src/git.rs` to reuse, so the provisioning half is net-new whichever input form is chosen.

**Layout.** A per-transaction root beneath a configurable capsule root, holding the clone, the writable temporary area, the agent home, and the output area as siblings. Distinct host directories map to the spike's fixed inner layout — the host path is never reproduced inside, which would read the parent directory of every other capsule into existence as a mountpoint chain (`sandbox.sh:58-66`). The transaction id is allocated trusted-side, so this does not touch the parked QUE-208. The capsule root is what REQ-461's free-space probe measures, the second reason it is not on tmpfs (DEC-156).

**Evidence for REQ-450 criterion 1.** Provision two transactions from one base and assert distinctness on each of the five axes the criterion names — checkout, repository, runtime, process, temporary state — by writing through one and observing absence in the other, never by comparing paths. Under DEC-156's discipline the paired control provisions the second transaction into the first's root and observes that the writes *are* visible, which is what makes the green arm carry information.
